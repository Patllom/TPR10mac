# คู่มือทะเบียนบุคลากร Module 6A

## ขอบเขต

Module 6A จัดการต้นสังกัดหลัก สายบังคับบัญชา และผู้รับผิดชอบ HR พร้อมกฎตรวจสิทธิ์และคัดเลือกผู้อนุมัติ ยังไม่มีการถ่ายรูป ลงเวลา เก็บ GPS หรือยื่นคำร้อง สิ่งเหล่านี้อยู่ใน 6B–6D

## เตรียมฐานข้อมูลและสิทธิ์

1. สำรองฐานข้อมูลและทดสอบกู้คืนในฐานข้อมูลแยกก่อนใช้ migration จริง รวมประวัติ migration และกุญแจป้องกันข้อมูลตามคู่มือระบบเดิม
2. ตรวจ migration `AddAttendanceDirectory` และ `ProtectAttendanceDirectoryHistory` ในสภาพแวดล้อมทดสอบก่อนนำขึ้นระบบ การอัปเกรดไม่มอบสิทธิ์ใหม่ให้ Admin อัตโนมัติ
3. ผู้มี `roles:manage` ที่ผ่าน MFA ล่าสุด สร้างบทบาทผู้จัดการทะเบียนผ่าน `POST /api/v1/roles` แล้วกำหนด `attendance:directory-manage` ผ่าน `PUT /api/v1/roles/{id}/permissions` และมอบบทบาทให้ผู้ปฏิบัติงานอีกคนผ่าน `PUT /api/v1/users/{id}/roles` ใช้ DTO ตาม OpenAPI และ CSRF token ของ session ปัจจุบัน
4. ใช้การแบ่งหน้าที่ ไม่เพิ่มสิทธิ์ attendance ให้ตนเองโดยแก้บทบาทที่ถืออยู่หรือมอบบทบาทให้ตนเอง การมีสิทธิ์จัดการทะเบียนไม่ให้สิทธิ์ดูรูปหรือพิกัดของพนักงาน
5. สิทธิ์ `attendance:team-read`, `attendance:hr-read`, `attendance:approve-supervisor`, `attendance:approve-hr` ต้องมอบอย่างชัดเจนผ่านบทบาทประเภท approval/accounting/finance-data-access ที่เหมาะสม การสร้าง HR assignment อย่างเดียวไม่ให้ capability เหล่านี้หรือสิทธิ์ลงเวลาใน Site

## การใช้งานหน้า Portal

เปิด `/portal/admin/attendance-directory` ด้วยบัญชีผู้จัดการทะเบียนที่ยืนยัน MFA แล้ว เมนูจะแสดงตามสิทธิ์ แต่ API ยังคงตรวจสิทธิ์ปัจจุบันทุกครั้ง

- เลือกประเภทต้นสังกัด สายบังคับบัญชา หรือผู้รับผิดชอบ HR
- ค้นหาผู้ใช้/หน่วยงาน/แผนกและเปลี่ยนหน้ารายการได้ ระบบไม่โหลดข้อมูลทั้งองค์กรพร้อมกัน
- การเพิ่มต้นสังกัดต้องระบุผู้ใช้ หน่วยงาน แผนก และเหตุผล; การกำหนดหัวหน้าต้องมีต้นสังกัดที่ใช้งานอยู่ในหน่วยงานเดียวกัน และไม่มีวงจรสายบังคับบัญชา
- การเปลี่ยนต้นสังกัดหรือหัวหน้าให้เลือก “เปลี่ยนรายการ” ของแถวปัจจุบัน ระบบส่ง version ที่อ่านมาจริง ห้ามกรอก version ที่คาดเดาหรือส่งซ้ำอัตโนมัติ
- การสิ้นสุดต้องระบุเหตุผลและเลือก “สิ้นสุดรายการ” ประวัติยังอยู่ ไม่ใช่การลบ; HR เปลี่ยนโดยสิ้นสุดการมอบหมายเก่าและสร้างการมอบหมายใหม่
- ประวัติที่สิ้นสุดแล้วอ่านได้อย่างเดียว ไม่แก้ย้อนหลัง วันเริ่ม–สิ้นสุดใช้เวลาปัจจุบันจาก server แบบ UTC และช่วงต้นรวม/ปลายไม่รวม
- ต้นสังกัดและหัวหน้าใช้ version เพิ่มต่อเนื่องข้ามประวัติ เช่น รายการแรก1 ปิดเป็น2 รายการแทนที่3 ไม่ถือว่ารายการใหม่ทุกครั้งต้องเริ่ม1

## เมื่อทำรายการไม่ได้

| ผลลัพธ์ | การดำเนินการ |
| --- | --- |
| 401 | เข้าสู่ระบบใหม่ session อาจถูกถอนจากการแก้สิทธิ์หรือต้นสังกัด |
| 403 | ตรวจ capability, MFA และข้อห้ามเพิ่มอำนาจตนเอง; ให้ผู้มีอำนาจอีกคนทำรายการที่เกี่ยวข้องกับตน |
| 404 | ตรวจว่าผู้ใช้และหน่วยงานยังใช้งานอยู่และความสัมพันธ์ถูกต้อง |
| 409 | ข้อมูลหรือ version เปลี่ยนแล้ว โหลดข้อมูลใหม่ ตรวจผลก่อนส่งด้วยตนเอง ห้ามส่ง mutation เก่าซ้ำ |
| 429 | รอตามเวลาที่ระบบกำหนด |
| 500/503 หรือเครือข่ายขาด | อย่าสรุปว่ารายการถูกยกเลิกจาก status เพียงอย่างเดียว ตรวจทะเบียนและ audit ก่อนส่งใหม่; หน้าเว็บซ่อนข้อมูลเมื่อยืนยันบัญชีไม่ได้และเก็บร่างในหน่วยความจำเดิมชั่วคราว |

เมื่อกด “โหลดข้อมูลใหม่” หลังความผิดพลาด ข้อมูลจะยังซ่อนจน API ที่จำเป็นตอบสำเร็จครบ การกดโหลดใหม่ไม่ส่งรายการแก้ไขซ้ำ ร่างไม่ใช่ข้อมูลที่บันทึกถาวร: การเปลี่ยนบัญชี ออกจากระบบ หรือโหลดหน้าใหม่ทั้งหน้าจะทิ้งร่างเพื่อป้องกันข้อมูลข้ามบัญชี

## ผลต่อความสัมพันธ์และ session

การเปลี่ยนหรือสิ้นสุดต้นสังกัดจะสิ้นสุดสายบังคับบัญชาที่เกี่ยวข้องทั้งเจ้าตัวและลูกทีมของผู้ใช้คนนั้นแบบระมัดระวัง ผู้จัดการต้องกำหนดสายที่ถูกต้องใหม่ ไม่คืนสิทธิ์เก่าโดยอัตโนมัติเมื่อย้ายกลับแผนกเดิม

การปิดบัญชี หน่วยงาน หรือแผนก สิ้นสุดความสัมพันธ์และถอน session ที่ได้รับผลใน transaction เดียวกับ audit การเปิดใช้งานกลับไม่ฟื้นความสัมพันธ์ที่สิ้นสุดแล้ว การแก้ไขที่ไม่มีผลจริงไม่ควรถอน session เพิ่ม

พนักงานดูข้อมูลตนเองได้ หัวหน้าดูเฉพาะลูกทีมโดยตรงและไม่เห็นรูป HR ดูได้เฉพาะหน่วยงานที่ได้รับมอบหมายและมี capability เพิ่มเติม ผู้ดูแลระบบไม่มีทางลัดดูข้อมูลเหล่านี้

## การอนุมัติในโมดูลถัดไป

ผลคัดเลือกผู้อนุมัติใน 6A เป็นข้อมูลสำหรับสร้างเส้นทาง ไม่ได้อนุมัติคำร้อง หัวหน้าและ HR ต้องเป็นคนละคนและไม่ใช่ผู้ยื่น กรณีหัวหน้ายื่นเองใช้ผู้บังคับบัญชาของหัวหน้าคนนั้น หากย้ายหน่วย ไม่มีผู้อนุมัติครบ หรือความสัมพันธ์เปลี่ยน ต้องหยุดและจัดเส้นทางใหม่

โมดูลคำร้องต้องตรวจ session, MFA, capability, ความสัมพันธ์ และ version ซ้ำก่อนทุกการตัดสินใจ ห้ามถือ snapshot เก่าว่าให้สิทธิ์อนุมัติถาวร

## ข้อจำกัดการปฏิบัติการ

ไม่ downgrade โดยหวังให้ลบประวัติอัตโนมัติ Migration จะปฏิเสธเมื่อมีข้อมูลทะเบียนหรือ grant ใหม่ที่เกี่ยวข้อง ต้องวางแผนย้าย/เก็บประวัติและถอน grant อย่างชัดเจนก่อน การลบข้อมูลจริงไม่อยู่ในคู่มือนี้

การเขียนทะเบียนรองรับ READ COMMITTED และใช้ lock ร่วมของระบบตัวตน ต้องประเมิน throughput ก่อน Production ผู้ดูแลฐานข้อมูลโดยตรงและการสมคบกันของผู้จัดการหลายคนยังต้องอาศัยการกำกับดูแลและการตรวจ audit

การทดสอบ HTTPS ใช้ฐานข้อมูลและบัญชีสังเคราะห์แยกทั้งหมด พร้อม CA เฉพาะ browser profile ทดสอบ ไม่เพิ่มความเชื่อถือ CA ระดับเครื่อง และไม่ใช้บัญชี Preview จริงในเอกสารหรือ fixture
