# ตั้งต้นผู้บริหารสิทธิ์การเงิน Module 7A

คำสั่งนี้ใช้ตั้งต้นครั้งเดียวต่อบริษัท (`workspaceId`) จากหลักฐานบริษัทที่ตรวจสอบภายนอกแอปแล้ว ผู้ดูแลระบบหรือสมาชิกทีมไม่ได้สิทธิ์การเงินอัตโนมัติ เป็นคำสั่ง local operator ผ่าน stdin ไม่ใช่ HTTP endpoint และไม่ทำงานเมื่อเปิดเว็บตามปกติ

ระหว่างพัฒนาและทดสอบใช้เฉพาะฐานทิ้งได้ใน test container ห้ามนำตัวอย่างนี้ไปรันกับฐานข้อมูลผู้ใช้จริง การเปิดใช้จริงต้องผ่านกระบวนการบริษัทและ final verification ของ controller แยกต่างหาก มือถือจริงและ NAS จริงยังพักการตรวจ

## เงื่อนไขที่บริษัทต้องตรวจ

1. ตรวจเอกสารมอบอำนาจจริง รายชื่อผู้รับ ขอบเขตบริษัท/โครงการ ชนิดสิทธิ์ที่มอบต่อได้ วงเงิน วันเริ่ม/สิ้นสุด และเลขอ้างอิงหลักฐานภายนอก เอกสารต้องครอบคลุมทุก grant ในชุด
2. ผู้รับรอง (`certifier`), ผู้ตรวจอิสระ (`reviewer`) และผู้ดำเนินการ (`operator`) ต้องเป็นสามบุคคลจริงที่ต่างกัน ทั้งสามคนห้ามเป็นผู้รับสิทธิ์คนใดในชุด แม้ใช้หลายบัญชีหรือรับสิทธิ์คนละโครงการ
3. ตรวจบัญชีและรหัสบุคคลที่บริษัทรับรองโดยชัดแจ้ง บัญชีหลายบัญชีของคนเดียวกันต้องใช้ person ID เดียวกัน ห้ามสร้าง person ID ใหม่เพื่อหลบการแยกหน้าที่ ไม่อนุมานบุคคลจากชื่อ บทบาท หรือ user ID
4. ทุกบัญชีใน manifest ต้องมีอยู่จริง เปิดใช้ อยู่ในบริษัท/แผนกที่เปิดใช้ มีสมาชิกบุคลากรปัจจุบันตรงบริษัทเพียงหนึ่งรายการ และมี MFA ที่ยืนยันแล้ว ไม่ถูกถอน และไม่ใช่ข้อมูลในอนาคต ทุกโครงการที่ระบุต้องเปิดใช้และอยู่ในบริษัทนั้น
5. ตรวจความเป็นอิสระของผู้ตรวจและสิทธิ์เข้าถึงเครื่องผู้ดำเนินการ เก็บเอกสารรับรอง/ผลตรวจภายนอกแอปในระบบบริษัทที่ควบคุมการเข้าถึงและตรวจสอบย้อนหลังได้

รหัสผู้รับรอง ผู้ตรวจ และผู้ดำเนินการใน manifest **ไม่ใช่ลายเซ็นดิจิทัล** แอปตรวจเงื่อนไขข้อมูลและความต่างของรหัสบุคคล ไม่ได้พิสูจน์ทางคริปโตว่าบุคคลเหล่านั้นลงนามหรือยินยอม และการตรวจ MFA enrollment ไม่ใช่การทำ MFA challenge ในคำสั่งนี้ ผู้ดำเนินการต้องตรวจเอกสารบริษัทจริงและผู้ตรวจอิสระก่อนรัน

ผู้ที่เข้าถึงเครื่อง กระบวนการรัน โค้ด หรือฐานข้อมูลโดยตรงอยู่ใน trust boundary ของโครงสร้างพื้นฐานนอกแอป ต้องแยกอำนาจ ควบคุมบัญชี OS/DB และดูแลหลักฐานนอกแอป การกรอกชื่อ/ID หรือมี hash ของ manifest ไม่แทนการรับรองตัวตนหรือลายเซ็น

## รูปแบบ manifest

ส่ง JSON UTF-8 หนึ่ง object ทาง stdin แบบ redirect เท่านั้น ต้องระบุ field ตามตัวอย่างครบ รวม `projectId`, `approvalLimit`, `endsAtUtc` แม้ค่าเป็น `null` ชื่อ field แยกตัวพิมพ์เล็ก/ใหญ่ ไม่รับ field ที่ไม่รู้จักหรือ key ซ้ำ ไม่รับ comment/trailing comma

ตัวอย่างต่อไปนี้เป็นข้อมูลสมมติทั้งหมด ต้องแทนทุก ID ด้วยข้อมูลที่บริษัทรับรองและตรวจวันเวลาตามเอกสาร ไม่มีการตั้งวงเงินธุรกิจจริงให้บริษัท:

```json
{
  "commandId": "76000000-0000-0000-0000-000000000101",
  "workspaceId": "71000000-0000-0000-0000-000000000001",
  "operator": {
    "userId": "71000000-0000-0000-0000-000000000034",
    "personId": "72000000-0000-0000-0000-000000000034"
  },
  "certifier": {
    "userId": "71000000-0000-0000-0000-000000000031",
    "personId": "72000000-0000-0000-0000-000000000031"
  },
  "reviewer": {
    "userId": "71000000-0000-0000-0000-000000000032",
    "personId": "72000000-0000-0000-0000-000000000032"
  },
  "reason": "ตั้งต้นตามเอกสารบริษัทและผลตรวจอิสระที่รับรองแล้ว",
  "evidenceReference": "EXAMPLE-EXTERNAL-APPROVAL-001",
  "grants": [
    {
      "recipient": {
        "userId": "71000000-0000-0000-0000-000000000033",
        "personId": "72000000-0000-0000-0000-000000000033"
      },
      "projectId": null,
      "capabilities": ["grant.propose", "grant.review", "grant.revoke"],
      "delegableCapabilities": ["grant.propose", "grant.review", "grant.revoke", "policy.review"],
      "approvalLimit": null,
      "startsAtUtc": "2026-10-20T00:00:00Z",
      "endsAtUtc": "2026-11-20T00:00:00Z"
    },
    {
      "recipient": {
        "userId": "71000000-0000-0000-0000-000000000035",
        "personId": "72000000-0000-0000-0000-000000000035"
      },
      "projectId": null,
      "capabilities": ["grant.propose", "grant.review", "grant.revoke"],
      "delegableCapabilities": ["grant.propose", "grant.review", "grant.revoke", "policy.review"],
      "approvalLimit": null,
      "startsAtUtc": "2026-10-20T00:00:00Z",
      "endsAtUtc": "2026-11-20T00:00:00Z"
    }
  ]
}
```

ข้อจำกัดและความหมาย:

- `commandId` เป็น UUID ของการดำเนินการ ต้องไม่เคยใช้ และ `workspaceId`/user ID/person ID ต้องไม่เป็น UUID ศูนย์
- `capabilities` เป็นสิทธิ์ใช้งานเริ่มต้น เลือกได้เฉพาะ `grant.propose`, `grant.review`, `grant.revoke` อย่างน้อยหนึ่งรายการ ห้ามซ้ำ ไม่อนุญาตสิทธิ์ใช้ข้อมูลธุรกิจ อนุมัติยอดเงิน ตรวจการเงิน หรือจ่ายเงินโดยตรง
- `delegableCapabilities` ระบุอำนาจมอบต่อโดยชัดแจ้ง แยกจากสิทธิ์ใช้งาน รับเฉพาะ `policy.edit.company`, `policy.edit.project`, `policy.review`, `grant.propose`, `grant.review`, `grant.revoke`, `request.approve`, `finance.check`, `payment.record`, `report.read` ห้ามซ้ำ อาร์เรย์ว่างหมายถึงไม่มีอำนาจมอบต่อ ไม่เติมให้อัตโนมัติ
- `approvalLimit` เป็นอำนาจวงเงินที่ใช้ตรวจการมอบต่อ ไม่ให้สิทธิ์ใช้ยอดเงินโดยตัวมันเอง `null` หมายถึงไม่มีอำนาจยอดเงิน ไม่ใช่ไม่จำกัด ค่าเลขเป็น decimal บาท/สตางค์ ไม่ติดลบ มีทศนิยมไม่เกินสองตำแหน่ง และอยู่ภายในความจุฐานข้อมูล `9999999999999999.99` ซึ่งเป็นเพดานชนิดข้อมูล ไม่ใช่วงเงินที่บริษัทได้รับ ห้ามบวกหลาย grant เพื่อขยายอำนาจ
- `projectId: null` ใช้กับงานระดับบริษัทเท่านั้น ไม่ใช่ wildcard โครงการ ต้องระบุแต่ละโครงการที่เอกสารรับรองเป็น grant แยก ไม่ซ้ำคู่บัญชีผู้รับ/โครงการในชุดเดียวกัน
- วันเวลาเป็น ISO 8601 พร้อม `Z` หรือ offset; บันทึก UTC เวลาเริ่มต้องไม่เป็นค่าขอบสุดของชนิดข้อมูล เวลาสิ้นสุดต้องหลังเวลาเริ่มและยังไม่หมดอายุขณะ commit `endsAtUtc: null` หมายถึงเอกสารไม่ได้กำหนดวันสิ้นสุด ไม่ทำให้อำนาจที่มอบต่อข้ามขอบเขตได้ ผู้รับใช้ grant ที่เริ่มในอนาคตได้เมื่อถึงเวลาเท่านั้น
- `reason` และ `evidenceReference` ไม่ว่าง ยาวไม่เกิน 1,000 อักขระ และไม่มี control character เลขอ้างอิงควรเป็นรหัสเอกสาร ไม่ใช่เนื้อหาเอกสาร เลขประจำตัวส่วนบุคคล credential, token หรือ URL ที่มี secret เพราะจะเก็บในหลักฐานและ audit
- ขนาด manifest ไม่เกิน 65,536 อักขระ จำนวน grant 1–100 และ JSON depth ไม่เกิน 16 หากบริษัทมีเกินขอบเขตนี้ให้หยุดเพื่อจัดการกระบวนการก่อนตั้งต้น ห้ามแบ่งรันหลายชุดให้บริษัทเดียวกัน
- หากยังไม่มี person/link จะสร้างเฉพาะ ID ที่ระบุในรายชื่อรับรอง หากมี mapping อยู่แล้วต้องตรงกันและมี active link ปัจจุบันหนึ่งรายการ ไม่แก้ประวัติ ไม่คืน link ที่สิ้นสุดแล้ว ไม่รับ link ในอนาคตหรือประวัติที่ผูกกับบุคคลอื่น หากพบให้หยุดเพื่อแก้กระบวนการ identity ที่ได้รับอนุมัติแยก

## วิธีดำเนินการที่ได้รับอนุมัติ

เตรียมฐานที่ migrate แล้วและชุดโปรแกรมที่ผ่านการตรวจ ตั้ง `TPR10_CONNECTION_STRING` ผ่านช่องทาง secret ของเครื่องที่ได้รับอนุมัติ คำสั่งไม่มีค่า connection เริ่มต้นและไม่ทำ migration/seed บัญชีเอง ห้ามใส่ connection string หรือ manifest ใน argument/shell history/log

เก็บ manifest ในตำแหน่งที่จำกัดสิทธิ์อ่านตามระเบียบบริษัท ตัวอย่างคำสั่งต่อไปนี้เป็นแบบสำหรับผู้ปฏิบัติการ ไม่ได้ถูกรันกับข้อมูลจริงระหว่างพัฒนา:

```sh
dotnet /secure/release/TPR10.Api.dll --bootstrap-finance < /secure/approved/finance-bootstrap.json
```

ใช้ flag เดียวนี้เท่านั้น ไม่ใช้ร่วมกับ `--bootstrap-admin` และไม่ใส่ JSON หลัง flag ผล stdout/stderr เป็นข้อความไทยสั้น ไม่มีการพิมพ์ manifest, ID บุคคล, connection string หรือรายละเอียด exception

| Exit code | ความหมายและการดำเนินการ |
|---|---|
| 0 | Commit สำเร็จ ตรวจหลักฐานที่เก็บในฐานและเอกสารบริษัทตามอำนาจที่ได้รับ |
| 2 | ปฏิเสธเพราะเคยตั้งต้น/มีประวัติ grant, command ID ถูกใช้, บุคคลหรือบัญชีไม่ผ่านเงื่อนไข, scope ไม่ตรง หรือหมดอายุระหว่างทำงาน ห้ามลบ guard เพื่อรันซ้ำ |
| 64 | รูปแบบคำสั่ง/manifest ไม่ถูกต้อง, ไม่ redirect stdin, ไม่ตั้ง connection หรือข้อมูลวันที่ไม่ผ่านก่อนเริ่มธุรกรรม ตรวจเอกสารต้นทางและแก้ input ตามที่รับรอง |
| 1 | เกิดข้อผิดพลาดระหว่างอ่านหรือดำเนินการ ตรวจระบบและผลธุรกรรมจากหลักฐานก่อนลองใหม่ โดยไม่เปิดเผย secret ใน log |

กรณีการเชื่อมต่อขาดระหว่างตอบผล commit อาจไม่ทราบผลจาก exit code เพียงอย่างเดียว ต้องตรวจ receipt ด้วยกระบวนการที่ได้รับอนุมัติก่อน retry ห้ามสรุปว่าฐานไม่เปลี่ยนจากข้อความล้มเหลวอย่างเดียว

## หลักฐานและการทำพร้อมกัน

คำสั่งถือ PostgreSQL transaction และ identity advisory lock `7241002` เดียวกับการแก้ identity/organization/grant ตรวจเงื่อนไขใหม่หลังได้ lock แล้วสร้าง person/link, proposal, review, assignment, audit และ receipt ใน transaction เดียว ตรวจความพร้อมและวันหมดอายุซ้ำก่อน commit หากบันทึก audit หรือส่วนใดล้มเหลว transaction จะ rollback ทั้งชุด

เก็บ `FinanceCommandReceipt` ของ batch หนึ่งรายการ พร้อม hash ของ manifest ที่ serialize ตามรูปแบบแอป, ID ผู้ดำเนินการ/ผู้รับรอง/ผู้ตรวจและบุคคล, เหตุผล, เลขอ้างอิงภายนอก และรายการ assignment เก็บ `FinanceBootstrapReceipt` เชื่อมทุก assignment ในชุด โดยมี audit `field-advance.bootstrap.completed` แยกแต่ละ grant ขอบเขต สิทธิ์ วงเงิน และเวลาครบใน proposal/review/assignment ที่เชื่อมกัน

การมี bootstrap receipt ใด ๆ ของบริษัทปิดทางตั้งต้นซ้ำถาวร แม้ถอน/หมดอายุสิทธิ์ทั้งหมดหรือเปลี่ยน command ID แล้วก็ตาม ประวัติ assignment เดิมก็บล็อกการตั้งต้นแม้ไม่มี bootstrap receipt การรันพร้อมกันจึงสำเร็จได้เพียงหนึ่ง batch ต่อบริษัท ไม่ลบ receipt ระหว่างถอนสิทธิ์ และไม่มีช่องทาง bootstrap reset ในแอป การคุ้มครองนี้ไม่อ้างว่าป้องกันผู้มีสิทธิ์แก้ DB โดยตรงได้

## หลังตั้งต้นและการกู้คืน

ใช้วงจรสามคนตามปกติ: ผู้เสนอ ผู้ตรวจอนุมัติ และผู้รับต่างบุคคล พร้อมอำนาจมอบต่อที่ครอบคลุม capability/วงเงิน/ช่วงเวลาและตรงบริษัท/โครงการ ผู้รับรองและผู้ตรวจภายนอกใน bootstrap ไม่ได้สิทธิ์แอปเพิ่มอัตโนมัติ ควรจัดรายชื่อเริ่มต้นให้มีผู้บริหารอย่างน้อยสองคนที่ใช้งานได้และมีอำนาจที่จำเป็นสำหรับกระบวนการปกติ โดยบริษัทเป็นผู้ตัดสินรายชื่อและอำนาจจริง

หากไม่มีผู้บริหารที่ผ่านเงื่อนไข สิทธิ์หมดอายุ ถอนหมด บัญชีสูญหาย หรือโครงการใหม่ไม่มีผู้มีอำนาจตรง scope ให้พักการทำรายการและใช้กระบวนการบริษัทอนุมัติกู้คืน/จัดตั้งอำนาจแยกต่างหาก ไม่เปิด bootstrap ซ้ำอัตโนมัติ ไม่ใช้ admin สำรอง ไม่แก้ DB หรือลบ receipt เป็นขั้นตอนกู้คืนของ runbook นี้ ห้ามขยาย `null` scope ให้ครอบคลุมโครงการเพื่อแก้ปัญหา

การเพิ่มบัญชี/เปลี่ยน mapping หลัง bootstrap เป็นงาน identity governance ที่ต้องได้รับอนุมัติแยก ไม่อยู่ในคำสั่งตั้งต้นนี้ และต้องรักษาประวัติบุคคลเดิมกับข้อห้ามที่มีอยู่
