# คู่มือส่งมอบและดูแลคำขอเงินทดรอง Module 7B

ขอบเขตคือจัดทำคำขอ ยืนยัน ส่งเข้าสายอนุมัติ และติดตามประวัติ ผล `Approved` แสดงว่า **อนุมัติแล้ว รอดำเนินการจ่าย** เท่านั้น ไม่มีการบันทึกจ่าย งวดจ่าย เคลียร์ค่าใช้จ่าย คืนเงิน หรือปิดบัญชีใน 7B การเปิดใช้เงินจริงและส่วน 7C/7D ต้องได้รับอนุมัติและตรวจรับแยกต่างหาก

ใช้ร่วมกับ [คู่มือ 7A](module-7a-policy-permissions.md), [แบบที่อนุมัติ](../superpowers/specs/2026-10-22-module-7b-requests-approvals-design.md) และ [รายงานตรวจรับ](../reports/2026-10-22-module-7b-verification.md) รายงานเป็นแหล่งสถานะ final gates; การมีคู่มือนี้ไม่ได้แปลว่าผ่านการเปิดใช้จริงแล้ว

## 1. เตรียมสิทธิ์และสายงาน

1. ตรวจ workspace/project ที่ถูกต้อง บัญชีและการจ้างงานยังใช้งานได้ และบัญชีเชื่อมกับบุคคลที่รับรองแล้ว การมีหลายบัญชีไม่ทำให้เป็นหลายบุคคล ต้องมี session/MFA ปัจจุบัน
2. ตรวจว่ากติกา 7A สำหรับโครงการมีผลจริง หากใช้กติกาเฉพาะโครงการ ให้ตรวจฐานบริษัทที่ผูกกับฉบับนั้น ห้ามนำบริษัทฉบับใหม่มาผสมโดยข้ามการทบทวน
3. มอบสิทธิ์ผ่านหน้าสิทธิ์การเงินหรือ API 7A ด้วยผู้เสนอ ผู้ตรวจอนุมัติ และผู้รับสิทธิ์ **สามบุคคลจริงต่างกัน** รวมกรณี aliases ผู้เสนอและผู้ตรวจต้องมีอำนาจมอบต่อครอบคลุม capability ระดับ วงเงิน ขอบเขต และช่วงเวลาของข้อเสนอ ไม่อาศัยบทบาท admin หรือเป็นสมาชิกโครงการ
4. ตรวจสายบังคับบัญชาของผู้รับผิดชอบเงินและผู้ดำรงบทบาทหลักของโครงการ ให้มีผู้มีอำนาจครบทุกขั้น และเป็นคนละบุคคลกับผู้รับผิดชอบ/ผู้ยื่นแทน รวมทั้งคนละคนระหว่างขั้นในฉบับเดียวกัน

| การใช้งาน | สิทธิ์ในโครงการและข้อมูลประกอบ |
|---|---|
| ยื่นเอง/เป็นผู้รับผิดชอบเงิน | `request.create` ของผู้รับผิดชอบในโครงการนั้น |
| จัดทำแทน | `request.delegate` ของผู้ยื่นแทน และ `request.create` ของผู้รับผิดชอบในโครงการเดียวกัน |
| อนุมัติ | `request.approve`, `approvalLevels` ตรงขั้น และ `approvalLimit` ครอบคลุมยอดทั้งหมดจากสิทธิ์ต้นทางเดียว |
| ผู้ดำรงบทบาทหลัก | `primaryApprovalLevels` ต้องเป็นส่วนหนึ่งของ `approvalLevels`; เช่น `project-manager` หรือรหัสระดับเพิ่มเติมในกติกา |
| มอบระดับต่อ | `delegableApprovalLevels`/`delegablePrimaryApprovalLevels` พร้อม `delegableCapabilities` และวงเงินที่ครอบคลุมเป้าหมาย |
| อ่านรายงาน | `report.read` แยกต่างหาก ไม่เพิ่มอำนาจยืนยัน/แก้/อนุมัติ |

หัวหน้าใช้สายงานของผู้รับผิดชอบเงิน ไม่ใช่ของผู้ยื่นแทน ลำดับคือ `supervisor` → `project-manager` → ทุกระดับเพิ่มเติมที่ยอดรวมกำหนดตามกติกาที่ตรึงไว้ วงเงินสูงไม่อนุญาตให้ข้ามขั้น สิทธิ์เดิม 7A ที่ยังไม่มีระดับไม่ถูกเปลี่ยนให้อนุมัติ 7B โดยอัตโนมัติ ต้องเสนอ/ตรวจสิทธิ์ใหม่ตามกระบวนการ

ผู้รับผิดชอบและผู้ยื่นแทนห้ามอนุมัติคำขอของตน ผู้อนุมัติคนเดิมกลับมาอนุมัติฉบับใหม่ได้ถ้ายังมีอำนาจ แต่ต้องลงผลใหม่และไม่ติดประวัติข้ามหน้าที่ระดับคำขอ การถอนแล้วให้สิทธิ์ใหม่ การเปลี่ยนบัญชี หรือการสร้างฉบับใหม่ไม่ล้างประวัติข้อห้าม

## 2. ยื่น ตรวจ และดูฉบับเก่า

- หน้าคำขอคือ `/portal/field-advances` และงานรออนุมัติคือ `/portal/field-advances/approvals` เลือกบริษัท/โครงการจากรายการที่มีสิทธิ์ หนึ่งคำขอมีหนึ่งโครงการและหนึ่งผู้รับผิดชอบเงิน
- ผู้ยื่นแทนบันทึกแล้ว “ส่งให้ผู้รับผิดชอบ”; ผู้รับผิดชอบตรวจและ “ยืนยันและส่ง” ผู้ยื่นแทนยืนยันหรือถอนแทนไม่ได้ สมาชิกทีมไม่มีสิทธิ์การเงินเพราะมีชื่อในทีม
- จำนวนได้ไม่เกิน 4 ตำแหน่ง อัตรา/ยอดได้ไม่เกิน 2 ตำแหน่ง ใช้บาทเท่านั้น หมวดมาตรฐานแก้อัตราหรือเลือกเหมาเพื่อหลบไม่ได้ ระบบปัดแต่ละบรรทัดแล้วรวมยอด; ข้อมูลเกินความละเอียดต้องแก้ก่อนส่ง ไม่ตัดทศนิยมเงียบ ๆ
- ก่อนยืนยันให้ตรวจวันที่ รายการ ยอด กติกา และลำดับขั้น หากข้อมูล/กติกาเปลี่ยนให้โหลดและทบทวนใหม่ หลังส่งแล้วแก้เนื้อหาทับไม่ได้
- ส่งกลับต้องระบุเหตุผลและสร้างฉบับแก้ไข ส่งใหม่เริ่มทุกขั้นด้วยกติกาที่มีผลใหม่ ฉบับเก่ายังคงกติกา/อัตรา/ผลเดิม ปฏิเสธเป็นผลถาวร; คัดลอกสร้างคำขอใหม่ที่อ้างต้นทางและไม่ยกผลอนุมัติมาด้วย
- ถอนต้องเป็นผู้รับผิดชอบที่ยังมีสิทธิ์ ระบุเหตุผล และยังไม่อนุมัติครบ ถอนแล้วไม่เปิดกลับและไม่ถอนหลังอนุมัติครบ
- ในหน้ารายละเอียดเลือก “ดูฉบับที่ …” เพื่อดูเนื้อหา ยอดคำนวณ กติกาที่ตรึงไว้ และผลแต่ละขั้นของฉบับนั้น เลื่อนหน้ารายการฉบับได้ หน้านี้อ่านอย่างเดียว ใช้ “กลับฉบับปัจจุบัน” ก่อนดำเนินการ ทุกครั้งยังตรวจสิทธิ์อ่านปัจจุบัน เวลาแสดงเขตเอเชีย/กรุงเทพฯ
- API อ่านฉบับ: `GET /api/v1/field-advances/requests/{id}/revisions?page=1&pageSize=20` และ `GET /api/v1/field-advances/requests/{id}/revisions/{revisionId}`; pageSize 1–100 ไม่เปิดฉบับของคำขออื่น ไม่ใช้สิทธิ์ในอดีตแทนสิทธิ์ปัจจุบัน

## 3. รับมือ Held และการเปลี่ยนผู้รับงาน

Held คือพัก **สายอนุมัติ 7B** เมื่อไม่มีผู้เข้าเงื่อนไข สายงานวนซ้ำ ตัวบุคคลตรวจไม่ได้ หรือบทบาทกำกวม ไม่ใช่ระงับ/ปลดระงับจ่าย 7C ไม่มีปุ่ม admin override ให้ข้ามสิทธิ์ และไม่แก้ status/assignee โดยตรงในฐานข้อมูล

1. ผู้มีสิทธิ์อ่านตรวจเหตุผลพัก ขั้นที่ค้าง ฉบับ กติกาที่ตรึง และประวัติการเปลี่ยนผู้รับงาน โดยไม่เผยยอดแก่ผู้ไม่มีสิทธิ์
2. ผู้มีอำนาจแก้สายงาน/บทบาทหรือเสนอและอนุมัติสิทธิ์ใหม่ผ่านกระบวนการเดิม ตรวจวงเงิน ระดับ วันหมดอายุ ความกำกวม และข้อห้ามของคำขอ ไม่เพิ่มสิทธิ์อัตโนมัติ
3. ให้ routing worker ประเมินใหม่ (ค่าเริ่มต้นทุก 30 วินาที ครั้งละ 50 คำขอ; backlog อาจทำให้รอนานกว่าหนึ่งรอบ) เมื่อพบคนที่เหมาะสมต้องกลับ `PendingApproval` ที่ **ขั้นเดิม** ไม่มีผลอนุมัติใหม่อัตโนมัติ ผลขั้นก่อนและกติกาเดิมต้องไม่เปลี่ยน
4. โหลดหน้าใหม่ ตรวจผู้รับงานและ history ของระบบ (`actor=null`) ผู้รับงานเดิมที่ยังมี grant แต่ route เปลี่ยนต้องไม่อ่านผ่านสิทธิ์ผู้อนุมัติเดิมระหว่างรอ worker ส่วนผู้รับงานใหม่ยังไม่อ่านด้วยบทบาทนี้จน assignment ถูกบันทึก สิทธิ์ owner/delegate/report ที่เป็นอิสระยังตรวจตามสิทธิ์นั้น
5. ถ้ายังค้าง ให้ตรวจสถานะ worker, backlog, สิทธิ์/สายงาน และ log ที่ได้รับอนุญาต ไม่แก้ผลอนุมัติหรือปลดข้อห้ามเพื่อให้ผ่าน เก็บ request/revision/step ID, เวลาและ correlation ID ที่ sanitize สำหรับผู้ดูแล ไม่เก็บ cookie/token/รหัสผ่าน

T7-M1 ยังติดตาม: log ของ worker ขณะ DB ล้มเหลวยังขาดบริบท SQLSTATE/request ID ที่เพียงพอ จึงห้ามตีความ log สั้นว่าเป็นหลักฐานว่าการประเมินสำเร็จ

## 4. ไม่ทราบผลคำสั่ง เครือข่ายขาด และสิทธิ์เปลี่ยน

เมื่อเครือข่ายขาดหลังส่งหรือได้ 5xx อาจบันทึกแล้วหรือ rollback แล้ว ห้ามสรุปว่าสำเร็จ/ล้มเหลวจากหน้าที่ค้าง และห้ามสร้าง `commandId` ใหม่อัตโนมัติ

1. เก็บรหัสคำสั่งและ payload เดิมในหน้าปัจจุบัน รวม expectedVersion, request/step, hash ยืนยัน และเหตุผล ปุ่ม “ตรวจผลด้วยคำสั่งเดิม” ส่ง operation เดิมด้วยข้อมูลเดิม ระบบไม่มี endpoint ตรวจ receipt แยกให้ใช้แทนโดยสมมติเอง
2. คำสั่งเดิมเนื้อหาเดิมไม่สร้างผลซ้ำ รหัสเดิมเนื้อหาต่างได้ 409 ผล receipt เป็นหลักฐานย้อนหลัง ต้องโหลด details/screen/history ปัจจุบันก่อนแสดงผลล่าสุด ไม่เอา receipt เก่าทับฉบับปัจจุบัน
3. ถ้าหน้าแจ้งว่าบันทึกแล้วแต่โหลดข้อมูลประกอบไม่ได้ ให้ตรวจต่อด้วยคำสั่งเดิม ห้ามเริ่มคำขอใหม่เพราะ projection ล้มเหลว
4. 409 ให้โหลดล่าสุดแล้วทบทวน ผู้ใช้ตัดสินใจก่อนคำสั่งใหม่ 401/403 ให้ล้างข้อมูลที่ป้องกันและตรวจ session/MFA/บัญชี/สิทธิ์ การ retry ไม่คืนสิทธิ์ที่ถูกถอน
5. หากเปลี่ยนบัญชี ผลที่กำลังกลับมาต้องถูกทิ้ง ห้ามส่ง payload ที่ผูกบัญชีเดิมจากบัญชีใหม่ หากคำสั่งเดิมสูญหาย ให้ผู้มีอำนาจตรวจประวัติและหลักฐานโดยไม่เดาหรือสร้างคำสั่งทดแทนทันที

## 5. Migration 7A → 7B และแผนกู้คืน

การทดสอบใช้ PostgreSQL disposable container เท่านั้น ไม่ได้ทดสอบหรือเปลี่ยนฐานผู้ใช้จริง ผู้ดูแลต้องตรวจรายงาน final gates และกำหนด maintenance window/หยุดเขียนตามกระบวนการบริษัทก่อน production migration

ฐาน 7A คือ `20261020233422_AddFieldAdvancePolicyLifecycle`; ส่วนเพิ่ม 7B คือ `20261022124725_AddFieldAdvanceRequests` และ `20261022161554_AddFieldAdvanceApprovalLevels`

1. สำรองฐานด้วยเครื่องมือที่องค์กรอนุมัติ (เช่น pg_dump แบบ custom) พร้อม release/config ที่จำเป็น เก็บ secrets ในระบบจัดการความลับและจำกัดสิทธิ์ archive ไม่ใส่ connection string/credentials ใน argument, เอกสาร หรือ log
2. Restore สำเนาลงฐานแยก ตรวจ schema migration history, จำนวนและค่าเดิมของข้อมูลบัญชี/องค์กร/กติกา/grant/review/assignment/receipt/audit และทดสอบเข้าใช้ตามสิทธิ์ก่อน migration สำเนา
3. สร้าง SQL จาก release ที่จะใช้ ตรวจ diff และ hash ของไฟล์ คำสั่งต่อไปนี้สร้างไฟล์เท่านั้น ไม่ใช่คำสั่งนำไปใช้กับ production; `Development` ใช้สำหรับ design-time generation ตาม fixture ไม่ใช่คำแนะนำตั้ง environment ของระบบจริง:

   ```sh
   ASPNETCORE_ENVIRONMENT=Development dotnet ef migrations script --idempotent --project backend/src/TPR10.Api --output /approved/output/module-7b-idempotent.sql
   ```

4. ทดลอง upgrade สำเนา ตรวจข้อมูลเดิมไม่เปลี่ยน request tables ใหม่ว่างก่อนเริ่มงาน และ grant เดิมไม่ถูกเติม approval levels อัตโนมัติ ทดสอบ SQL ซ้ำกับสำเนาโดยต้องไม่สร้างผลซ้ำหรือเปลี่ยนข้อมูลเดิม
5. หลังตรวจรับจึงดำเนินการตามแผน production ที่ได้รับอนุมัติ ตรวจ migration history, health และสิทธิ์อีกครั้งก่อนเปิดเขียน หาก migration ล้มเหลวให้ตรวจ transaction/history จริงก่อน retry
6. การย้อน release ต้องอาศัย backup/restore ที่ซ้อมไว้และประเมินข้อมูลที่เกิดหลัง backup พร้อมแผนเก็บ/กระทบยอดและอนุมัติ recovery point **ไม่ใช้ destructive migration Down, drop ตารางคำขอ หรือลบประวัติเพื่อให้ downgrade ผ่าน** ห้ามเปิดโปรแกรมเก่าที่ไม่รองรับ schema บนฐานที่เปลี่ยนแล้วโดยไม่มีแผนตรวจสอบ

เทสต์ส่งมอบซ้อม backup/restore จากข้อมูล 7A สังเคราะห์ เปรียบเทียบทุกคอลัมน์เดิมของทุกตารางเดิม จำลอง DDL ล้มเหลวระหว่าง migration เพื่อตรวจ rollback แล้ว upgrade และ replay idempotent SQL ข้อพิสูจน์นี้ไม่แทนการซ้อมกู้คืนข้อมูลจริงขององค์กร

## 6. ข้อจำกัดและเกณฑ์ก่อนส่งต่อ

- M2 ยังติดตาม: ตัวเลข query/latency ของ HTTP path ใหม่เป็นการวัดใน disposable fixture ไม่มี concurrent production load ไม่ใช่ SLA และไม่ปิดประสิทธิภาพ scope/history เดิม ต้องวัดหลายโครงการและ lock-wait ตามภาระจริงก่อน rollout
