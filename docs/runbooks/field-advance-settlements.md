# คู่มือเคลียร์ค่าใช้จ่าย คืนเงิน และสะสางคำขอเงินทดรอง

ใช้กับ Module 7D และสิทธิ์ปัจจุบันของแต่ละโครงการ คู่มือนี้ไม่อนุญาต deploy, ย้ายฐานจริง, โอนเงินจริง หรือเปลี่ยนนโยบายธุรกิจ ผลทดสอบเป็นฐานจำลองและโฟลเดอร์ในเครื่องเท่านั้น มือถือจริงและ NAS จริงยังพักไว้

## ก่อนเริ่มใช้งาน

ตรวจว่าคำขอ ฉบับอนุมัติ วงเงิน และผู้รับผิดชอบเงินถูกต้อง ใช้เงินบาท จำนวนไม่เกิน 4 ตำแหน่ง อัตรา/ยอดเหมารวมไม่เกิน 2 ตำแหน่ง ปัดแต่ละรายการเป็นสตางค์แล้วรวม ห้ามแก้ยอดจ่ายเก่าเพื่อให้ยอดคงค้างดูตรง

ผู้รับผิดชอบเงินกับผู้ยื่นแทนต้องไม่อนุมัติ/ตรวจ/จ่ายของตนเอง คนเดียวหลายบัญชียังคงเป็นคนเดียว ผู้อนุมัติ ผู้ตรวจการเงิน และผู้จ่ายต้องคงการแยกหน้าที่ทั้งชุดคำขอ สิทธิ์ admin หรือสมาชิกโครงการไม่สร้างสิทธิ์การเงิน หากไม่มีผู้มีสิทธิ์เข้าเงื่อนไขให้พักรายการและใช้กระบวนการสิทธิ์เดิม ห้ามสร้าง grant ด้วย SQL

ตั้งค่าปลายทาง/ผู้รับเงินของบริษัทตามที่ได้รับอนุมัติก่อนใช้งานจริง หากยังไม่มีข้อยุติให้พัก ไม่สมมติบัญชีหรือผู้รับ ระยะเวลาแก้ไขต้องมาจากกติกาที่ผ่านอนุมัติ หากกติกาเดิมไม่มีค่า ให้แสดงว่ากติกาไม่พร้อม ไม่เติมวันเริ่มต้นเอง

## รอบค่าใช้จ่ายและรายการรอตรวจ

1. เจ้าของหรือผู้ยื่นแทนเตรียมร่างในคำขอที่ถูกต้อง แนบรูป/PDF และข้อมูลผู้ออก เลขที่หรือระบุไม่มีเลข วันที่ และยอดเอกสาร
2. ผู้รับผิดชอบเงินยืนยันเนื้อหาฉบับนั้น จากนั้นผ่านหัวหน้า → ผู้จัดการโครงการ → ผู้ตรวจการเงิน คนละคนและสิทธิ์ปัจจุบัน
3. ส่งกลับทั้งรอบพร้อมเหตุผล แก้เป็นฉบับใหม่ ให้เจ้าของยืนยันและเดินสายอนุมัติใหม่ทั้งหมด รอบก่อนที่รับรองแล้วคงเดิม
4. เอกสารที่รับรอง รอตรวจ และส่งกลับแต่ยังกันยอด รวมกันห้ามเกินยอดใบ ลดรายการคืนเฉพาะส่วนต่าง การแก้ลดค่าใช้จ่ายที่รับรองแล้วไม่คืนยอดใบก่อนผลแก้ผ่าน

ห้ามใช้ใบเสร็จข้ามคำขอ รวมคำขอส่วนเพิ่ม หากสงสัยซ้ำให้พักส่ง ผู้ตรวจต้องมีสิทธิ์ทั้งสองโครงการและไม่ติดข้อห้ามทั้งสองคำขอ การยืนยันคนละเอกสารต้องมีเหตุผลและผูกกับเวอร์ชันปัจจุบัน ผู้ยื่นปลดเองไม่ได้ และห้ามเปิดข้อมูลอีกคำขอแก่ผู้ไม่มีสิทธิ์

ใบเดียวเกินวงเงินให้พักส่วนเกินส่งการเงินพิจารณาภายนอก ไม่แบ่งใบไปส่วนเพิ่ม ไม่ถือว่ารับรองแล้ว และไม่ผลักภาระให้พนักงานเอง หมายเหตุอย่างเดียวไม่สะสางข้อค้างหรือสร้างเงินจ่าย

## จบงานและกำหนดเวลา

ผู้จัดการโครงการยืนยันวันจบงานจริง ผู้รับผิดชอบเงินยืนยันส่งครบ นับวันปฏิทินใน Asia/Bangkok โดยวันถัดจากจบงานเป็นวันที่ 1 วันคืนเงินตรงกับวันครบกำหนดเคลียร์

แยก “ส่งครบแล้วรอตรวจ” จาก “รับรองครบแล้ว” ใช้เวลาส่งที่ระบบบันทึก ไม่ใช้วันที่ผู้กรอกย้อนหลังเพียงอย่างเดียว การแก้วันจบงานต้องเสนอพร้อมเหตุผลและมีผู้ตรวจอีกคนยืนยัน เก็บกำหนดเดิม/ใหม่และประวัติเดิมเสมอ การส่งกลับใช้กติกาเวอร์ชันที่มีผลตอนนั้น ไม่เลื่อนเส้นตายเก่าเมื่อแก้กติกาใหม่

ก่อนปิด ถอนการยืนยันส่งครบได้พร้อมเหตุผล แล้วต้องยืนยันใหม่ หลังปิดห้ามเปิดคำขอเดิมเพื่อเพิ่มค่าใช้จ่าย

## คืนเงินและแก้เงินคืน

ยื่นคืนได้หลายครั้ง แต่เงินคืนรอตรวจยังไม่ลดหนี้ที่รับรองแล้ว และต้องกันความสามารถยื่นซ้ำไม่ให้ยอดยืนยันรวมยอดเสนอเกินยอดคืนได้ แนบหลักฐานของคำขอนั้นและช่องทาง/ผู้รับบริษัทให้ครบ เจ้าของยืนยัน แล้วผู้ตรวจการเงินตรวจรับ ไม่ถือว่าสลิปเท่ากับรับคืนสำเร็จ

ก่อนรับรอง ผู้ตรวจส่งกลับพร้อมเหตุผลได้ หลังรับรองต้องสร้างคำร้องแก้ไขพร้อมหลักฐานและผู้ตรวจอีกคน เก็บยอดก่อน–หลัง อ้างอิงเวอร์ชันล่าสุด และลงผลต่างครั้งเดียว ไม่แก้แถวเดิม ไม่ใช้เงินคืนชุดเดียวทั้งช่องเงินเหลือและช่องเหตุจ่ายผิด

เมื่อคำสั่งไม่ทราบผล ให้เก็บ command ID และเนื้อหาเดิม ตรวจผลคำสั่งค้าง/receipt ก่อนส่งใหม่ ห้ามสร้าง command ID ใหม่โดยเดาว่าคำสั่งแรกไม่สำเร็จ ผลตอบกลับ 403 หลัง commit อาจหมายถึงสิทธิ์ถูกถอน ไม่ได้แปลว่าธุรกรรมถูกยกเลิก ให้ผู้มีสิทธิ์ตรวจประวัติตาม workflow ไม่ส่งซ้ำเพื่อทดลอง

## เหตุจ่ายผิดและส่วนขาด

คงรายการ Paid เดิมเป็นประวัติ แยกข้อเท็จจริงเงินจริงถึงเจ้าของ เงินถึงบุคคลอื่น และเงินเรียกคืนที่ตรวจแล้ว observed amount ไม่ใช่ Paid โดยอัตโนมัติ

งวด 10,000 บาท หากเจ้าของได้รับ 8,000 ภาระเริ่มที่ 8,000 ส่วนขาด 2,000 ต้องตรวจงวดใหม่; หากได้รับ 12,000 ภาระเริ่มที่ 12,000 และพักสะสางส่วนเกิน 2,000; หากไปผิดคนทั้งหมด เจ้าของไม่มีหนี้จากเงินนั้น แต่เหตุยังค้างจนเรียกคืนครบและตรวจปลด ผลต้องสอดคล้องทั้งพบก่อนและหลังบันทึก Paid

เสนอข้อเท็จจริง → ผู้ตรวจอีกคนยืนยัน → เสนอ/ตรวจรับเงินเรียกคืน → ตรวจปลดเหตุเฉพาะเหตุ → เตรียมและตรวจงวดส่วนขาด เป็นคนละการกระทำ คืนผิดคนไม่ครบยังปิดไม่ได้ ปลดเหตุหนึ่งไม่ล้างเหตุอื่น การรับคืนไม่เปิดวงเงินหรือจ่ายใหม่อัตโนมัติ

## ปิดคำขอและเคสหลังปิด

ระบบปิดเมื่อมีวันจบงานและยืนยันส่งครบ ยอดคงค้างเป็นศูนย์ ไม่มีร่าง/รอตรวจ/แก้ไข/งวด/วงเงินกัน/ผลจ่ายไม่ชัดเจน/เหตุระงับค้าง ค่าใช้จ่ายไม่เกินวงเงิน และยอดไม่ได้ใช้ยุติตามขั้นตอน 7C แล้ว ระบบต้องตรวจปัจจุบันภายใต้ transaction/lock ไม่ใช่เจ้าหน้าที่บังคับปิด

คำขอหลักปิดได้ตามเงื่อนไขตน ส่วนเพิ่มที่สร้างและ commit ก่อนหลักปิดยังเดินต่อรวมส่งแก้ได้ แต่ห้ามสร้างส่วนเพิ่มใหม่หลังหลักปิด ภาพรวมทั้งชุดรวมเฉพาะคำขอที่ผู้ดูมีสิทธิ์ และแสดงความครบถ้วนตามสิทธิ์ ห้ามอนุมานยอดที่ซ่อน

แก้ยอดคืนหลังปิดด้วยเคสแยก อ้าง ClosureRecord เดิม State คง Closed ภาพรวมแสดงรายการปรับปรุงจนสะสางครบ เช่นเคยคืน 2,000 แต่จริง 1,500 ต้องติดตามรับเพิ่ม 500 ผ่านเคส หากบริษัทต้องคืนเงินให้เจ้าของ ให้บันทึกผลจ่ายภายนอกพร้อมหลักฐานและผู้ตรวจแยกหน้าที่ ไม่เปิดวงเงินเดิมอัตโนมัติ การแก้ค่าใช้จ่ายหลังปิดยังต้องผ่านสายอนุมัติครบ

## เมื่อเกิดข้อผิดพลาด

- 409 หรือ version เปลี่ยน: โหลดสถานะใหม่ ตรวจผลคำสั่งเดิมก่อนตัดสินใจ ห้าม retry แบบไม่ดูผล
- 401/403 หรือสิทธิ์หมดอายุ: หยุดเปิดเผยข้อมูล ใช้ผู้มีสิทธิ์ปัจจุบันและไม่ติดข้อห้าม ห้ามข้าม MFA/session/TLS
- ไฟล์อ่านไม่ได้หรือ digest ไม่ตรง: พักรายการ คงไฟล์/metadata/ประวัติเดิม ตรวจที่เก็บที่กำหนดผ่าน workflow; ห้ามเปลี่ยน hash ให้ตรงไฟล์เสีย
- COMMIT ล้ม: ตรวจ receipt/สถานะจากฐานปัจจุบัน ใช้คำสั่งเดิมได้เมื่อยืนยันว่าไม่เกิดผลแล้วตาม workflow การคืนจาก backup ไม่ล้างสิทธิ์ที่ถอน
- ปิดไม่สำเร็จ: ตรวจรายการค้างและเหตุระงับทุกชนิด การไม่มีรายการในคิวของผู้ใช้หนึ่งคนไม่ได้พิสูจน์ว่าไม่มีข้อค้างทั้งระบบ

ห้าม DELETE, TRUNCATE, เปลี่ยนสถานะ, ลบประวัติ, ปลด hold หรือเพิ่ม grant ด้วย SQL นอก workflow เพื่อให้ผ่านเงื่อนไข ห้าม downgrade โดยลบข้อมูลที่ guard ป้องกัน ถ้าขาดข้อเท็จจริง/นโยบายให้ขอเจ้าของธุรกิจตัดสินใจและคงรายการไว้

## ซ้อมย้ายและกู้คืนในฐานจำลอง

ใช้ `FieldAdvanceSettlementDeliveryTests` กับ Docker/Testcontainers PostgreSQL ที่สร้างสำหรับเทสต์เท่านั้น ชุดนี้ซ้อม pg_dump/pg_restore ไปฐานใหม่ ตรวจ pending refund + Closed + adjustment case + revoked grant แล้วตรวจว่า replay ไม่มีสิทธิ์และข้อมูลเงิน/receipt ไม่เปลี่ยน

การย้ายไฟล์ใช้ `FinanceEvidenceMigration.CopyAndSwitchAsync` ไปโฟลเดอร์ local ที่ตั้งค่าไว้ ตรวจ digest/length ก่อนเปลี่ยนตำแหน่ง current คงประวัติตำแหน่งและการอ้างอิงเงินเดิม ซ้อมไฟล์ปลายทางเสียแล้วต้องไม่ส่ง bytes การทดสอบนี้ไม่รับรอง NAS, ACL ข้ามเครื่อง, RPO/RTO หรือการกู้คืนระบบจริง

ซ้อมอัปเกรดจากสำเนา 7C: migrate สองครั้ง แล้ว idempotent SQL สองครั้ง ต้องไม่สร้างเงิน/grant/วันแก้ไขที่ไม่เคยอนุมัติ การซ้อม Down ของ Task4 ต้องอยู่บน schema ประวัติ Task4; มีหลายคู่ต่อ command แล้วต้องล้มและคงข้อมูล/index/migration history ไม่บังคับให้ downgrade ผ่าน

เก็บผลคำสั่ง เวลา UTC exit code source SHA-256 และ log ที่ sanitize ก่อนล้าง `/tmp` ไม่เก็บ secrets, cookies, tokens หรือข้อมูลเงินจริง รายงานรับมอบและข้อจำกัดอยู่ที่ [ผลตรวจ Module 7D](../reports/2026-10-31-module-7d-verification.md)

## ข้อควรทราบจากการตรวจส่งมอบ Task18

- เอกสารค่าใช้จ่ายต้องเลือกชนิดหลักฐานทางธุรกิจให้ตรงหมวด ไม่ใช้ชนิดไฟล์แทน เอกสารเดิมที่ไม่มีชนิดให้เปิดแก้ไขและเลือกชนิดก่อนส่งรอบ โดยเก็บหลักฐานเดิมไว้
- เมื่อรับรองข้อเสนอแก้วันจบงาน ข้อเสนอค้างที่ใช้ฐานเดียวกันจะถูกยุติเป็น Cancelled พร้อมประวัติและ version ใหม่ โดยไม่นำวันที่ของข้อเสนอที่ยุติมาใช้ ข้อเสนอเก่าที่หมดฐานก่อนปรับระบบให้ผู้ตรวจที่มีสิทธิ์ยุติผ่านคำสั่งตรวจเดิม ไม่ลบข้อมูล
- ผู้ตรวจการเงินที่มีสิทธิ์สามารถอัปโหลดหลักฐานใหม่เพื่อแก้รายการคืนที่รับรองแล้วได้ทั้ง Approved และ Closed ตามเงื่อนไขต้นทาง ไม่ต้องเพิ่มสิทธิ์ผู้บันทึกจ่าย
- เมื่อกู้ receipt ของการบันทึกเอกสารสำเร็จ ฟอร์มจะล้างข้อมูล หากต้องการแก้ต่อ ให้เปิดเอกสารปัจจุบันใหม่เพื่อใช้ version ล่าสุด คำสั่งที่ผลยังไม่ทราบต้องคง pending ไว้จนตรวจผลได้
