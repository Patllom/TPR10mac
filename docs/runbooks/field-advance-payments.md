# คู่มือปฏิบัติและส่งมอบการจ่ายเงินทดรอง Module 7C

วันที่ 31 ตุลาคม 2569 อ้างอิงแบบที่อนุมัติ 24 ตุลาคม 2569 และโค้ดฐาน `2711025c38413d53b998de03f9bacbeb7c30da68` เอกสารนี้ไม่ใช่การอนุมัติเปิดใช้เงินจริงหรือ deploy ผลตรวจรับแยกไว้ใน [รายงานตรวจสอบ](../reports/2026-10-24-module-7c-verification.md)

## 1. ขอบเขตและผู้รับผิดชอบ

**ตรวจผ่านยังไม่จ่าย** การกันวงเงินและผลตรวจการเงินไม่ได้สั่งธนาคารโอนเงิน เจ้าหน้าที่โอนหรือจ่ายเงินสดภายนอกระบบให้ผู้รับผิดชอบเงินเท่านั้น ผู้ยื่นแทนไม่เป็นผู้รับเงินแทน

ผู้เตรียม/บันทึกจ่ายต้องมี `payment.record` ผู้ตรวจต้องมี `finance.check` ในโครงการปัจจุบัน ผู้รับผิดชอบและผู้ยื่นแทนห้ามอนุมัติ ตรวจ หรือจ่ายในชุดเดียวกัน ผู้เคยอนุมัติ ผู้เคยตรวจ และผู้เคยจ่ายห้ามสลับสามหน้าที่ข้ามฉบับ งวด ส่วนเพิ่ม หรือบัญชีของบุคคลเดิม การถอนแล้วให้สิทธิ์ใหม่ไม่ล้างประวัติ admin และสมาชิกทีมไม่มีสิทธิ์การเงินอัตโนมัติ

ผู้จัดการระบบรับผิดชอบสำรองฐาน/ไฟล์ ตั้งค่า root และตัวตรวจเอกสาร การมีสิทธิ์ filesystem หรือ Docker ไม่ใช่สิทธิ์อ่านหลักฐานผ่านแอป และไม่อนุญาตให้แก้แถวการเงินหรือให้ grant แทนกระบวนการตรวจสิทธิ์

## 2. จัดงวด ตรวจ และเริ่มก่อนเงินจริง

1. ตรวจคำขอที่อนุมัติครบ โครงการ ผู้รับผิดชอบเงิน วงเงินของคำขอนั้น และเหตุระงับล่าสุด แยกวงเงินอนุมัติ ยอดกันไว้ ยอดจ่าย และยอดพร้อมจัดงวด
2. สร้างงวดและส่งตรวจ การส่งตรวจกันวงเงินครั้งเดียว หลายงวดต้องไม่เกินวงเงิน ส่งกลับยังคงยอดกันไว้ ลดงวดคืนเฉพาะส่วนต่าง เพิ่มงวดต้องมีวงเงินพอ
3. ผู้ตรวจอีกคนทบทวนฉบับปัจจุบัน รวมยอด ช่องทาง ผู้รับ บัญชี และหลักฐาน การเปลี่ยนยอด/ช่องทาง/บัญชีแม้ลดหรือเป็นบัญชีเจ้าของเดิมต้องตรวจใหม่ ผลตรวจเก่าไม่รับรองฉบับใหม่
4. ก่อนโอนเงินจริงหรือส่งมอบเงินสด ให้กดเริ่มจ่ายและตรวจว่าระบบยืนยันการเริ่มสำเร็จพร้อมผู้จ่าย ผู้รับ ยอด ช่องทาง และปลายทางตรงฉบับที่ตรวจผ่าน หากผลคำสั่งไม่ชัดให้หยุดตรวจผลตามข้อ 3 ห้ามเดาว่าสำเร็จแล้วโอน
5. ผู้จ่ายที่ล็อกไว้ดำเนินการภายนอกเพียงครั้งเดียว เก็บวันจ่าย เลขอ้างอิง และหลักฐาน แล้วบันทึกผลตรงยอด/ผู้รับที่ตรวจผ่าน การบันทึกย้ายยอดกันไว้เป็นยอดจ่ายครั้งเดียว ไม่ลดวงเงินซ้ำ

ใช้เงินบาทและการคำนวณฐานสิบฝั่งเซิร์ฟเวอร์: จำนวนไม่เกิน 4 ตำแหน่ง อัตรา/ยอดเหมารวมไม่เกิน 2 ตำแหน่ง ปัดแต่ละบรรทัดเป็นสตางค์แบบหลักที่สามตั้งแต่ 5 ปัดขึ้น แล้วรวมตาม 7B ไม่ปัดข้อมูลนำเข้าที่เกินความละเอียดเงียบ ๆ

ยอดงวดและยอดจ่ายเป็นจำนวนบวกไม่เกิน 2 ตำแหน่ง ตรวจ overflow และขอบเขตชนิดข้อมูล ไม่มีการสร้างเพดานธุรกิจใหม่ขึ้นเอง

`ยอดจ่ายสำเร็จสะสม + ยอดกันไว้ของงวดที่ยังไม่เสร็จ <= วงเงินอนุมัติที่ใช้จ่ายได้`

ตัวอย่างคำขอหลัก 10,000 บาท จ่าย 2,000 บาท ส่วนเพิ่ม 3,000 บาทใช้ฐานอำนาจอนุมัติ 13,000 บาท แต่ส่วนเพิ่มจ่ายได้ไม่เกิน 3,000 บาทเมื่ออนุมัติแล้ว คำขอหลักเหลือ 8,000 บาทก่อนหักยอดกันไว้ ไม่สร้างยอดหลักซ้ำ

## 3. Response หายและอ่านผลคำสั่ง

เก็บรหัสคำสั่งเดิมกับบัญชีผู้สั่ง ห้ามเปลี่ยน command ID เพื่อหนีสถานะไม่ชัด หน้าจอแสดง “กำลังตรวจสอบผล ห้ามจ่ายซ้ำ” ให้ตรวจคำสั่งเดิมผ่าน `GET /api/v1/field-advances/payment-commands/{commandId}` ด้วย session/MFA/สิทธิ์ปัจจุบันของบัญชีเดิม แล้วอ่านสถานะงวดล่าสุด ระบบคืนสถานะปัจจุบันโดยผูก receipt กับผู้สั่ง ไม่เปิดผลเก่าให้บัญชีอื่น

| ผลที่พบ | วิธีดำเนินการ |
|---|---|
| เริ่มสำเร็จ แต่ไม่แน่ใจว่าเงินจริงออกหรือไม่ | คงล็อก/ยอดกันไว้ ตรวจเอกสารภายนอกและใช้ผู้ตรวจสะสาง ห้ามโอนซ้ำ |
| จ่ายแล้ว | ตรวจยอด/ผู้รับ/หลักฐาน ห้ามเริ่มหรือบันทึกเงินจริงรอบใหม่ |
| 401/403 | หยุดเปิดข้อมูล ตรวจบัญชี session/MFA และสิทธิ์ ไม่ใช้ admin หรือบัญชีอื่น replay |
| 409 หรือข้อมูลเก่า | โหลดรุ่นล่าสุดและทบทวนเหตุระงับ ไม่เปลี่ยนรุ่น/command เพื่อบังคับผ่าน |
| ไม่พบผล หรือเครือข่าย/บริการไม่พร้อม | ไม่เท่ากับยืนยันว่าไม่ได้จ่าย รักษาหลักฐานและรอผู้มีสิทธิ์ตรวจประวัติ |

ไม่มี timeout ที่ปลดล็อกหรือคืนยอดกันไว้เอง การ rollback ฐานข้อมูลไม่ย้อนการโอนภายนอก หากไฟล์หายหรือระบบบันทึกไม่ได้หลังเงินจริงออก ให้พักบันทึกเพื่อสะสาง ไม่กลับไปจ่ายอีก

## 4. สะสาง รับช่วง และจ่ายผิด

ผู้จ่ายเสนอผลพร้อมหลักฐานให้ผู้ตรวจต่างคนที่ยังมีสิทธิ์ยืนยัน: จ่ายตรงงวดให้บันทึกครั้งเดียว; ยืนยันไม่ได้จ่ายจริงให้กลับไปตรวจงวดใหม่โดยคงยอดกันไว้; ยังไม่ชัดให้คงพัก ห้าม retry โอนเพื่อทดสอบ

หากผู้จ่ายเดิมหมดสิทธิ์ ผู้จ่ายคนใหม่ที่มีสิทธิ์อยู่แล้วเสนอรับช่วงและผู้ตรวจอีกคนยืนยัน การรับช่วงให้สิทธิ์เสนอผลสะสางคนเดียวในปัจจุบัน ไม่เปลี่ยนผู้จ่ายเดิมในประวัติ ไม่เพิ่ม grant ไม่คืนวงเงิน และไม่อนุญาตจ่ายใหม่เอง ไม่มีผู้เข้าเงื่อนไขให้คงพัก

จ่ายผิดยอด/ผิดคนให้บันทึกเหตุผิดปกติพร้อมยอดและผู้รับที่พบจริง ระบบระงับเริ่มจ่ายทั้งชุดหลักและส่วนเพิ่ม งวดที่เริ่มแล้วต้องสะสางต่อ คงผลจ่ายและหลักฐานเดิมถ้าบันทึกแล้ว หรือคงยอดกันไว้ถ้ายังไม่บันทึก **7C ไม่มีคำสั่งปลด PaymentMismatch หรือแก้เงินจริง ให้คงพักรอ 7D** การแก้ metadata รับช่วง ยุติยอด หรืออนุมัติส่วนเพิ่มไม่ล้างเหตุนี้

ยกเลิกงวดต้องให้ผู้จ่ายเสนอและผู้ตรวจยืนยันว่าไม่จ่ายจริง จึงคืนยอดกันไว้ครั้งเดียว งวดเริ่มแล้ว/ไม่ทราบผลต้องสะสางก่อน แก้วันจ่าย เลขอ้างอิง หรือหลักฐานหลังจ่ายให้เสนอ–ตรวจต่างคน เก็บก่อน–หลัง ไม่เปลี่ยนยอด/ผู้รับและไม่เปิดจ่ายซ้ำ

## 5. ปรับวงเงิน ส่วนเพิ่ม และยุติยอด

ก่อนจ่ายจริง เริ่มปรับวงเงินต้องระงับเริ่มจ่ายก่อนสร้างฉบับใหม่ ผู้รับผิดชอบยืนยันและอนุมัติใหม่ครบ ต้องยืนยันยกเลิกงวดเดิมและคืนยอดกันไว้ครบด้วยจึงใช้วงเงินใหม่ได้ ถอน/ปฏิเสธยังคงพัก ไม่กลับมาจ่ายเอง ผลไม่ชัดบล็อกการปรับเดิม

หลังจ่ายจริงแม้บางส่วน ใช้คำขอส่วนเพิ่มเฉพาะส่วนต่าง โครงการและเจ้าของเดิม ส่งค้างได้หนึ่งรายการต่อชุด รวมส่งกลับ/พัก คำขอหลักยังจ่ายวงเงินเดิมได้ถ้าไม่มีเหตุระงับอื่น ไม่ใช้วงเงินส่วนเพิ่มก่อนอนุมัติ ฐานอำนาจนับวงเงินหลักและส่วนเพิ่มที่อนุมัติแล้วครั้งเดียวต่อคำขอ ไม่บวกทุกฉบับซ้ำ ผู้อนุมัติส่วนเพิ่มเห็นเฉพาะข้อมูลฐานที่อนุญาต ลิงก์ต้นทางตรวจสิทธิ์แยก

ยุติยอดที่เหลือ: ผู้ตรวจการเงินเสนอ ผู้ดำรงบทบาทอนุมัติขั้นสุดท้ายปัจจุบันที่มีอำนาจครบยืนยันต่างคน รอสะสางผลค้างและยืนยันยกเลิกงวดก่อนทำให้มีผล คงยอดจ่ายจริงและวงเงินอนุมัติเดิมสำหรับฐานสะสม ไม่ปิดคำขอทางการเงิน การเคลียร์ คืนเงิน และปิดคำขอเป็น 7D

## 6. หลักฐาน private และการย้ายที่เก็บ

ใช้ [คู่มือหลักฐานการเงิน](module-7c-finance-evidence.md) ประกอบ รองรับ JPEG/PNG/PDF ที่ตรวจเนื้อหาจริง ค่าเริ่มต้น `MaxFileBytes=10485760`, `MaxFiles=10`, `MaxTotalBytes=52428800`, `MaxImagePixels=25000000` ห้ามปิดตัวตรวจเพื่อรับไฟล์ PDF ต้องใช้ image ID ที่ตรวจแล้วใน process แยกตามคู่มือ ไม่มี fallback parse ใน API

`FinanceEvidence:Roots` จับคู่ GUID กับ absolute root ส่วนตัวที่ไม่ผ่าน symlink และไม่อยู่ใต้ public/static; `ActiveStorageId` ใช้สำหรับไฟล์ใหม่เท่านั้น ค่าเริ่มต้นใน repository ยังไม่พร้อมใช้จริง จำกัดสิทธิ์ OS ให้บัญชีบริการและผู้ดูแล root ที่ได้รับมอบหมาย เก็บ credentials/keys/connection strings ในระบบจัดการความลับ ไม่ใส่ใน git/log/ภาพหน้าจอ

การย้ายใช้บริการผู้ปฏิบัติ `FinanceEvidenceMigration.CopyAndSwitchAsync` ซึ่งยังไม่มี HTTP endpoint สำหรับผู้ดูแล: copy → ตรวจ length/SHA-256 → สลับ current location ในธุรกรรมโดยตรวจตำแหน่งเก่าอีกครั้ง คง ID หลักฐานและไฟล์/แถวตำแหน่งเดิมไว้ ไม่แก้ location SQL ด้วยมือ หาก digest/ไฟล์/commit ผิดให้คงต้นทาง การดาวน์โหลดชนการสลับอาจคืน 409 โดยไม่ส่ง bytes เก่า ให้โหลดใหม่ตามสิทธิ์ ไม่กระทบสถานะเงิน

`FinanceEvidenceReconciler.FindOrphansAsync` รายงานเท่านั้น ไม่ลบไฟล์อัตโนมัติ แถวตำแหน่งย้อนหลังและไฟล์ staged ยังถือเป็น reference ห้ามกวาดไฟล์เพียงเพราะไม่ใช่ current หรือยังไม่มีผลจ่าย

## 7. สำรอง ย้าย schema และกู้คืนไปข้างหน้า

Task15 ใช้ PostgreSQL disposable clone และไฟล์ทดสอบเท่านั้น ขั้นต่อไปสำหรับระบบจริงต้องอยู่ในแผนปฏิบัติที่องค์กรอนุมัติ ไม่ถือว่าได้รับอนุญาตจากรายงานนี้

1. กำหนดช่วงหยุดเขียนการเงิน/อัปโหลด/ย้ายไฟล์ เก็บรายการงวดกำลังจ่ายภายนอกเพื่อกระทบยอดหลัง restore อย่าสมมติว่าหยุดแอปแล้วเงินจริงหยุดด้วย
2. สำรอง PostgreSQL แบบ consistent พร้อม **ทุก storage GUID/root ทั้ง current และ historical** เก็บ manifest ID/locator/length/SHA-256, migration history, release/config และกุญแจที่จำเป็นในที่ควบคุมแยกกัน จำกัดสิทธิ์ archive ห้ามสำรองเฉพาะ DB หรือเฉพาะไฟล์
3. Restore ลงสำเนาแยกก่อน ตรวจสิทธิ์ที่ถอนแล้ว session/บัญชี ประวัติบทบาท receipt/audit ผลจ่าย ยอดกันไว้ หลักฐานและ digest รวมไฟล์เก่า ไม่เชื่อสถานะ backup ว่าสำเร็จโดยไม่ซ้อมอ่าน
4. ตรวจฐาน 7B และ migration ที่มีอยู่จริง เพิ่ม `20261024075718_AddFieldAdvancePayments` พร้อม migrations ต่อมาของ release ที่ตรวจรับ สร้างและทบทวน idempotent SQL จาก release โดยเครื่องมือเดิมของโครงการ ทดลองเฉพาะ clone ก่อน บันทึก hash/เวลา/exit/history และทดสอบ apply ซ้ำ
5. ตรวจ SourceRequestId เดิมยังเป็นการคัดลอกคนละ family ไม่กลายเป็น supplement ตรวจยอดอนุมัติเดิมเพียงครั้งเดียว ไม่มีการ seed ผลจ่าย ยอดกันไว้ หรือ grant เอง การทดสอบ Task15 ใช้ EF MigrateAsync ซ้ำและ generated idempotent SQL จากฐาน 7B ซ้ำสองครั้ง; ไม่อ้างว่าเทียบทุกคอลัมน์ 7B ในงานนี้
6. เมื่อผิดพลาด หยุดเขียนและเก็บหลักฐาน ตรวจ transaction/history ที่ commit จริง เลือกแก้ไปข้างหน้าหรือ restore ตาม recovery point ที่อนุมัติ ห้าม Down migration ลบหลักฐานบนฐานจริง ห้ามนำฐานก่อนโอนมาใช้แล้วสรุปว่าโอนไม่เกิด ต้องกระทบยอดเงินจริงภายนอกกับ receipt/attempt/result หลัง backup ก่อนเปิดใช้งาน
7. ก่อนเปิดเขียน ตรวจยอด `Paid + Reserved <= Spendable`, ผลที่ไม่ชัดยังล็อก, mismatch ยังพัก, download ตรวจสิทธิ์/digest และ no-store ตาม API พร้อมผู้รับผิดชอบอนุมัติกู้คืน

## 8. รายการคงค้าง

คง M2-R1, R2-C1, HTTPS504, Minor log, OpenAPI500, T13-M1 และ T14-M1 เปิดติดตาม ไม่อ้างปิดจากเทสต์ Task15 รหัสสถานะภาษาอังกฤษบางส่วนยังเป็น Minor ที่พักไว้ มือถือจริง/NAS จริงพักตามผู้ใช้ local folders และ viewport ไม่ทดแทนเครื่องจริง ผล Test/Build/Format/Lint, HTTPS matrix และผู้ตรวจอิสระผ่านตาม [รายงานตรวจรับ](../reports/2026-10-24-module-7c-verification.md) ขอบเขตผลตรวจไม่รวมการใช้งานเงินจริงหรือฮาร์ดแวร์ที่พักไว้


## 9. ตรวจ fixture HTTPS และอ่านผลตรวจรับล่าสุด

สำหรับ disposable HTTPS payment/supplement fixture ต้องตั้ง `TPR10_PAYMENT_E2E=1` อย่างชัดเจนก่อนเรียก runHttpsSmoke เพื่อให้ test-only executable สร้าง appsettings.Testing.json และ private root ภายใน container เท่านั้น ห้ามนำ flag/config นี้ไปเปิด storage ของระบบจริง หาก upload ได้503 ให้ตรวจ opt-in และ existing `--payment-storage-probe` ใน disposable API container ก่อนสรุปว่า product ผิด ห้ามลด validation หรือเปลี่ยน default production root เพื่อให้เทสต์ผ่าน

หลักฐาน Task15 ปัจจุบัน: backend ใหม่เคยผ่าน13/13 และ delivery diagnostic ล่าสุด5/5; broader focused run ถูกยกเลิก ไม่ใช่ผ่าน UI stale-alert regression มี RED→GREEN แต่ request suite รวม10ผ่าน/1timeout และ supplement รอบที่ไม่ได้ระบุ opt-in ชัดเจนได้503 Controller รับผิดชอบ corrected invocation, diagnostic request และ final gates จึงยังไม่ใช่การอนุมัติส่งมอบจริง

Request diagnostic ที่อนุมัติเก็บเฉพาะ phase/เวลา elapsed และ pathname/status ของ protected API ไม่เก็บ query/body/credentials/cookies จำกัด120 response events ต่อกรณี และเปิดด้วย `TPR10_SMOKE_DIAGNOSTICS=1` ผล diagnostic ยังไม่ออก ณ การอัปเดตนี้ ห้ามนำการเพิ่ม logging มาอ้างว่า timeout ถูกแก้ รายละเอียด command/exit/เวลา/source hash อยู่ในรายงาน Task15 และผล final ของ controller
