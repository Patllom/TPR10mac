# เอกสารออกแบบ Module 7A — กติกาและสิทธิ์เงินทดรองออกสนาม

วันที่: 19 ตุลาคม 2569 (2026-10-19)

สถานะ: ผู้ใช้อนุมัติเอกสารและแผนแล้ว เลือกแยกผู้ลงมือกับผู้ตรวจ Task 1–5 เสร็จและผ่าน Test, Build, Lint พร้อมผู้ตรวจอิสระแล้ว ณ 21 ตุลาคม 2569; ขั้นถัดไป Task 6 ยังไม่เริ่ม ยังไม่ถือว่า Module 7A ส่งมอบครบ

## สรุปสำหรับผู้ตรวจ

7A สร้างฐานกติกาและสิทธิ์ของระบบเงินทดรองออกสนาม ให้บริษัทปรับวงเงิน อัตรา ผู้มีอำนาจ และขอบเขตโครงการได้ โดยไม่แก้ประวัติย้อนหลัง ไม่ให้สิทธิ์ผู้ดูแลระบบเกินบทบาท และไม่เปิดช่องให้คนเดียวอนุมัติประโยชน์ของตนเอง

หลักสำคัญมีสี่ข้อ:

1. กติกามีฉบับ ผู้แก้ไขกับผู้อนุมัติต้องต่างคน และอนุมัติก่อนเปิดใช้
2. การมอบหมายสิทธิ์แยกผู้เสนอ ผู้อนุมัติ และผู้รับเป็นสามคนต่างกัน
3. คำขอใช้กติกาที่บันทึกไว้ แต่ผู้ดำเนินการต้องมีสิทธิ์ปัจจุบันและผ่านกติกาแยกหน้าที่เสมอ
4. ข้อมูลผิด สิทธิ์ไม่พอ หรือบันทึกไม่ครบ ต้องหยุดรายการ ไม่ลดข้อจำกัดอัตโนมัติ

เอกสารนี้ไม่ใช่ผลทดสอบหรือการรับรองพร้อมใช้งานจริง การทดสอบมือถือจริงและ NAS จริงยังพักตามคำสั่งผู้ใช้

## 1. เป้าหมาย ขอบเขต และตำแหน่งในโครงการ

### 1.1 การแบ่ง Module 7 ที่เห็นชอบ

| ส่วน | หน้าที่ |
|---|---|
| 7A | กติกา วงเงิน หมวด อัตรา หลักฐาน กำหนดเคลียร์ และสิทธิ์ |
| 7B | คำขอ การยื่นแทน การยืนยันผู้รับผิดชอบ และสายอนุมัติ |
| 7C | ตรวจงวด บันทึกจ่าย ระงับจ่าย และคำร้องปรับปรุง |
| 7D | เคลียร์ค่าใช้จ่าย ตรวจเอกสารซ้ำ คืนเงิน และปิดคำขอ |

เลือกแบ่งส่วนเพื่อทบทวนและทดสอบความถูกต้องทีละขอบเขต แทนการทำทั้งหมดครั้งเดียว หรือขยายไปพัฒนาระบบอนุมัติกลางก่อน

### 1.2 สิ่งที่รวมใน 7A

- กติกาบริษัทและกติกาเฉพาะโครงการ พร้อมฉบับและการอนุมัติ
- ช่วงวงเงิน ลำดับระดับอนุมัติ และขอบเขตอำนาจอนุมัติที่ตั้งค่าได้
- หมวดค่าใช้จ่าย หน่วย อัตรามาตรฐาน และประเภทหลักฐานที่ยอมรับ
- จำนวนวันปฏิทินสำหรับส่งเคลียร์หลังจบงาน
- การเสนอ อนุมัติ เริ่มใช้ ระงับ ถอน และตรวจประวัติการมอบหมายสิทธิ์
- หน้าจอจัดการ งานรอตรวจ เปรียบเทียบการเปลี่ยนแปลง และตัวอย่างประเมินวงเงิน
- ส่วนบริการเลือกกติกา ประเมินสิทธิ์ และเตรียมข้อมูลกติกาสำหรับ 7B–7D

### 1.3 สิ่งที่ไม่รวม

- สร้างคำขอเงินจริง จ่ายเงิน เคลียร์ คืนเงิน หรือปิดคำขอจริง
- การเบิกคืนและเงินทดรองทั่วไป รวมถึงสกุลเงินอื่นนอกจากบาท
- การโอนธนาคารอัตโนมัติ ระบบไฟล์/NAS กลางเต็มรูปแบบ หรือ Module 5 ระบบอนุมัติกลางเต็มรูปแบบ
- การทดสอบมือถือจริงและ NAS จริงที่พักไว้ ไม่ถือว่าการพักคือผ่านการทดสอบ

## 2. ส่วนที่หนึ่ง — กติกาและวงจรชีวิต

### 2.1 ค่าเริ่มต้นและข้อแตกต่างโครงการ

- บริษัทมีค่าเริ่มต้น โครงการสามารถเข้มงวดหรือผ่อนปรนกว่าได้ แต่ผู้มีสิทธิ์ระดับบริษัทต้องอนุมัติก่อนใช้
- แสดงที่มาของแต่ละค่าอย่างชัดเจนว่าใช้บริษัทหรือกำหนดเฉพาะโครงการ
- โครงการที่ไม่มีข้อแตกต่าง ใช้กติกาบริษัทที่มีผลล่าสุดเมื่อส่งคำขอใหม่
- โครงการที่มีข้อแตกต่างผูกกับฉบับบริษัทที่ใช้เป็นฐาน เมื่อบริษัทออกฉบับใหม่ ให้แจ้งทบทวน คงชุดเดิมที่อนุมัติไว้จนกว่าชุดโครงการใหม่จะผ่านอนุมัติ ไม่ผสมค่าฉบับใหม่เข้าไปเงียบ ๆ
- การเปลี่ยนจากกติกาเฉพาะกลับไปใช้บริษัททั้งหมดถือเป็นการเปลี่ยนกติกาที่ต้องอนุมัติ
- คำขอที่ส่งแล้วไม่เปลี่ยนตามกติกาใหม่ การส่งฉบับใหม่หลังถูกส่งกลับจึงประเมินด้วยชุดที่มีผลขณะส่งใหม่

### 2.2 วงจรกติกา

ร่าง → ส่งตรวจ → อนุมัติและเปิดใช้ โดยมีทางส่งกลับแก้ไขหรือปฏิเสธพร้อมเหตุผล

- ผู้แก้ไขกับผู้อนุมัติเป็นคนละคน แม้ถือสิทธิ์ทั้งสองระดับ ผู้ร่วมแก้เนื้อหาฉบับนั้นต้องไม่อนุมัติฉบับเดียวกัน
- ฉบับรอตรวจต้องมีเนื้อหาคงที่ การแก้หลังส่งตรวจต้องส่งให้ตรวจใหม่ ผลอนุมัติเดิมไม่ย้ายมาใช้
- ฉบับเปิดใช้แล้วแก้ทับไม่ได้ ต้องสร้างฉบับใหม่และเก็บฉบับเดิมสำหรับอ้างอิงย้อนหลัง
- ขณะรอตรวจใช้ฉบับเดิม หากไม่มีชุดที่ใช้ได้ ให้ปฏิเสธการส่งคำขอใหม่ ไม่สร้างค่าเริ่มต้นการเงินขึ้นเอง
- การเปิดใช้ฉบับใหม่ต้องเปลี่ยนสถานะฉบับเดิมและบันทึกประวัติในธุรกรรมเดียวกัน ไม่มีฉบับที่มีผลซ้อนกันในขอบเขตเดียวกัน

### 2.3 วงเงินและลำดับอนุมัติ

- กำหนดช่วงยอดและระดับอำนาจเป็นข้อมูล ไม่ฝังยอดวงเงินธุรกิจไว้ในโค้ด
- สำหรับ 7B ลำดับเริ่มจากหัวหน้าตามสายงาน → ผู้จัดการโครงการ → ผู้บริหารทุกระดับที่ต้องผ่านตามยอดรวม
- ขอบช่วงต้องระบุชัดว่ายอดเท่าขอบอยู่ระดับใด ห้ามช่วงทับซ้อนหรือกำกวม ยอดที่ไม่มีอำนาจรองรับต้องให้ผลว่าไม่พร้อมดำเนินการ
- การประเมินวงเงินใช้ยอดรวมคำขอ ไม่ใช้เฉพาะยอดเพิ่มเพื่อหลบระดับอนุมัติ
- ระดับอำนาจที่ต้องผ่านไม่เท่ากับบุคคลที่มีสิทธิ์ลงมือ การเลือกบุคคลต้องตรวจสิทธิ์ปัจจุบันและการแยกหน้าที่อีกชั้น

### 2.4 หมวด อัตรา หลักฐาน และกำหนดเคลียร์

- เริ่มห้าหมวด: เดินทาง ที่พัก อาหาร เบี้ยเลี้ยง และน้ำมัน ผู้มีสิทธิ์เพิ่มหรือปิดใช้งานได้ ไม่ลบข้อมูลที่รายการเก่าอ้างอิง
- หมวดที่มีอัตรามาตรฐานใช้จำนวน × อัตราเท่านั้น ผู้ขอแก้อัตราหรือใช้ยอดเหมารวมเลี่ยงมาตรฐานไม่ได้
- หมวดไม่มีอัตรามาตรฐานเลือกยอดเหมารวมหรือจำนวน × อัตราที่กรอกเองได้
- อัตราบริษัทและโครงการผ่านการแยกผู้แก้กับผู้อนุมัติระดับบริษัทเหมือนกติกาวงเงิน
- เก็บจำนวนเงินด้วยเลขฐานสิบที่เหมาะกับเงิน ไม่ใช้เลขทศนิยมแบบประมาณค่าเพื่อเปรียบเทียบวงเงิน ผลยอดเงินเป็นบาทและสตางค์ การกำหนดความละเอียดจำนวนและการปัดเศษต้องระบุให้ตรงกันในสัญญาคำนวณก่อนพัฒนา 7B
- ทุกหมวดต้องมีประเภทหลักฐาน เช่น ใบเสร็จ ใบรับเงิน หรือเอกสารรับรองออกสนาม 7A จัดการข้อกำหนด ไม่อัปโหลดหรือตรวจเอกสารเงินจริง
- กำหนดจำนวนวันเคลียร์ได้ระดับบริษัทและโครงการ นับวันปฏิทิน โดยวันถัดจากวันจบงานจริงเป็นวันที่ 1 ไม่ฝังจำนวนวันธุรกิจตายตัว
- หมวดที่ปิดหรืออัตราที่เปลี่ยนต้องไม่เปลี่ยนข้อมูลในฉบับคำขอเก่า การใช้อัตราใหม่กับคำขอที่อนุมัติแล้วต้องผ่านกระบวนการปรับปรุงในส่วนถัดไป

## 3. ส่วนที่สอง — สิทธิ์และการแยกหน้าที่

### 3.1 แยกสิทธิ์ตามหน้าที่

| กลุ่มสิทธิ์ | ขอบเขตและข้อจำกัด |
|---|---|
| แก้กติกาบริษัท | เสนอฉบับบริษัท ไม่อนุมัติฉบับที่ตนแก้ |
| แก้กติกาโครงการ | เฉพาะโครงการที่ได้รับมอบหมาย ไม่อนุมัติเอง |
| อนุมัติกติกา | ผู้ได้รับสิทธิ์ระดับบริษัท ตรวจได้เฉพาะขอบเขตที่มอบหมาย |
| เสนอและอนุมัติการมอบหมาย | เป็นสิทธิ์บริหารแยกกัน ไม่ทำให้มีสิทธิ์ใช้ข้อมูลการเงิน |
| อนุมัติคำขอ | ดูเฉพาะคำขอที่มอบหมายให้อนุมัติ ภาพรวมต้องมีสิทธิ์รายงานเพิ่ม |
| ตรวจสอบการเงิน | ดูตามโครงการที่มอบหมาย การลงมือต้องผ่านข้อห้ามของคำขอ |
| บันทึกจ่าย | แยกจากผู้ตรวจการเงิน และผ่านข้อห้ามของคำขอ |
| ดูรายงาน | มอบหมายแยกและระบุขอบเขต ไม่ทำให้อนุมัติ ตรวจ หรือจ่ายได้ |

สมาชิกทีมออกสนามไม่ได้สิทธิ์ดูข้อมูลการเงินเพราะมีชื่อในทีม ผู้ดูแลระบบและผู้จัดการโครงการไม่ได้สิทธิ์จัดการกติกาหรือข้อมูลการเงินทั้งหมดโดยอัตโนมัติ

**ยืนยันขอบเขตเพิ่มเติม 20 ตุลาคม 2569:** ผู้มีสิทธิ์ระดับบริษัทในการอนุมัติกติกาและจัดการสิทธิ์ดำเนินการกับโครงการได้เฉพาะโครงการที่ได้รับมอบหมายเป็นรายโครงการ ไม่มีการครอบคลุมทุกโครงการอัตโนมัติ การตรวจ capability ต้องตรงทั้งบริษัทและโครงการของงานนั้น; grant ระดับบริษัทที่ไม่ระบุโครงการใช้กับงานระดับบริษัทเท่านั้น และไม่เพิ่มสิทธิ์ดูยอดเงินหรือหลักฐาน

### 3.2 วงจรมอบหมายสิทธิ์

เสนอ → ตรวจอนุมัติ → เริ่มใช้ตามวันเวลาที่กำหนด

แต่ละรายการมีผู้รับ บทบาท/ความสามารถ ขอบเขตบริษัทหรือโครงการ เวลาเริ่ม เวลาหมดอายุถ้ามี และเหตุผล

- ผู้เสนอ ผู้อนุมัติ และผู้รับต้องเป็นสามคนต่างกัน ตรวจโดยตัวตนบุคคล ไม่ใช่เพียงเลือกชื่อบทบาทต่างกัน
- ผู้เสนอและผู้อนุมัติต้องได้รับอำนาจมอบหมายสิทธิ์ประเภทนั้นและขอบเขตนั้นโดยเฉพาะ การมีสิทธิ์ใช้งานไม่ได้หมายถึงมอบให้คนอื่นได้
- การเพิ่มโครงการ เพิ่มวงเงินอำนาจ ต่ออายุ หรือเพิ่มความสามารถของบทบาทเดิมต้องผ่านขั้นตอนเดียวกัน
- ห้ามช่องทางจัดการบทบาทหรือ scope เดิมเพิ่มสิทธิ์การเงินโดยข้ามกระบวนการนี้ ต้องตรวจเส้นทางแก้สิทธิ์เดิมร่วมด้วย
- ถ้าไม่มีผู้อนุมัติที่เข้าเงื่อนไข ให้ค้างรอ ไม่ใช้ admin สำรองอัตโนมัติ
- ผู้มีสิทธิ์ระงับ/ถอนทำได้ทันทีภายในอำนาจพร้อมเหตุผล การคืนสิทธิ์ต้องเสนอและอนุมัติใหม่
- การถอน หมดอายุ หรือระงับไม่ลบประวัติ และต้องมีผลกับการตรวจสิทธิ์ครั้งถัดไปแม้ผู้ใช้ยังเปิดหน้าจอเดิม

**กติกาการมอบหมายที่ผู้ใช้ยืนยันเพิ่มเติม 20 ตุลาคม 2569:**

- ไม่ระบุวงเงิน (`ApprovalLimit = null`) หมายถึงไม่มีอำนาจอนุมัติยอดเงิน ไม่ใช่วงเงินไม่จำกัด ไม่บวกวงเงินหลายสิทธิ์เพื่อขยายอำนาจ แต่ละประเภทสิทธิ์ที่มอบต้องมีอำนาจต้นทางครอบคลุมวงเงินนั้น
- สิทธิ์ที่มอบต้องไม่หมดอายุช้ากว่าอำนาจมอบหมายของผู้เสนอและผู้อนุมัติ และตรวจเงื่อนไขนี้อีกครั้งก่อนอนุมัติ
- ผู้ถอนต้องมีสิทธิ์ถอนในขอบเขตนั้น และมีอำนาจมอบหมายครอบคลุมประเภทสิทธิ์และวงเงินของรายการเป้าหมายด้วย

### 3.3 ห้ามใช้สิทธิ์ใหม่ล้างข้อห้ามคำขอ

หลักที่จะใช้ร่วมกับ 7B–7D:

- ผู้รับผิดชอบเงินและผู้ยื่นแทนไม่อนุมัติ ตรวจการเงิน หรือบันทึกจ่ายของคำขอนั้น
- ผู้อนุมัติแต่ละขั้นต้องต่างคน คนซ้ำส่งต่อระดับถัดไปที่มีอำนาจ หากไม่มีให้พัก
- ผู้อนุมัติคำขอ ผู้ตรวจการเงิน และผู้บันทึกจ่ายต้องแยกกัน
- คนที่เคยตรวจการเงินห้ามบันทึกจ่าย และคนที่เคยบันทึกจ่ายห้ามตรวจงวดอื่นของคำขอเดียวกัน
- การถอนแล้วให้สิทธิ์ใหม่ เปลี่ยนบทบาท หรือย้ายโครงการไม่ล้างประวัติการมีส่วนร่วม

7A ทดสอบตัวประเมินข้อห้ามด้วยบริบทจำลอง ยังไม่ถือว่ากระบวนการคำขอและงวดเงินจริงซึ่งจะสร้างใน 7B–7D ผ่านการทดสอบแล้ว

### 3.4 ผู้บริหารสิทธิ์ชุดแรก

ตั้งต้นผ่านรายชื่อที่บริษัทรับรองและมีผู้ตรวจอิสระ บันทึกผู้รับรอง ผู้ตรวจ ผู้ดำเนินการ เหตุผล และขอบเขต โดยไม่ให้บัญชี admin ได้สิทธิ์ธุรกิจอัตโนมัติ

ข้อกำหนดเพิ่มเติมที่ผู้ใช้ยืนยันสำหรับ Task 5:

- สร้างข้อมูลบุคคลและการผูกบัญชีที่ยังไม่มีได้เฉพาะรหัสบุคคลที่ระบุชัดในรายชื่อบริษัทรับรอง หากขัดกับข้อมูลเดิมต้องปฏิเสธ และบันทึกพร้อมสิทธิ์ในธุรกรรมเดียวกัน
- ผู้รับรอง ผู้ตรวจอิสระ และผู้รันคำสั่งต้องเป็นคนละบุคคล และทั้งสามต้องไม่เป็นผู้รับสิทธิ์คนใดในชุดนั้น ตรวจระดับบุคคล ไม่ใช่เพียงชื่อบัญชี
- สิทธิ์ใช้งานชุดตั้งต้นจำกัดที่เสนอ–อนุมัติ–ถอนสิทธิ์ (`grant.propose`, `grant.review`, `grant.revoke`) พร้อมระบุสิทธิ์ที่มอบต่อได้ วงเงิน และขอบเขตบริษัทหรือโครงการอย่างชัดเจน ไม่ให้สิทธิ์ดูข้อมูลการเงินหรือจ่ายเงินโดยอัตโนมัติ ขอบเขตบริษัทไม่ครอบคลุมทุกโครงการโดยปริยาย

ช่องทางตั้งต้นต้องใช้เพื่อการตั้งระบบเท่านั้น ไม่เป็นทางลัดมอบสิทธิ์ประจำวัน เมื่อมีผู้บริหารสิทธิ์ที่ใช้งานได้แล้วให้ใช้วงจรสามคน การเลือกบุคคลจริงและหลักฐานรับรองเป็นเงื่อนไขก่อนเปิดใช้ ไม่ใช่สิ่งที่โค้ดสร้างหรืออนุมานให้บริษัท

ข้อจำกัดความปลอดภัย: กติกานี้ควบคุมผ่านแอปพลิเคชันและ API ไม่รับรองการป้องกันบุคคลที่มีอำนาจแก้ฐานข้อมูลหรือโค้ดโดยตรง ต้องแยกสิทธิ์โครงสร้างพื้นฐานและดูแลหลักฐานตรวจสอบนอกแอปร่วมด้วย

## 4. ส่วนที่สาม — ข้อมูลและหน้าจอ

### 4.1 กลุ่มข้อมูลเชิงแนวคิด

| กลุ่มข้อมูล | เนื้อหาหลัก |
|---|---|
| ฉบับกติกา | ขอบเขต ฉบับฐานบริษัท สถานะ ผู้แก้ รายละเอียด และเวลาเปิดใช้ |
| รายละเอียดกติกา | ระดับวงเงิน หมวด หน่วย อัตรา ประเภทหลักฐาน และจำนวนวันเคลียร์ |
| ผลตรวจฉบับ | ฉบับเนื้อหาที่ตรวจ ผู้ตรวจ ผล เหตุผล และเวลา |
| ข้อเสนอสิทธิ์ | ผู้เสนอ ผู้รับ สิทธิ์ ขอบเขต ระยะเวลา สถานะ และผลอนุมัติ |
| สิทธิ์ที่มีผล | ข้อเสนอที่เป็นต้นทาง ระยะเวลามีผล การระงับ/ถอน และรุ่นข้อมูล |
| ประวัติเหตุการณ์ | ผู้ทำรายการ การกระทำ เป้าหมาย ขอบเขต ผล เหตุผล และเวลา |

ชื่อกลุ่มเป็นขอบเขตออกแบบ ไม่ใช่ข้อบังคับชื่อฐานข้อมูลจริง กติกาและผลอนุมัติอ้างฉบับที่แน่นอน ไม่อ้างเพียงแถวข้อมูลล่าสุดที่แก้ทับได้

### 4.2 หน้าจอที่ส่งมอบ

1. กติกาบริษัท: จัดการฉบับและดูฉบับที่มีผล
2. กติกาโครงการ: แสดงค่าจากบริษัท ข้อแตกต่าง ฉบับฐาน และสถานะต้องทบทวน
3. หมวดและอัตรา: จัดการหมวด หน่วย อัตรา และหลักฐาน โดยการเปลี่ยนกติกาที่มีผลต้องผ่านการอนุมัติ
4. การมอบหมายสิทธิ์: เสนอ ตรวจ ระงับ ถอน และดูระยะเวลาสิทธิ์
5. งานรอตรวจ: เปรียบเทียบก่อน–หลัง ส่งกลับ/ปฏิเสธพร้อมเหตุผล และอนุมัติ
6. ประวัติ: ดูเหตุการณ์เฉพาะขอบเขตที่มีสิทธิ์ ไม่เปิดข้อมูลการเงินเพิ่มเพียงเพราะมีสิทธิ์ดูประวัติการตั้งค่า

มีตัวอย่างประเมินวงเงินให้กรอกยอดแล้วเห็นระดับที่ต้องผ่าน ไม่สร้างคำขอหรือรับรองว่ามีบุคคลพร้อมอนุมัติจริง การแสดงข้อมูลตัวอย่างและชื่อบุคคลต้องอยู่ในขอบเขตที่ผู้ใช้มีสิทธิ์

### 4.3 การตรวจข้อมูลก่อนส่งและก่อนเปิดใช้

- ตรวจข้อมูลจำเป็น ขอบเขตจริง ความสัมพันธ์บริษัท–โครงการ และสถานะใช้งาน
- ตรวจช่วงยอด/ลำดับอนุมัติ อัตรา/หน่วย และทุกหมวดมีประเภทหลักฐาน
- ตรวจฉบับที่ผู้ตรวจเห็นตรงกับฉบับที่จะเปิดใช้ พร้อมตรวจสิทธิ์ปัจจุบันอีกครั้ง
- ตรวจข้อเสนอสิทธิ์ว่าผู้เกี่ยวข้องต่างคน ขอบเขตไม่เกินอำนาจ และเวลามีผลสมเหตุสมผล
- ช่องทาง API ใช้กฎเดียวกับหน้าจอ ห้ามเชื่อข้อมูลที่ผู้ใช้ส่งมาเพื่อขยาย scope

## 5. ส่วนที่สี่ — สถาปัตยกรรม ข้อผิดพลาด และการทดสอบ

### 5.1 เชื่อมระบบเดิมอย่างมีขอบเขต

ใช้ระบบบัญชี/session/MFA โครงสร้างองค์กร โครงการ ขอบเขตสิทธิ์ และ audit เดิม โดยเพิ่มส่วนการเงินที่แยกหน้าที่ชัดเจน:

- ส่วนจัดการฉบับกติกา: สร้างร่าง ส่งตรวจ เปิดใช้ และเก็บประวัติ
- ส่วนเลือกกติกา: รับบริษัท/โครงการและเวลาที่ประเมิน คืนฉบับที่ใช้พร้อมที่มาของค่า
- ส่วนประเมินระดับวงเงิน: รับยอดกับชุดกติกา คืนระดับที่ต้องผ่านหรือเหตุผลที่ไม่พร้อม
- ส่วนบริหารการมอบหมาย: เสนอ อนุมัติ เริ่มใช้ ระงับ ถอน และบันทึกประวัติ
- ส่วนประเมินสิทธิ์และการแยกหน้าที่: รับผู้กระทำ ขอบเขต การกระทำ และบริบทคำขอ คืนอนุญาต/ปฏิเสธพร้อมเหตุผลที่ไม่เผยข้อมูลเกินสิทธิ์

ฐานที่ตรวจอ้างอิงจาก origin/main มี Organization/EffectiveRolePolicy.cs, Scopes/Assignments/AssignmentContracts.cs และ Organization/OrganizationService.cs ซึ่งแสดงระบบ MFA ขอบเขต assignment การตรวจรุ่นข้อมูล และธุรกรรม audit อยู่แล้ว แต่ยังไม่ถือว่ามีกระบวนการสามคนของ 7A ต้องตรวจทุกช่องทางเพิ่มสิทธิ์ก่อนนำมาใช้

ไม่ใช้ workflow คำร้องลงเวลาเป็น workflow การเงินโดยตรง ไม่คัดลอกสิทธิ์ attendance มาใช้แทนสิทธิ์การเงิน และไม่สร้างระบบอนุมัติทั่วไปเกินขอบเขตนี้

### 5.2 กติกาคงเดิม แต่สิทธิ์ต้องเป็นปัจจุบัน

เมื่อ 7B ส่งคำขอ ต้องบันทึกชุดกติกาและอัตราเป็นหลักฐานของฉบับนั้น ส่วนการลงมือทุกครั้งตรวจผู้ใช้ สิทธิ์ ขอบเขต อายุสิทธิ์ และข้อห้ามจากประวัติปัจจุบัน ไม่ใช้ snapshot เพื่อคงสิทธิ์ที่ถูกถอน

ถ้าไม่มีผู้ผ่านเงื่อนไขให้พักรายการพร้อมเหตุผล ไม่ลดขั้นหรือขยายสิทธิ์อัตโนมัติ

### 5.3 ความถูกต้องเมื่อทำพร้อมกันหรือเกิดข้อผิดพลาด

| กรณี | ผลที่ต้องได้ |
|---|---|
| ส่งหรืออนุมัติซ้ำ | ไม่เกิดสิทธิ์ ผลอนุมัติ หรือการเปิดใช้ซ้ำ |
| แก้พร้อมกัน | ตรวจรุ่นข้อมูล แจ้งให้โหลดฉบับล่าสุด ไม่เขียนทับเงียบ ๆ |
| ถอนสิทธิ์ขณะมีรายการอนุมัติ | จัดลำดับการเปลี่ยนสถานะอย่างสอดคล้องและตรวจสิทธิ์ก่อนยืนยันผล |
| บันทึกข้อมูลหรือ audit ล้มเหลว | ย้อนคืนการเปลี่ยนแปลงทั้งหมด ไม่เหลือสิทธิ์หรือกติกาเปิดใช้บางส่วน |
| หมดอายุหรือโครงการปิดใช้ | ปฏิเสธการทำรายการใหม่ตามขอบเขต ไม่ฟื้นสิทธิ์เองเมื่อเปิดโครงการอีกครั้ง |
| ขอข้อมูลโครงการที่ไม่มีสิทธิ์ | ปฏิเสธโดยไม่เปิดเผยเนื้อหา ชื่อ หรือจำนวนรายการที่ไม่มีสิทธิ์ |
| บริการตรวจสิทธิ์หรือกติกาไม่พร้อม | ไม่อนุญาตโดยปริยาย ให้ข้อความลองใหม่ที่ไม่เผยรายละเอียดภายใน |

การทำรายการที่เปลี่ยนสถานะต้องมีธุรกรรม การควบคุมรุ่นข้อมูล และการจัดการคำสั่งซ้ำ ไม่พึ่งการปิดปุ่มหน้าจออย่างเดียว บันทึกเวลาเหตุการณ์ฝั่งเซิร์ฟเวอร์และแสดงเขตเวลาให้ชัดเจน

ทดสอบระดับหน่วย ส่วนเชื่อมฐานข้อมูล/API และหน้าจอตามความเสี่ยง สำหรับข้อห้ามคำขอใช้บริบทจำลองใน 7A และเพิ่มการทดสอบคำขอจริงใน 7B–7D ภายหลัง

ขั้นพัฒนาต้องทำ TDD, Code Review และรัน Test, Build, Lint ครบ พร้อมเก็บคำสั่งและผลจริงก่อนอ้างว่าส่งมอบสำเร็จ การตรวจเอกสารฉบับนี้ไม่ใช่ผลผ่านการทดสอบโปรแกรม

## 6. เงื่อนไขก่อนเปิดใช้งานและขั้นถัดไป

- บริษัทต้องจัดผู้บริหารสิทธิ์ชุดแรกและหลักฐานรับรองตามกระบวนการตั้งต้น
- ต้องมีวงเงิน อัตราที่ต้องใช้ จำนวนวันเคลียร์ และผู้มีสิทธิ์จริงที่ผ่านอนุมัติ ไม่มีการใส่ยอดสมมติเป็นนโยบายผลิตจริง
- การรับรอง 7A ไม่ใช่การรับรองกระบวนการเงินทั้งระบบ ต้องพัฒนาและตรวจ7B–7Dก่อนใช้เงินจริงครบวงจร
- คงพักมือถือจริงและ NAS จริง บันทึกเป็นงานที่ยังไม่ได้ตรวจ ไม่ลบออกจากรายการตรวจความพร้อมใช้งานจริง
- Implementation Plan ได้รับอนุมัติแล้ว ดำเนินการเฉพาะ Task ที่ผู้ใช้สั่งเริ่ม; ปัจจุบัน Task 1–4 เสร็จ ขั้นถัดไปคือ Task 5 ตั้งต้นผู้บริหารสิทธิ์โดยไม่ให้ admin อัตโนมัติ รอผู้ใช้สั่งเริ่ม

## 7. ผลตรวจเอกสารก่อนส่งผู้ใช้

- รวมแบบทั้งสี่ส่วนและแยกขอบเขต7Aจาก7B–7Dชัดเจน
- แยกกติกาสองคนออกจากการมอบหมายสิทธิ์สามคน และแยกสิทธิ์ปัจจุบันจากกติกาคำขอที่ตรึงไว้
- แยกโครงการรับบริษัททั้งหมดออกจากโครงการเฉพาะที่ต้องทบทวนฐานฉบับใหม่
- ระบุกรณีล้มเหลว สิทธิ์ข้ามขอบเขต การเปลี่ยนพร้อมกัน และเกณฑ์ทดสอบที่ต้องพิสูจน์
- ไม่ใส่รหัสผ่าน คีย์ MFA หรือข้อมูลลับ ไม่แก้เอกสารเดิมที่ค้างอยู่ใน workspace
- ขณะตรวจเอกสารรอบแรกยังไม่เริ่มพัฒนา ผู้ใช้อนุมัติเอกสารแล้วและให้จัดทำแผน; สถานะปัจจุบันให้ยึดหัวเอกสารและผลตรวจแต่ละ Task ใน Implementation Plan
