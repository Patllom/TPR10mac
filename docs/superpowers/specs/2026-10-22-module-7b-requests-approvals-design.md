# เอกสารออกแบบ Module 7B คำขอเงินทดรองออกสนามและสายอนุมัติ

วันที่: 22 ตุลาคม 2569 (2026-10-22)

สถานะ: ผู้ใช้อนุมัติเอกสารฉบับรวมแล้วเมื่อ 22 ตุลาคม 2569 ให้จัดทำ Implementation Plan ภาษาไทย ยังไม่เริ่มพัฒนา 7B และต้องรออนุมัติแผนก่อนเริ่มลงมือ

## สรุปสำหรับผู้ตรวจ

7B ทำให้ผู้มีสิทธิ์ขอเงินทดรองออกสนามได้ด้วยตนเองหรือยื่นแทน โดยแต่ละคำขอมีผู้รับผิดชอบเงินหนึ่งคน ผู้รับผิดชอบต้องยืนยันก่อนส่งเข้าสายอนุมัติ ระบบใช้ยอดรวมกำหนดทุกขั้นที่ต้องผ่าน ตรวจสิทธิ์ปัจจุบันและการแยกหน้าที่ก่อนลงผลทุกครั้ง และเก็บประวัติแต่ละฉบับโดยไม่แก้ย้อนหลัง

ผลปลายทางของ 7B คือ “อนุมัติแล้ว รอดำเนินการจ่าย” ไม่ใช่จ่ายแล้ว การจ่ายและปรับปรุงคำขอที่อนุมัติแล้วเป็น 7C ส่วนเคลียร์ค่าใช้จ่าย คืนเงิน และปิดบัญชีคำขอเป็น 7D

คง Minor M2/M3 ไว้ติดตามตามหัวข้อ 7 และพักการทดสอบมือถือจริงกับ NAS จริง ไม่ถือว่ารายการที่พักผ่านแล้ว

## 1. เป้าหมายและขอบเขต

### 1.1 สิ่งที่รวม

- คำขอรายบุคคลและแบบทีม โดยหนึ่งโครงการและหนึ่งผู้รับผิดชอบเงินต่อคำขอ
- ร่างคำขอ ประมาณการค่าใช้จ่าย การยื่นแทน และการยืนยันของผู้รับผิดชอบเงิน
- ฉบับแก้ไขแยกจากคำขอหลัก พร้อมข้อมูลและกติกาที่ตรึงไว้เมื่อส่ง
- สายอนุมัติเรียงตามลำดับ การเปลี่ยนผู้รับงานตามสิทธิ์ปัจจุบัน และการพักเมื่อไม่มีผู้เข้าเงื่อนไข
- การส่งกลับ ปฏิเสธ ถอนก่อนอนุมัติครบ และคัดลอกเป็นคำขอใหม่ที่อ้างอิงต้นทาง
- หน้าจอ/API ตามขอบเขตสิทธิ์ ประวัติ และการป้องกันคำสั่งซ้ำหรือชนกัน

### 1.2 สิ่งที่ไม่รวม

- งวดจ่าย หลักฐานการจ่าย การระงับจ่าย และคำร้องปรับปรุงหลังอนุมัติครบ ซึ่งเป็น 7C
- รับรองค่าใช้จ่าย อัปโหลด/ตรวจหลักฐานค่าใช้จ่าย ตรวจเอกสารซ้ำ คืนเงิน และปิดคำขอทางการเงิน ซึ่งเป็น 7D
- กระบวนการเบิกคืน สกุลเงินอื่น โอนธนาคารอัตโนมัติ และระบบอนุมัติกลางสำหรับทุกโมดูล
- การแก้ Minor M2/M3 โดยถือว่าเสร็จไปพร้อมเอกสาร หรือการทดสอบมือถือจริง/NAS จริง

การมีข้อกำหนดชนิดหลักฐานในกติกา 7A ไม่ได้หมายความว่าต้องมีใบเสร็จค่าใช้จ่ายจริงก่อนขอเงินใน 7B

## 2. ส่วนที่หนึ่ง คำขอ ฉบับแก้ไข และยอดเงิน

### 2.1 โครงสร้างที่เลือก

ใช้คำขอหลักพร้อมฉบับแยกในระบบเดิม เชื่อมฐานกติกาและสิทธิ์ 7A ไม่สร้างบริการอนุมัติแยกหรือระบบเก็บทุกการเปลี่ยนแปลงแบบ event sourcing เต็มรูปแบบ เพราะยังไม่จำเป็นต่อขอบเขตนี้

| ข้อมูล | หน้าที่ |
|---|---|
| คำขอหลัก | ตัวตนคำขอ โครงการ ผู้รับผิดชอบเงิน ผู้ยื่นแทนถ้ามี สถานะรวม และคำขอต้นทางถ้าคัดลอก |
| ฉบับคำขอ | เนื้อหา ประมาณการ เลขฉบับ ผู้จัดทำ การยืนยัน และสถานะของฉบับนั้น |
| ชุดกติกาที่บันทึกไว้ | ฉบับบริษัท/โครงการ อัตรา หมวด และระดับอนุมัติที่ใช้ตอนส่ง พร้อมข้อมูลตรวจความตรงกัน |
| ขั้นอนุมัติ | ลำดับ บทบาทที่ต้องผ่าน ผู้รับงานปัจจุบัน และเหตุผลที่พัก/เปลี่ยนผู้รับงาน |
| ผลอนุมัติและประวัติ | ผู้กระทำที่ระบุตัวบุคคลได้ เวลา เหตุผล ฉบับ ขั้น และผลการเปลี่ยนสถานะ |
| ประวัติการมีส่วนร่วม | ผู้รับผิดชอบ ผู้ยื่นแทน ผู้อนุมัติ และหน้าที่การเงินที่ใช้ป้องกันผลประโยชน์ทับซ้อน |

เนื้อหาที่ส่งเข้าสายอนุมัติแล้วแก้ทับไม่ได้ การเปลี่ยนผู้รับงานปัจจุบันไม่ใช่การเปลี่ยนเนื้อหาหรือผลอนุมัติเดิม

### 2.2 ข้อมูลสำหรับจัดทำคำขอ

- รูปแบบรายบุคคลหรือทีม โครงการ ผู้รับผิดชอบเงิน และรายชื่อทีมเมื่อเป็นแบบทีม
- รายละเอียดงานออกสนาม ช่วงวันที่ออกสนาม และวันที่ต้องการรับเงิน
- ประมาณการแยกรายการ: หมวด รายละเอียด วิธีคำนวณ จำนวน/หน่วย/อัตราตามวิธีที่เลือก และยอดรายการ
- ยอดรวมที่ระบบคำนวณ ไม่ให้กรอกยอดรวมอิสระที่ไม่ตรงกับรายการ
- ข้อมูลฉบับ เหตุผลเมื่อส่งกลับหรือถอน และการอ้างอิงคำขอเดิมถ้ามี

หมวดเริ่มต้นคือเดินทาง ที่พัก อาหาร เบี้ยเลี้ยง และน้ำมัน ใช้หมวดที่เปิดใช้ได้ตามกติกา 7A และเก็บชื่อ/ค่าที่ฉบับเก่าอ้างอิงไว้ โครงการเดียวต่อคำขอ หากหลายโครงการต้องแยกคำขอ

### 2.3 สัญญาการคำนวณ

ใช้เงินบาทเท่านั้น คำนวณฝั่งเซิร์ฟเวอร์ด้วยเลขฐานสิบที่เหมาะกับเงิน ไม่ใช้ floating point เป็นผลตัดสินวงเงิน

1. จำนวนไม่เกิน 4 ตำแหน่งทศนิยม อัตราและยอดเหมารวมไม่เกิน 2 ตำแหน่ง
2. หมวดมีอัตรามาตรฐานใช้จำนวน × อัตราตามกติกาเท่านั้น ห้ามแก้อัตราหรือเลือกเหมารวมเพื่อหลบมาตรฐาน
3. หมวดไม่มีอัตรามาตรฐานเลือกเหมารวมหรือจำนวน × อัตราที่กรอกเองได้
4. ปัดผลแต่ละรายการเป็นสตางค์ หลักที่สามตั้งแต่ 5 ปัดขึ้น แล้วจึงรวมยอดรายการที่ปัดแล้ว
5. ใช้ยอดรวมนี้กำหนดระดับอนุมัติ ไม่ประเมินจากยอดก่อนปัดหรือแบ่งรายการเพื่อลดระดับ
6. กรอกเกินความละเอียดให้แจ้งแก้ไข ไม่ตัดทศนิยมหรือปัดข้อมูลนำเข้าเงียบ ๆ
7. ไม่รับจำนวน/เงินติดลบหรือค่าที่เก็บและคำนวณไม่ได้ ยอดคำขอต้องมากกว่าศูนย์ ตรวจขอบเขตตัวเลขและผลคูณก่อนบันทึกตามขีดจำกัดชนิดข้อมูลและกติกา 7A ไม่สร้างเพดานธุรกิจใหม่ขึ้นเอง

ตัวอย่างคำนวณ: จำนวน 1.2345 × อัตรา 10.00 ได้ 12.345 จึงเป็น 12.35 บาท ถ้ามีสองรายการเช่นนี้ ยอดรวมคือ 24.70 บาท ไม่ใช่รวมก่อนแล้วปัดเป็น 24.69 บาท ตัวเลขนี้เป็นตัวอย่างคำนวณ ไม่ใช่อัตราบริษัท

### 2.4 การยืนยันและตรึงกติกา

ผู้ยื่นแทนจัดทำแล้วส่งให้ผู้รับผิดชอบเงินตรวจ ผู้ยื่นแทนยืนยันแทนไม่ได้ หากยื่นเอง ผู้รับผิดชอบใช้การกระทำ “ยืนยันและส่ง” ได้ในครั้งเดียว

ขณะยืนยันและส่ง ระบบตรวจสิทธิ์ เนื้อหาฉบับ ยอด และกติกาที่มีผลสำหรับโครงการอีกครั้ง แล้วบันทึกเนื้อหา การยืนยัน ชุดกติกา และสายอนุมัติร่วมกัน หากข้อมูลหรือกติกาต่างจากที่ผู้รับผิดชอบตรวจทาน ต้องหยุดให้โหลดและยืนยันใหม่ ไม่เปลี่ยนชุดข้อมูลเงียบ ๆ

คำว่า “กติกาล่าสุด” หมายถึงชุดที่มีผลสำหรับโครงการตามตัวเลือกกติกา 7A: โครงการใช้บริษัททั้งหมดรับฉบับบริษัทที่มีผล ส่วนโครงการเฉพาะยังใช้ฐานบริษัทที่อนุมัติผูกไว้จนผ่านการทบทวน ไม่ดึงบริษัทฉบับใหม่มาผสมเอง

หลังส่ง ตรึงกติกาและอัตราตลอดรอบอนุมัติของฉบับ แม้กติกากลางเปลี่ยน ผู้ดำเนินการยังต้องมีสิทธิ์ปัจจุบันเสมอ หากถูกส่งกลับแล้วส่งฉบับใหม่จึงเลือกกติกาที่มีผลใหม่อีกครั้ง

## 3. ส่วนที่สอง สิทธิ์และการแยกหน้าที่

### 3.1 สิทธิ์ยื่นคำขอ

เพิ่มความสามารถแยกกันรายโครงการคือ `request.create` สำหรับยื่นเอง/เป็นผู้รับผิดชอบที่มีสิทธิ์ และ `request.delegate` สำหรับยื่นแทน โดยใช้กระบวนการมอบหมาย 7A ผู้เสนอ ผู้อนุมัติ และผู้รับสิทธิ์เป็นสามบุคคลต่างกัน

ผู้ยื่นแทนต้องมีสิทธิ์ยื่นแทนในโครงการนั้น และผู้รับผิดชอบต้องมีสิทธิ์รับผิดชอบ/ยื่นคำขอในโครงการเดียวกัน ไม่มีสิทธิ์โดยอัตโนมัติเพราะเป็น admin หัวหน้า ผู้จัดการโครงการ หรือสมาชิกทีม การเพิ่มสิทธิ์ไม่ยกเว้นข้อห้ามของคำขอ

### 3.2 การอ่านและลงมือ

| ผู้เกี่ยวข้อง | ขอบเขต |
|---|---|
| ผู้รับผิดชอบเงินที่ยังมีสิทธิ์ | คำขอตนเอง ฉบับ และประวัติ ยืนยัน/ส่ง/ถอนตามสถานะที่อนุญาต |
| ผู้ยื่นแทนที่ยังมีสิทธิ์ | คำขอที่ตนยื่นแทน ไม่ใช่ทุกคำขอในโครงการ ไม่ยืนยันหรือถอนแทนผู้รับผิดชอบ |
| ผู้อนุมัติที่มีสิทธิ์ปัจจุบัน | คำขอที่ได้รับมอบหมายให้อนุมัติ ลงมือเฉพาะขั้นปัจจุบัน |
| สมาชิกทีมออกสนาม | ไม่มีสิทธิ์การเงินเพียงเพราะมีชื่อในทีม |
| ผู้มีสิทธิ์รายงาน | อ่านตามขอบเขตสิทธิ์รายงานแยกต่างหาก ไม่ได้สิทธิ์แก้หรืออนุมัติ |
| ผู้ดูแลระบบ | ไม่มีสิทธิ์อ่านยอด คำขอ หรือหลักฐานอัตโนมัติ |

ตรวจสิทธิ์ที่รายการ รายละเอียด ประวัติ และทุกคำสั่งบนเซิร์ฟเวอร์ ไม่พึ่งการซ่อนปุ่ม ไม่เปิดเผยชื่อ จำนวนรายการ หรือข้อมูลคำขออื่นผ่านข้อความผิดพลาด การเป็นอดีตผู้อนุมัติไม่ได้ทำให้มีสิทธิ์อ่านตลอดไปโดยอัตโนมัติ

เมื่อถอน/หมดอายุสิทธิ์ ให้หยุดการเข้าถึงและการกระทำที่อาศัยสิทธิ์นั้น แต่ไม่ลบประวัติผู้จัดทำ ผู้ยื่นแทน หรือข้อห้ามเดิม การมีบทบาทอื่นต้องตรวจตามบทบาทนั้นใหม่ ไม่ถือว่าการถอนแล้วให้ใหม่ล้างประวัติ

### 3.3 ข้อห้ามสองระดับ

**ระดับคำขอทั้งสายฉบับ:** ผู้รับผิดชอบเงินและผู้ยื่นแทนไม่อนุมัติ ตรวจการเงิน หรือบันทึกจ่ายคำขอนั้น ผู้เคยอนุมัติไม่เปลี่ยนไปตรวจการเงินหรือบันทึกจ่าย ผู้ตรวจการเงินกับผู้บันทึกจ่ายไม่สลับหน้าที่ข้ามงวด กฎเหล่านี้ยังคงเมื่อเปลี่ยนฉบับหรือสิทธิ์ และต้องเตรียมข้อมูลให้ 7C/7D ใช้ต่อ

**ระดับฉบับ:** ผู้อนุมัติคนหนึ่งอนุมัติได้หนึ่งขั้นต่อฉบับ ผู้อนุมัติเดิมกลับมาอนุมัติฉบับใหม่ได้หากยังมีอำนาจและผ่านข้อห้ามระดับคำขอ ต้องลงผลใหม่ทุกครั้ง ไม่ยกผลเก่ามาใช้

ตรวจตัวบุคคลจริง ไม่ใช้การเปลี่ยนบัญชีหรือหลายบทบาทหลบข้อห้าม ประวัติข้อห้ามมาจากเซิร์ฟเวอร์ ไม่รับชุดผู้เกี่ยวข้องจากผู้ใช้เป็นหลักฐานสิทธิ์

## 4. ส่วนที่สาม สายอนุมัติและการพักคำขอ

### 4.1 ลำดับที่ต้องผ่าน

ผู้รับผิดชอบยืนยัน → หัวหน้าตามสายงานของผู้รับผิดชอบ → ผู้จัดการโครงการ → ทุกระดับเพิ่มเติมตามยอดรวมและกติกาที่ตรึงไว้ → อนุมัติแล้ว รอดำเนินการจ่าย

ทุกขั้นต้องต่างบุคคลภายในฉบับ ผ่านตามลำดับ ห้ามข้ามขั้นเพียงเพราะคนหนึ่งมีวงเงินสูง ผู้ยื่นเลือกผู้อนุมัติเพื่อหลบสายงานไม่ได้

ผู้รับงานต้องเป็นผู้ดำรงบทบาท/ระดับที่เหมาะสม มีสิทธิ์ในโครงการ อำนาจครอบคลุมยอดรวม มีสถานะใช้งาน และผ่านการแยกหน้าที่ ตรวจทั้งตอนมอบหมายและตอนลงผลในธุรกรรม

### 4.2 เปลี่ยนผู้รับงานและไล่ระดับ

หากผู้รับงานเปลี่ยนตำแหน่งหรือไม่มีอำนาจ ให้ประเมินและส่งต่อผู้ดำรงตำแหน่งปัจจุบันอัตโนมัติพร้อมประวัติ หากติดข้อห้าม เช่น เป็นผู้รับผิดชอบ ผู้ยื่นแทน หรืออนุมัติขั้นก่อนในฉบับแล้ว ให้ไล่ไปผู้บังคับบัญชาระดับถัดไปที่มีอำนาจทำหน้าที่ขั้นนั้นได้

การไล่ระดับคือหา “ผู้ทำขั้นเดิม” ไม่ใช่ตัดขั้นนั้นทิ้ง ไม่ให้วงเงินสูงอย่างเดียวแทนข้อกำหนดบทบาท ไม่มีการเพิ่มสิทธิ์อัตโนมัติ และไม่แก้ผลขั้นที่อนุมัติไปแล้ว

### 4.3 ไม่มีผู้เข้าเงื่อนไข

พักคำขอเมื่อหาไม่ได้ สายบังคับบัญชาวนซ้ำ หรือข้อมูลผู้ดำรงบทบาทกำกวม ไม่สุ่มเลือกและไม่ใช้ admin ข้ามข้อจำกัด เก็บขั้นที่ค้างและเหตุผลที่แสดงได้ตามสิทธิ์

เมื่อโครงสร้าง/สิทธิ์ได้รับการแก้ตามกระบวนการที่มีอำนาจ ให้ประเมินใหม่ หากพบผู้เข้าเงื่อนไขให้กลับเป็นรออนุมัติที่ขั้นเดิม เก็บผลก่อนหน้าที่ยังถูกต้องและชุดกติกาเดิม ไม่อนุมัติเอง การพักนี้เป็นการพักสายอนุมัติ 7B ไม่ใช่การปลดระงับจ่าย 7C

## 5. ส่วนที่สี่ ส่งกลับ ปฏิเสธ และถอน

| เหตุการณ์ | ผู้ดำเนินการ | ผล |
|---|---|---|
| ส่งกลับก่อนผู้รับผิดชอบยืนยัน | ผู้รับผิดชอบเงิน | คืนข้อมูลให้แก้พร้อมเหตุผล ยังไม่เริ่มสายอนุมัติ |
| ส่งกลับระหว่างอนุมัติ | ผู้รับงานขั้นปัจจุบันที่ยังมีอำนาจ | คืนทั้งฉบับ ระบุสิ่งที่ต้องแก้และเหตุผล |
| ส่งใหม่หลังถูกส่งกลับ | ผู้จัดทำที่มีสิทธิ์และผู้รับผิดชอบยืนยัน | ฉบับใหม่ ใช้กติกาที่มีผลตอนส่ง เริ่มอนุมัติใหม่ทุกขั้น |
| ปฏิเสธ | ผู้รับงานขั้นปัจจุบันที่ยังมีอำนาจ | ปิดแบบปฏิเสธถาวร ต้องมีเหตุผล |
| ถอนก่อนอนุมัติครบ | ผู้รับผิดชอบเงินที่ยังมีสิทธิ์เท่านั้น | ถอนถาวร ต้องมีเหตุผล หยุดงานอนุมัติที่ค้าง เก็บประวัติ |
| แก้ไขหลังอนุมัติครบ | ไม่เปิดให้ทำตรงผ่าน 7B | ใช้คำร้องปรับปรุง 7C ในระยะถัดไป แม้ยังไม่จ่าย |

ฉบับเดิมและผลเดิมยังอยู่เป็นประวัติ แต่ไม่ใช้เป็นผลอนุมัติฉบับใหม่ การถอนทำได้ในสถานะก่อนอนุมัติครบ รวมรอผู้รับผิดชอบ รออนุมัติ พัก และส่งกลับ แต่คำขอที่ปฏิเสธหรือถอนแล้วไม่เปิดกลับ ผู้ยื่นแทนถอนให้ไม่ได้

หากต้องการขออีกหลังปฏิเสธหรือถอน ให้สร้างคำขอใหม่ คัดลอกข้อมูลที่ผู้ใช้ยังมีสิทธิ์อ่านและอ้างอิงต้นทางได้ โดยตรวจสิทธิ์/กติกาและยืนยันใหม่ ไม่คัดลอกผลอนุมัติ สถานะ หรือสิทธิ์จากคำขอเก่า การคัดลอกไม่ยกเว้นข้อห้ามของผู้เกี่ยวข้องในคำขอใหม่

หากคำสั่งถอนชนกับอนุมัติขั้นสุดท้าย ให้จัดลำดับและตรวจรุ่นข้อมูล มีผลสำเร็จเพียงทางเดียว อีกคำสั่งต้องรับสถานะล่าสุด ไม่เกิดคำขอทั้งอนุมัติและถอนพร้อมกัน

## 6. ส่วนที่ห้า หน้าจอ บริการ ความถูกต้อง และเกณฑ์ทดสอบ

### 6.1 หน้าจอ

1. **คำขอของฉัน/ที่ยื่นแทน:** สถานะ ยอด วันที่ต้องการเงิน และสิ่งที่ต้องดำเนินการ เฉพาะรายการที่มีสิทธิ์
2. **จัดทำคำขอ:** ข้อมูลออกสนาม รายการประมาณการ และยอดคำนวณ แจ้งข้อมูลผิดที่ช่อง ไม่ปรับตัวเลขเงียบ ๆ
3. **ยืนยันผู้รับผิดชอบ:** เนื้อหาครบ ยอด กติกาที่ใช้ และความต่างจากฉบับก่อน หากเปลี่ยนก่อนส่งต้องทบทวนใหม่
4. **งานรออนุมัติ:** รายการที่มอบหมาย ขั้นปัจจุบัน และการอนุมัติ/ส่งกลับ/ปฏิเสธตามสิทธิ์
5. **รายละเอียดและประวัติ:** ฉบับ ผลแต่ละขั้น การเปลี่ยนผู้รับงาน เหตุผลส่งกลับ/ปฏิเสธ/ถอน และการพัก โดยไม่แสดงข้อมูลนอกสิทธิ์

ทุกหน้าต้องแยกอนุมัติครบออกจากจ่ายแล้ว โหลดผลรุ่นล่าสุดหลังคำสั่งสำเร็จ และหยุดแสดงข้อมูลที่ไม่มีสิทธิ์ต่อเมื่อ session หรือสิทธิ์ใช้ไม่ได้ ข้อผิดพลาดไม่เปิดเผยข้อมูลบุคคล/โครงการอื่น

### 6.2 ขอบเขตบริการและ API

ใช้บัญชี session/MFA โครงสร้างองค์กร โครงการ และ audit เดิม ไม่คัดลอกสิทธิ์ลงเวลามาแทนสิทธิ์การเงิน แยกความรับผิดชอบดังนี้:

| ส่วน | หน้าที่และการเชื่อมต่อ |
|---|---|
| จัดการคำขอ/ฉบับ | ควบคุมสถานะ เนื้อหา และคำสั่ง เรียกสิทธิ์ คำนวณ และกติกา |
| คำนวณประมาณการ | รับข้อมูลรายการที่ตรวจแล้ว คืนยอดฐานสิบและข้อผิดพลาดรายช่อง |
| เลือกและตรึงกติกา | ใช้ตัวเลือกกติกา 7A ภายในบริการที่ตรวจสิทธิ์คำขอแล้ว คืนเฉพาะข้อมูลที่จำเป็น ไม่เพิ่มสิทธิ์จัดการกติกาให้ผู้ขอ |
| ประเมินสายอนุมัติ | รับยอดและชุดกติกาเพื่อกำหนดขั้น แล้วใช้โครงสร้าง/สิทธิ์ปัจจุบันหาผู้รับงาน |
| ประเมินสิทธิ์/ข้อห้าม | ตรวจตัวบุคคล ขอบเขต อายุสิทธิ์ ประวัติระดับคำขอ และการอนุมัติระดับฉบับ |
| อ่านข้อมูล | กรองรายการ รายละเอียด และประวัติตามสิทธิ์ก่อนคืนข้อมูล |
| ประวัติและผลคำสั่ง | บันทึกร่วมธุรกรรมและใช้ตรวจผลเมื่อส่งซ้ำหรือเครือข่ายขาด |

สัญญาคำสั่งต้องระบุคำขอ/ฉบับ รุ่นข้อมูลที่ผู้ใช้เห็น รหัสคำสั่งกันซ้ำ และเหตุผลสำหรับการกระทำที่บังคับ ผู้กระทำ ขอบเขตสิทธิ์ ยอดจริง และชุดกติกาที่ใช้ต้องตรวจจากเซิร์ฟเวอร์ ไม่เชื่อค่าจาก client ส่วนชื่อ endpoint และชนิดตารางจะกำหนดในแผนโดยรักษาสัญญานี้

### 6.3 ธุรกรรมและข้อผิดพลาด

- เปลี่ยนสถานะ ผลอนุมัติ งานที่มอบหมาย ประวัติ และผลคำสั่งกันซ้ำให้ครบในธุรกรรมเดียว ถ้าเกิดข้อผิดพลาดต้องย้อนทั้งหมด
- ตรวจรุ่นข้อมูลก่อนแก้หรืออนุมัติ ไม่เขียนทับฉบับใหม่ ให้ข้อขัดแย้งและโหลดใหม่
- คำสั่งเดิมที่เนื้อหาเดิมไม่สร้างผลซ้ำ รหัสเดิมแต่เนื้อหาต่างต้องถูกปฏิเสธ การเรียกซ้ำยังตรวจสิทธิ์ปัจจุบันก่อนเปิดเผยผล
- ควบคุมความสอดคล้องกับการถอนสิทธิ์/เปลี่ยนตำแหน่งพร้อมกัน ไม่ใช้ผลตรวจสิทธิ์เก่าที่ไม่สัมพันธ์กับจุดบันทึก
- เครือข่ายขาดหลังส่งให้แสดงว่าไม่ทราบผลและตรวจสถานะก่อนลองใหม่ ไม่สรุปว่าล้มเหลวทั้งที่บันทึกแล้ว
- หากบริการสิทธิ์หรือกติกาไม่พร้อม ให้หยุด ไม่อนุญาตโดยปริยาย
- เวลาเหตุการณ์ใช้เซิร์ฟเวอร์ เก็บและแสดงเขตเวลาให้ชัด ไม่ให้เวลาเครื่องผู้ใช้กำหนดสิทธิ์

### 6.4 เกณฑ์รับงาน

| รหัส | สิ่งที่ต้องพิสูจน์เมื่อพัฒนา |
|---|---|
| B01 | ยื่นเอง/ยื่นแทนได้เฉพาะโครงการที่มีสิทธิ์ ผู้รับผิดชอบหนึ่งคนต่อคำขอ ยื่นแทนยืนยันแทนไม่ได้ |
| B02 | ความละเอียด 4/2 ตำแหน่ง การปัดรายบรรทัด ผลรวม และยอดตรงขอบวงเงินถูกต้อง ตรวจเกินความละเอียด/overflow |
| B03 | หมวดมาตรฐานแก้อัตราหรือใช้เหมารวมหลบไม่ได้ หมวดไม่มาตรฐานรองรับสองวิธี |
| B04 | เปลี่ยนเนื้อหาหรือกติกาก่อนยืนยันต้องทบทวนใหม่ หลังส่งตรึงฉบับ และโครงการเฉพาะไม่รับฐานบริษัทใหม่เอง |
| B05 | หัวหน้า → ผู้จัดการโครงการ → ทุกระดับที่จำเป็นตามยอดรวม ไม่มีข้ามขั้น คนละคนในฉบับ |
| B06 | เจ้าของ/ผู้ยื่นแทนอนุมัติไม่ได้ รวมหลายบัญชีของบุคคลเดียวและการถอนแล้วให้สิทธิ์ใหม่ |
| B07 | ผู้อนุมัติเดิมอนุมัติฉบับใหม่ได้ด้วยสิทธิ์ปัจจุบันและผลใหม่ แต่ประวัติข้อห้ามข้ามหน้าที่ทั้งคำขอไม่หาย |
| B08 | เปลี่ยนผู้ดำรงตำแหน่ง/วงเงิน/สิทธิ์แล้วตรวจใหม่ ไล่ระดับได้ถูกต้อง ไม่มีคนเหมาะสม/สายวน/กำกวมให้พัก |
| B09 | หลังแก้โครงสร้างหรือสิทธิ์กลับมารอขั้นเดิมได้ ไม่อนุมัติเองหรือเปลี่ยนผลก่อนหน้า |
| B10 | ส่งกลับทั้งฉบับ มีเหตุผล ส่งใหม่เริ่มทุกขั้นด้วยกติกาที่มีผล ปฏิเสธถาวรและคัดลอกไม่ยกผลเดิม |
| B11 | ถอนเฉพาะผู้รับผิดชอบที่ยังมีสิทธิ์ก่อนอนุมัติครบ ต้องมีเหตุผล ถอนแล้วไม่เปิดกลับ และไม่ถอนหลังอนุมัติครบ |
| B12 | อนุมัติขั้นสุดท้ายชนถอน/คำสั่งซ้ำ/ข้อมูลล้าสมัยมีผลถูกต้องเพียงครั้งเดียว |
| B13 | จำลองล้มเหลวระหว่างบันทึกแล้ว rollback ครบ รวม audit ผลคำสั่ง และผู้รับงาน ไม่มีผลสำเร็จบางส่วน |
| B14 | รายการ รายละเอียด ประวัติ และข้อความผิดพลาดไม่รั่วข้ามสิทธิ์ admin/สมาชิกทีมไม่มีสิทธิ์อัตโนมัติ |
| B15 | หน้าจอไทยแสดงสถานะ ฉบับ ความต่าง เหตุผล และผลล่าสุดตรงจริง รวมเครือข่ายขาด/สิทธิ์ถูกถอน/เปิดหน้าค้าง |
| B16 | การเชื่อม 7A บัญชี MFA โครงสร้างองค์กร และระบบเดิมไม่ถดถอยจากการเพิ่ม 7B |

ใช้เทสต์ระดับหน่วย ฐานข้อมูล/API และหน้าจอตามความเสี่ยง โดยเฉพาะกรณีธุรกรรมต้องทดสอบกับฐานข้อมูล ไม่ใช้ mock อย่างเดียว ตรวจหน้าจอในสภาพแวดล้อม dev พอร์ต 4000 และ production preview พอร์ต 4001 ตามการตั้งค่าโครงการ โดยใช้ HTTPS ตามความจำเป็นของ session ไม่เปลี่ยนมาตรการความปลอดภัยเพื่อให้เทสต์ผ่าน

เมื่อเริ่มพัฒนา ให้เขียนแบบ TDD แยกผู้ลงมือกับผู้ตรวจแต่ละ Task และรัน Test, Build, Lint ครบ บันทึกคำสั่ง ผล และข้อจำกัดจริงก่อนอ้างว่าส่งมอบสำเร็จ รายการข้างต้นเป็นเกณฑ์ในอนาคต ไม่ใช่ผลเทสต์ 7B ที่รันแล้ว

## 8. จุดเชื่อมกับโค้ดเดิมและขั้นถัดไป

ฐานที่ตรวจในการจัดทำเอกสารคือ commit `e20fab17c2c6419dc74ca18f5e9709cf7c911a93` ของงาน 7A ใช้เอกสาร `2026-10-19-module-7a-policy-permissions-design.md` และรายงาน `2026-10-19-module-7a-verification.md` เป็นบริบทของกติกาและ Minor ไม่ใช้ข้อความสถานะเก่าในเอกสารเหล่านั้นยืนยันสถานะ Git ปัจจุบัน

- `FinanceCapabilities.cs` ยังไม่มี `request.create`/`request.delegate` ต้องเพิ่มพร้อมตรวจทุกช่องทางมอบหมายสิทธิ์ ไม่ให้ role ทั่วไปข้ามกระบวนการสามคน
- `SeparationRules.cs` ปัจจุบันรับชุดผู้อนุมัติเดียว ต้องแยกบริบทระดับฉบับกับประวัติระดับคำขอ พร้อมเทสต์ถดถอย ไม่ล้างชุดประวัติเก่าเพื่อเปิดให้อนุมัติใหม่
- `ApprovalLevelEvaluator.cs` เป็นฐานประเมินลำดับจากยอด/กติกา ต้องต่อการเลือกบุคคลและความสัมพันธ์กับบทบาท ไม่ตีความสิทธิ์ `request.approve` หรือวงเงินสูงว่าแทนได้ทุกขั้น
- `PolicyResolver` ต้องใช้ภายในทางเดินที่ตรวจสิทธิ์คำขอแล้ว ไม่ขยายสิทธิ์อ่านหน้าจัดการกติกาให้ผู้ขอทุกคน

เอกสารนี้รวมส่วนที่ 1–5 พร้อมเกณฑ์รับงาน แยกกติกาที่ตรึงไว้จากสิทธิ์ปัจจุบัน และแยกการพักอนุมัติ 7B จากการระงับจ่าย 7C ชัดเจน ไม่มีการอนุมัติพัฒนาจากเอกสารฉบับนี้โดยอัตโนมัติ

ขั้นปัจจุบันคือจัดทำ Implementation Plan ภาษาไทยให้ผู้ใช้ตรวจ การเริ่มพัฒนาต้องรออนุมัติแผนก่อน โดยคงวิธีแยกผู้ลงมือกับผู้ตรวจตามที่ตกลงไว้
