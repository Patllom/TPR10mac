## 1. เป้าหมายและขอบเขตการอนุมัติ

ให้พนักงานลงเวลาออนไลน์ด้วยกล้องและ GPS จากมือถือ ตรวจย้อนหลังตามสิทธิ์ และแก้เวลาที่ขาดหายผ่านหัวหน้าตามสายบังคับบัญชาแล้วจึง HR ระบบต้องรักษาหลักฐานเดิมและไม่ทำให้รูปเก่าเสียเมื่อเปลี่ยนที่เก็บ

ผู้ใช้เลือกพัฒนา Module 6 ก่อน Module 4–5 เต็มชุด แต่ข้อกำหนดนี้ต้องใช้ส่วนจัดเก็บรูปและการอนุมัติขั้นต่ำภายในขอบเขตลงเวลา ไม่ถือว่าทั้งสองโมดูลถูกส่งมอบแล้ว

อ้างอิง [Architecture baseline](2026-09-18-tpr10-module-0-architecture-baseline-design.md), [Module 3 design](2026-09-24-module-3-organization-scope-design.md) และ [Module 3 exit gate](../../architecture/module-3-exit-gate.md)

ความสำเร็จคือบันทึกหนึ่งคู่เข้า–ออกต่อวันทำงานโดยไม่ซ้ำ หลักฐานครบ ตรวจสิทธิ์ที่ API รูปเก่าเข้าถึงได้หลังย้าย storage และเวลามีผลจากคำร้องได้เมื่อผ่านสองขั้นในฉบับเดียวกันเท่านั้น ไม่ใช่ระบบ Payroll หรือการรับรองความถูกต้องของ GPS/ภาพแบบป้องกันการปลอมได้ทั้งหมด

| R02 | วัน–เวลาต้องประทับอยู่ในไฟล์ภาพจริง ไม่ใช่เฉพาะข้อความบนหน้าเว็บ |

| R13 | ระยะแรกยังไม่ลบรูปลงเวลาอัตโนมัติ |
| R14 | พนักงานดูรูปและ GPS ของตนเอง หัวหน้าดู GPS ลูกทีมแต่ห้ามดูรูปลูกทีม HR ดูรูปและ GPS เฉพาะหน่วยงานที่ได้รับมอบหมาย |
| R15 | Admin ไม่ได้สิทธิ์ข้อมูลลงเวลาอัตโนมัติ หัวหน้าดูรูปของตนเองได้ตามสิทธิ์พนักงาน |

## 3. แนวทางสถาปัตยกรรมและทางเลือก

| ทางเลือก | ผลดี | ต้นทุน/ข้อเสีย |
| --- | --- | --- |
| A — ส่วนขั้นต่ำแบบแยกขอบเขตภายใต้ Module 6 (เสนอ) | ส่งมอบงานลงเวลาได้ก่อน และคงรหัสรูป/ประวัติอนุมัติสำหรับต่อยอด | ต้องทำ storage และ approval เฉพาะงานลงเวลาด้วย ไม่ใช่ข้าม dependency ทั้งหมด |
| B — ทำ Module 4–5 เต็มชุดก่อน | ใช้โครงสร้างร่วมกับโมดูลอื่นทันที | ชะลอ Module 6 และเกินความต้องการปัจจุบัน |
| C — เก็บพาธรูปในรายการเวลาและแก้ฐานโดยผู้ดูแล | เริ่มต้นเร็ว | ย้ายรูปยากและข้ามการอนุมัติที่ผู้ใช้ต้องการ จึงไม่เลือก |

เลือก A เป็นข้อเสนอของฉบับนี้ ใช้ ASP.NET Core/PostgreSQL และ Next.js Portal เดิม ไม่เพิ่มบริการ cloud หรือออกแบบ workflow engine ทั่วไป

แบ่งขอบเขตสำหรับจัดแผนย่อยภายหลัง:

1. **โครงสร้างพนักงานและสิทธิ์:** ต้นสังกัด สายบังคับบัญชา และ HR assignment
2. **หลักฐานภาพ:** รับภาพ ประทับเวลา เก็บ/อ่านด้วยสิทธิ์ และย้าย storage
3. **ลงเวลา:** camera/GPS online, pairing, วันทำงาน และ idempotency
4. **คำร้อง:** revision, สองขั้นอนุมัติ, ส่งกลับ, หมดอายุ และปรับ effective time

แต่ละส่วนมี interface และ acceptance ของตน Implementation Plan ต้องแยกงานตามขอบเขตนี้ ไม่สร้างไฟล์ service เดียวดูแลทุกอย่าง และหากขนาดงานมากเกินรอบเดียวให้เสนอแบ่งแผนย่อยก่อนเริ่ม

## 4. สิ่งที่เปลี่ยนจาก baseline และยังไม่ทำ

- ส่วนภาพขั้นต่ำแทนการรอ File module เต็มชุด และ approval เฉพาะคำร้องแทนการรอ Workflow module เต็มชุด
- ภาพรับรองเวลาต้องประทับโดยเซิร์ฟเวอร์ แทนการเชื่อ overlay จาก client ตาม baseline เดิม; client แสดง preview ได้แต่ไม่เป็นหลักฐานเวลา
- เปิดเฉพาะ online ไม่ทำ offline grant, queue หรือ sync แม้ baseline ระบุแนวทางในอนาคต
- ไม่มี geofence, Payroll, OT/สาย/ขาดงานอัตโนมัติ, ตารางกะกลางคืน, facial recognition หรือ liveness detection
- ไม่มี generic file manager, cloud storage adapter, email/Gmail delivery, delegation/escalation อัตโนมัติ หรือ export รูป/GPS จำนวนมากในรอบนี้
- มี inbox และสถานะใน Portal; การอนุมัติไม่ต้องพึ่งการส่งอีเมล
- ไม่แก้ Landing Page สาธารณะให้เข้าถึงข้อมูลภายใน และไม่เปลี่ยนสิทธิ์เดิมของ Module 2–3 ให้กว้างขึ้น

## 5. ข้อมูลบุคลากรและการเชื่อม Module 3

จากโค้ดจริง Module 3 มี Workspace, Department, Project, Site และ exact scope assignments แต่ยังไม่มี employee membership, reporting line หรือ HR assignment จึงต้องเพิ่ม ไม่ใช้ Department เป็น security scope เดิมโดยปริยาย

ข้อเสนอ:

- `EmployeeMembership`: user, workspace, department และช่วงเวลาที่มีผล พนักงานมีต้นสังกัดหลักหนึ่งแห่ง ณ เวลาหนึ่ง ไม่มีช่วงทับซ้อน
- `ReportingLine`: พนักงานกับผู้บังคับบัญชาโดยตรงและช่วงเวลาที่มีผล ต้องไม่ชี้ตนเอง ไม่วนวง และอ้างสมาชิกที่ถูกต้อง
- หัวหน้าแผนกมีผู้บังคับบัญชาของตนเองใน ReportingLine จึงไม่ส่งคำร้องกลับมาหาตัวเอง
- `HrAssignment`: ผู้ใช้กับคู่ workspace/department ที่ได้รับอนุญาตอย่างชัดเจน มีช่วงเวลาที่มีผล ไม่ใช้ global Admin role เป็นทางผ่าน
- ใช้ capability เฉพาะงาน เช่น `attendance:record`, `attendance:team-read`, `attendance:hr-read`, `attendance:approve-supervisor`, `attendance:approve-hr`, `attendance:directory-manage`, `attendance:storage-manage` ชื่อเหล่านี้เป็นข้อเสนอ ไม่ใช่รายการที่มีอยู่ในโค้ดปัจจุบัน
- การลงเวลาต้องเป็นเจ้าของบัญชีเอง มี employment active และ exact Site assignment ที่อนุญาตจริง ไม่รับ userId จาก body เพื่อแทน actor
- ห้ามนำ capability สำหรับ scope-probe จาก Module 3 มาใช้กับข้อมูลลงเวลาจริง
- Directory/storage management ไม่ให้สิทธิ์อ่านรูปหรือ GPS; การมอบหมายสิทธิ์อนุมัติของตัวเองต้องถูกปฏิเสธและมี audit

## 6. ตารางสิทธิ์ข้อมูลและผู้อนุมัติ

| ผู้กระทำ | ขอบเขตอ่านรายการเวลา | รูป | GPS | พิจารณาคำร้อง |
| --- | --- | --- | --- | --- |
| พนักงาน | ของตนเอง | ได้ | ได้ | ยื่น/แก้ฉบับของตน ไม่อนุมัติเอง |
| หัวหน้า | ลูกทีมที่สัมพันธ์ตามนโยบายสายบังคับบัญชา | ไม่ได้ | ได้ | ขั้นหัวหน้าตาม route ของคำร้อง |
| HR | หน่วยงานที่ได้รับมอบหมาย | ได้ | ได้ | ขั้นสุดท้าย หลังขั้นหัวหน้าผ่าน |
| Admin | ไม่มีสิทธิ์ข้อมูลธุรกิจจากตำแหน่ง Admin อย่างเดียว | ไม่ได้อัตโนมัติ | ไม่ได้อัตโนมัติ | ไม่ได้อัตโนมัติ |

สิทธิ์ own-record ใช้กับทุกบทบาท หากหัวหน้าดูรายการตนเองจึงดูรูปได้ หากคนเดียวมี HR assignment ที่ถูกต้องด้วย สิทธิ์ดูรูปลูกทีมเกิดจาก HR grant เท่านั้น ไม่ใช่เพราะเป็นหัวหน้า ต้องแสดงและ audit ฐานสิทธิ์ที่ใช้

ข้อเสนอเรื่องข้อมูลย้อนหลัง: บันทึกต้นสังกัด ณ วันทำงานลง snapshot ที่แก้ไม่ได้ ใช้ current reporting relation ร่วมกับสิทธิ์หน่วยงานประวัติสำหรับการอ่านลูกทีม ไม่ให้หัวหน้าใหม่อ่านประวัติก่อนย้ายหน่วยโดยอัตโนมัติ HR อ่านตาม department snapshot และ current HR assignment ไม่สืบทอดสิทธิ์เมื่อถูกถอน

คำว่า “ลูกทีม” เสนอให้เริ่มจากผู้ใต้บังคับบัญชาโดยตรงเท่านั้น ไม่เปิดทั้งต้นไม้โดยปริยาย ผู้บังคับบัญชาระดับถัดไปได้ข้อมูลที่จำเป็นของคำร้องที่ส่งถึงตนผ่าน workflow grant ไม่ได้สิทธิ์อ่านทั้งองค์กร

ระบบอนุมัติใช้คนต่างกันสองคน ผู้ยื่น คนอนุมัติขั้นแรก และคนอนุมัติขั้นสุดท้ายต้องไม่เป็นคนเดียวกัน HR หลายคนมีสิทธิ์ใน queue ได้ แต่ใช้ version/transaction ให้เกิดผู้อนุมัติสำเร็จเพียงคนเดียว

รายการ รูป thumbnail download และ GPS ทุกช่องทางตรวจสิทธิ์ที่ API ซ้ำ หัวหน้าที่เดา fileId ได้ก็อ่านรูปไม่ได้ API ห้ามส่งรูป/URL/ตำแหน่งที่เก็บให้ client ของหัวหน้าแล้วเพียงซ่อน UI

## 7. ลงเวลาและวันทำงาน

### 7.1 การนับหนึ่งคู่

- เก็บ instant เป็น UTC และใช้ `Asia/Bangkok` แปลงวันทำงาน/แสดงผล ไม่ใช้ timezone ของเครื่องผู้ใช้
- วันทำงานของคู่คือวันที่เข้า หนึ่ง `userId + workDate` มีคู่ได้หนึ่งคู่ทั่วระบบ ไม่รีเซ็ตจำนวนเมื่อเปลี่ยน Site หรือ Workspace
- แต่ละ user มีรอบเปิดได้ไม่เกินหนึ่งรอบพร้อมกัน ใช้ constraint/lock ที่ฐานข้อมูล ไม่อาศัยปิดปุ่มใน UI
- เข้าและออกต้องมี Site ของเหตุการณ์นั้นที่ตนมี exact assignment การมีสิทธิ์ Site ตอนเข้าไม่ให้สิทธิ์ออกที่ Site อื่น
- ข้อเสนอให้รองรับต่าง Workspace ด้วยเมื่อผู้ใช้มี exact assignment ทั้งสอง แต่การอ่านคู่ใช้ employment snapshot ไม่ทำให้ HR ของ Site ปลายทางได้อ่านทั้งคู่โดยอัตโนมัติ ต้องยืนยันนโยบายนี้ก่อน implementation
- เวลาออกต้องหลังเวลาเข้า ถ้าออกข้ามวันยังเป็นคู่ของวันที่เข้า เช่น 25 ก.ย. 08:00 → 26 ก.ย. 01:00 แล้วจึงเปิดคู่วันที่ 26 ก.ย. ได้

### 7.2 ข้ามวันจริงกับลืมออกงาน

ข้อมูลเพียง “ข้ามเที่ยงคืน” ไม่พอระบุว่าลืมออกงาน เพราะผู้ใช้อนุญาตทำงานต่อเนื่องข้ามวันด้วย

ข้อเสนอรอตรวจ: เมื่อออกข้ามวัน ให้พนักงานยืนยันว่าเป็นการทำงานต่อเนื่องจริง แล้วบันทึกเวลาออกปัจจุบันพร้อมกล้อง/GPS หากระบุว่า “ลืมลงเวลา” ต้องเข้าคำร้อง ห้ามกรอกเวลาออกย้อนหลังใน flow ปกติ ไม่เดาว่าลืมจากจำนวนชั่วโมงและยังไม่ตั้งเพดานชั่วโมงที่ผู้ใช้ไม่ได้กำหนด

กรณีมีรอบเก่าค้างและไม่ใช่งานต่อเนื่อง ต้องปิดด้วยคำร้องก่อนเริ่มรอบใหม่ตามกติกาที่ตกลง ซึ่งอาจทำให้วันถัดไปต้องยื่นคำร้องด้วย ผลกระทบนี้ต้องยอมรับใน spec หรือปรับนโยบายก่อนเขียนโค้ด

## 8. กล้อง GPS และเวลาในภาพ

1. ผู้ใช้เลือก Site และเปิดกล้องผ่าน browser camera API ไม่มี file-picker หรือ drag/drop upload ในหน้าลงเวลา
2. ขอ GPS ใหม่ เก็บ latitude, longitude, accuracyMeters และเวลาที่รับตำแหน่ง ไม่ใช้ EXIF เป็นแหล่ง GPS ที่เชื่อถือได้
3. ไม่มีรัศมีบังคับ พิกัดที่ได้ต้องมีช่วงค่าถูกต้องและ accuracy เป็นค่าบวก ข้อเสนอใช้ GPS sample อายุไม่เกิน 60 วินาทีก่อนกดส่ง; accuracy ต่ำให้แสดงคำเตือนและบันทึกค่า ไม่สร้าง geofence โดยอ้อม
4. ถ่ายภาพจาก camera stream แสดงภาพให้ยืนยัน เมื่อออกจากหน้า/เปลี่ยนบัญชีให้หยุด stream และทิ้งภาพร่างใน memory ไม่เก็บภาพ/GPS ใน localStorage หรือ cache ถาวร
5. ก่อน capture ขอ challenge อายุสั้นที่ผูกกับ user/session, action และ Site ข้อเสนออายุ 120 วินาที ใช้ได้ครั้งเดียวและผูกกับ idempotency key; หมดอายุต้องถ่ายใหม่
6. API ตรวจ session, CSRF, assignment, challenge, payload และกำหนด `occurredAtUtc` จากเวลาเซิร์ฟเวอร์เมื่อรับคำขอที่ผ่านการตรวจ เก็บ device capture time แยกเป็นข้อมูลประกอบ ไม่ใช้คำนวณเวลาอย่างมีอำนาจ
7. Server decode ภาพ จำกัด bytes/pixels ตัด metadata ที่ไม่จำเป็น แล้วประทับวันที่–เวลาไทยและประเภทเข้า/ออกลง pixels จริง ใช้ instant เดียวกับ event เช่น `25/09/2026 08:30:15 (UTC+7) — เข้า` เก็บ checksum ของไฟล์สุดท้าย
8. timestamp บนภาพหมายถึงเวลาที่ระบบรับลงเวลา ไม่อ้างว่าเป็นเวลาชัตเตอร์ที่พิสูจน์ได้ การอัปโหลดล่าช้าต้องเห็นเวลาต่างกันใน metadata
9. เก็บเฉพาะไฟล์ที่ผ่านประทับและตรวจแล้วเป็นหลักฐานถาวร ภาพ upload ต้นทางเป็น staging ไม่เปิดอ่านและไม่เก็บเพิ่มโดยไม่มีเหตุผล

ข้อเสนอขีดจำกัดเริ่มต้น: JPEG/PNG ที่ decode ได้จริง ไม่เกิน 10 MiB และ 20 ล้านพิกเซลต่อภาพ แปลงเป็น JPEG ที่อ่านวันเวลาได้ ไม่มี SVG/ไฟล์ executable ตรวจ signature ไม่เชื่อ MIME จาก client ตัวเลขนี้ต้องได้รับอนุมัติและทดสอบบนมือถือก่อนใช้จริง

Camera-only เป็นข้อบังคับ UX และ challenge ช่วยลด replay แต่เว็บไม่สามารถรับรองว่าไม่มี virtual camera, GPS spoofing หรือการถ่ายภาพจากจอ ห้ามอ้างเป็น biometric/liveness verification

## 9. การจัดเก็บและย้ายรูป

### 9.1 สัญญาที่ไม่ผูกพาธ

- Event อ้าง `evidenceId` ถาวร ไม่เก็บ UNC path, drive letter หรือ public URL เป็นตัวอ้างหลัก
- `EvidenceObject` เก็บเจ้าของ เหตุการณ์ ชนิดข้อมูล checksum ขนาด และสถานะ; `EvidenceLocation` แยก objectId, storageId, relativeObjectKey, checksum และสถานะสำเนา
- `StorageLocation` แต่ละรุ่นมี ID ถาวร, adapter `local-folder`/`nas-mounted-folder`, root configuration reference และสถานะอ่าน/รับไฟล์ใหม่ ห้ามแก้ root ของ storageId ที่มีไฟล์แล้วให้ชี้อีกที่
- NAS mount ที่ฝั่งเซิร์ฟเวอร์ด้วย service identity สิทธิ์ขั้นต่ำ ไม่ส่ง credential หรือ mount path ให้ browser ไม่เข้าถึง SMB จาก browser
- Root/credential เป็น protected deployment configuration ไม่ใส่ secret ในฐานทั่วไปหรือ Git; หน้า Admin เลือกได้เฉพาะ location ที่ Operations จัดเตรียม ไม่รับพาธอิสระจากเว็บ
- Object key สร้างโดยเซิร์ฟเวอร์ ไม่มีชื่อผู้ใช้/ข้อมูลส่วนตัว ป้องกัน traversal, symlink escape และไฟล์ชื่อชนกัน; รูปไม่อยู่ใต้ webroot และไม่มี anonymous static access

### 9.2 เปลี่ยนปลายทางรูปใหม่

ลงทะเบียน location ใหม่ ตรวจ write/read/checksum readiness แล้วเปลี่ยน active write target แบบ versioned และ audit ไฟล์ที่กำลังรับ pin storage version ของตน รูปเก่ายังอ่านผ่าน location เก่า ไม่ rewrite ทุก event และไม่ fallback เขียนผิดที่อย่างเงียบ ๆ เมื่อ NAS ล่ม

### 9.3 ย้ายรูปเก่า

`วางแผน → คัดลอก → ตรวจขนาด/Checksum → เปิดใช้สำเนาใหม่แบบ atomic → ตรวจการอ่าน → เก็บต้นฉบับไว้`

- งานย้ายมี manifest, progress, resumable/idempotent ต่อ object และ retry แบบจำกัด เปลี่ยน metadata หลังอ่านไฟล์ปลายทางและ checksum ตรงเท่านั้น
- ระหว่างคัดลอกอ่านต้นทางได้ หลังเปลี่ยน active location ยังเก็บต้นทางที่ตรวจแล้วเป็น fallback ตามการตั้งค่าและมี audit ไม่สลับไปอ่านข้อมูลไม่ตรง checksum
- หาก crash หลัง copy แต่ก่อน metadata commit ให้ reconcile สำเนาด้วย objectId/checksum ไม่สร้าง event หรือ fileId ใหม่
- ไม่ลบต้นฉบับอัตโนมัติในระยะแรก การเลิกใช้ NAS/โฟลเดอร์เก่าทำได้เมื่อไม่มี active reference และ restore/read verification ผ่าน พร้อมอนุมัติแยก
- หากถอดที่เก็บเก่าก่อนย้ายสำเร็จ รูปเก่าอาจอ่านไม่ได้ ระบบไม่สามารถรับประกันข้อมูลที่ต้นทางสูญหาย จึงต้องมี backup ทั้งไฟล์และ metadata
- แจ้งเตือนพื้นที่เหลือ/เขียนไม่ได้/ไฟล์หาย โดยไม่เปลี่ยนรูปที่หายเป็นผลสำเร็จหรือสร้างหลักฐานใหม่แทน

## 10. Transaction และการกู้คืนความล้มเหลว

Filesystem กับ PostgreSQL ไม่ใช่ transaction เดียวกัน ห้ามอ้าง atomic commit ข้ามทั้งสองโดยไม่มี protocol

ข้อเสนอ: รับไฟล์ใน staging ส่วนตัว → decode/ประทับ/checksum → durable finalize เป็น object immutable ที่ยังไม่เปิดอ่าน → transaction ตรวจสิทธิ์/สถานะซ้ำและสร้าง event + evidence reference + audit → commit แล้วจึงตอบสำเร็จ

ถ้า storage ไม่สำเร็จห้ามสร้างรายการลงเวลาสำเร็จ ถ้า database/audit ไม่สำเร็จห้ามเผยแพร่ไฟล์ที่ finalize แล้ว โดยทำเครื่องหมายเพื่อ reconcile เป็น orphan ไม่มี business reference การเก็บกวาด staging/orphan ที่ยืนยันว่าไม่เคยผูก event ไม่เท่ากับการลบหลักฐานที่ตกลงว่าไม่ลบ ต้องมี grace period และรายงานก่อนเปิดใช้ cleanup

Idempotency key ผูก actor/action และ hash ของ payload คำขอเดิมคืนผลเดิม คีย์เดิมแต่ payload ต่างตอบ conflict การตรวจสถานะหลัง network timeout ต้องใช้ key เดิม ไม่ถ่าย/สร้างรายการใหม่ทันที

ใช้ lock ต่อพนักงานร่วมกันระหว่าง check-in/out กับอนุมัติแก้ไขขั้นสุดท้าย ตรวจ version ของคู่เวลาและสิทธิ์ปัจจุบันอีกครั้งก่อน commit ป้องกันคำร้องและการลงเวลาสดเขียนทับกัน

## 11. คำร้องแก้ไขเวลา

### 11.1 ข้อมูลและการรักษาหลักฐาน

คำร้องระบุวันทำงาน ชนิดเวลาที่ขาด/ต้องแก้ ค่าเวลาที่เสนอ Site ที่เกี่ยวข้อง และเหตุผล มี before-state/version ของคู่เวลา โดยไม่บังคับแนบรูปย้อนหลัง รูป/GPS เดิมไม่แก้หรือเขียนทับ และเหตุการณ์เพิ่มย้อนหลังไม่มีภาพ/GPS ที่สร้างให้เหมือน capture จริง

แยก original immutable events จาก effective attendance หลังอนุมัติ หากแก้เวลาออกจากภาพเดิม เวลาในภาพยังเป็นเวลาเดิม แสดงป้าย “เวลาที่อนุมัติแก้ไข” และเชื่อมคำร้อง ห้ามประทับภาพเก่าใหม่ให้ตรงข้อมูลที่แก้

ขอบเขตเสนอให้รองรับเข้าอย่างเดียว ออกอย่างเดียว ขาดทั้งคู่ และแก้เวลาที่มีอยู่ แต่ทุกชนิดผ่านสองขั้น ห้ามแก้เจ้าของบัญชี ถ้าแก้วันทำงาน/Site ต้องตรวจ unique day, ลำดับเวลา, รอบเปิด และ assignment ประวัติที่ตรวจสอบได้; ไม่มีหลักฐาน assignment ให้ค้าง ไม่ให้ HR เลือก Site ตามอำเภอใจ

### 11.2 State machine

`Draft → PendingSupervisor → PendingHr → Approved`

จาก PendingSupervisor หรือ PendingHr ส่งกลับเป็น `Returned` พร้อมเหตุผลได้ พนักงานแก้เป็น revision ใหม่แล้วส่ง `PendingSupervisor` เสมอ ผลอนุมัติฉบับก่อนหน้าไม่ใช้กับฉบับใหม่ หากเลยกำหนดใน Returned เป็น `Expired` และส่งต่อไม่ได้ เก็บประวัติครบ

- ขณะ pending ห้ามพนักงานแก้ body ของ revision ที่ผู้อนุมัติกำลังอ่าน
- ผู้อนุมัติทำ approve หรือ return พร้อม version ไม่แก้เวลาแทนพนักงานเงียบ ๆ; ข้อความ “แก้ไขหรืออนุมัติ” ในขอบเขตนี้ใช้การส่งกลับแก้ไขและอนุมัติค่าที่ร้องขอ
- ไม่เพิ่ม reject-and-close เพราะผู้ใช้เลือกส่งกลับจนผ่าน ไม่เพิ่มการอนุมัติแบบข้ามขั้น
- มี active request ได้หนึ่งเรื่องต่อ user/workDate เพื่อป้องกันคำร้องซ้อนแก้รายการเดียวกัน
- เมื่ออนุมัติขั้นสุดท้าย ตรวจค่าที่ขอ, baseline version, constraints และ audit ใน transaction เดียว ถ้ามีรายการเปลี่ยนระหว่างรอให้ conflict ไม่ปรับเวลา ให้ส่งกลับทบทวน

### 11.3 Routing

เมื่อส่งแต่ละ revision ให้ผูก snapshot ต้นสังกัด สายหัวหน้า และ HR unit ของคำร้อง ใช้หัวหน้าตามสายบุคลากร ไม่ยึด Site ที่ออกงาน หา route ไม่ครบ/วน/self-approval ให้ไม่รับ submission พร้อมข้อความแก้ directory

Snapshot รักษาประวัติว่าใครควรพิจารณา แต่ไม่ให้สิทธิ์คนที่ถูกถอน ทุก action ต้องตรวจ active identity, capability, recent MFA และ assignment ปัจจุบัน ถ้าหัวหน้าย้าย/ลาออกให้คำร้องค้างเพื่อผู้มีสิทธิ์จัด route ใหม่แบบ audit และเริ่มตรวจจากขั้นแรก ไม่ข้ามไป HR โดยอัตโนมัติ

ผู้ยื่นที่เป็น HR ยังต้องผ่านหัวหน้าและ HR คนอื่นในหน่วยงานที่มีสิทธิ์ หากไม่มีคนที่สองให้หยุด ไม่ให้ self-approval หรือ Admin bypass

### 11.4 กำหนด 7 วัน

ข้อเสนอวิธีนับที่ต้องรับรองในฉบับนี้: วันปฏิทินตาม Asia/Bangkok รวมเสาร์อาทิตย์ ไม่ใช่ 168 ชั่วโมง

- ครั้งแรก วันทำงาน D ส่งได้ถึงก่อน 00:00 ของ D+8 (รวมตลอด D+7) เช่น 25 ก.ย. → ถึง 2 ต.ค. 23:59:59… การสร้าง Draft ไม่สงวนสิทธิ์ ต้อง submit สำเร็จทันกำหนด
- ส่งกลับวันที่ R ส่งฉบับแก้ไขได้ถึงก่อน 00:00 ของ R+8 เริ่มใหม่ทุกครั้งที่ส่งกลับ
- ช่วง PendingSupervisor/PendingHr ไม่หมดอายุเพราะพนักงานไม่ใช่ผู้ดำเนินการ ไม่มี approval SLA ที่ตั้งขึ้นเอง
- คำร้อง Returned พ้น deadline เป็น Expired แม้ background job ยังไม่ทำงาน API ต้องตรวจเวลาและปฏิเสธทันที
- การแก้แล้วส่งทันเวลาเปิด revision ใหม่และหัวหน้าต้องอนุมัติใหม่ แต่การบันทึก Draft ไม่ต่ออายุ
- ไม่ให้สร้างคำร้องใหม่เพื่อหลบวันครบกำหนดเดิม คำร้อง expired ยังอ่านประวัติได้ กรณีผิดพลาดหลังหมดอายุไม่มี bypass ใน release นี้ ต้องจัดนโยบายยกเว้นแยกก่อนเปิดใช้จริง

## 12. แบบจำลองข้อมูลเชิงแนวคิด

| กลุ่ม | ข้อมูลหลัก/ข้อบังคับ |
| --- | --- |
| บุคลากร | membership/reporting lines/HR assignments แบบมีช่วงเวลาและ version; ห้าม cycle/self-manager |
| AttendanceDay | userId + workDate unique, employment snapshot, effective in/out, version; รอบเปิดต่อ user ไม่เกินหนึ่ง |
| AttendanceEvent | ประเภทเข้า/ออก, actor, UTC/server time, device time, exact Site tuple, GPS/accuracy, evidenceId, source `live` หรือ `approved-correction` |

| CaptureChallenge/Operation | session/actor/action/Site binding, expiry, one-time use, idempotency key/hash และผลคำขอ |
| CorrectionRequest/Revision | เจ้าของ, workDate, immutable proposed values/reason, baselineVersion, deadline และ status |
| ApprovalAction | request/revision/step, actor, outcome/reason, UTC, routing snapshot; uniqueness กันอนุมัติซ้ำ |
| AttendanceAdjustment | effective change ที่ผูก approved revision, before/after และผู้อนุมัติ; ไม่เขียนทับ evidence เดิม |

## 13. หน้าจอและ API ที่เสนอ

หน้าภายใน `/portal/attendance`: ลงเวลา/สถานะรอบเปิด/ประวัติตนเอง; `/corrections`: คำร้องและ revisions; `/team`: รายการลูกทีมไม่มีภาพ; `/hr`: รายการหน่วยงานพร้อมรูปตามสิทธิ์; `/approvals`: queue หัวหน้าและ HR แยกขั้น มีเหตุผลส่งกลับและเวลาครบกำหนด

หน้า directory และ storage เป็นงานผู้มีสิทธิ์เฉพาะ มีการตรวจ version และ audit ไม่เปิดแก้จากผู้ใช้ทั่วไป ทุกหน้าอยู่หลัง session protection เดิม

กลุ่ม API เสนอภายใต้ `/api/v1/attendance`:

- POST capture-challenges และ POST check-ins/check-outs พร้อม idempotency
- GET current, mine, team, hr พร้อม pagination/filter ที่บังคับขอบเขตก่อน query
- GET evidence/{id} ผ่าน authorization เฉพาะหลักฐาน ไม่มี public file URL และไม่ใช้ signed URL อายุยาวที่ถอนสิทธิ์ไม่ได้
- POST corrections, GET corrections/{id}, POST revisions/submit, supervisor-approve, hr-approve และ return พร้อม expectedVersion
- APIs บุคลากร/HR assignment/storage registration/write-target/migration แยก permission โดยเฉพาะ ไม่รวมไว้ใน generic admin bypass

ชื่อ endpoint เป็นข้อเสนอเพื่อแบ่งความรับผิดชอบ Implementation Plan ต้องล็อก DTO/route/status และ OpenAPI ทุก operation ก่อนลงมือ รวม field omission สำหรับหัวหน้า ไม่ส่งรูปหรือ storage locator กลับมา

401 ไม่มี session; 403 ขาดสิทธิ์/MFA/CSRF; 404 ไม่พบหรือซ่อน resource ข้ามขอบเขต; 409 version/วันซ้ำ/รอบค้าง; 400 ข้อมูลหรือ deadline ไม่ผ่าน; 413 ไฟล์ใหญ่; 415 ชนิดไฟล์ไม่รองรับ; 429 rate limit พร้อมเวลารอ; 503 storage/DB/audit ไม่พร้อม ห้ามแกล้ง redirect เป็น logout ทุกครั้งที่ dependency ล่ม

## 14. ความปลอดภัยและการปฏิบัติงาน

- ใช้ HTTPS same-origin, cookie/session, CSRF และ MFA เดิม ไม่ลดรหัสผ่านหรือ MFA เพื่อ demo
- หัวหน้า/HR ใช้ recent MFA สำหรับการอนุมัติและการอ่านข้อมูลละเอียดตาม policy ที่กำหนดใหม่ ห้ามกำหนดให้มีแต่ MFA แล้วข้าม capability/scope
- ห้าม cache รูป/GPS แบบ public; no-store, private DOM invalidation และ cancellation เมื่อเปลี่ยนบัญชี/สิทธิ์ตามบทเรียน Module 3
- เพิกถอนสิทธิ์ต้องมีผลต่อ API อ่านรูปและ action ที่กำลังรอ lock ไม่ให้ snapshot คงอำนาจเดิม
- NAS outage ไม่ทำให้เวลา/รูปถูกบันทึกครึ่งเดียว ผู้ใช้เห็นผลลัพธ์ที่ retry/ตรวจสถานะได้ ไม่ retry mutation ด้วย key ใหม่อัตโนมัติ
- ไม่มีการลบหลักฐานอัตโนมัติในระยะแรก แต่ต้องมี capacity alert และ backup/restore drill ที่ทดสอบไฟล์กับฐานข้อมูลร่วมกัน checksum ไม่ใช่ backup
- ก่อน Production ต้องกำหนดผู้รับผิดชอบข้อมูลภาพ/พิกัด การแจ้งพนักงาน การเข้าถึง และนโยบายเก็บรักษาอย่างเป็นทางการ ไม่อ้างว่าการไม่ลบเป็นการผ่านข้อกำหนดกฎหมายโดยอัตโนมัติ

## 15. Acceptance และหลักฐานที่ต้องมี

| กรณี | ผลที่ต้องพิสูจน์ |
| --- | --- |
| กล้อง/GPS | ปฏิเสธสิทธิ์ เปิดไม่ได้ พิกัดหาย/เก่า หรือภาพไม่ครบ ไม่สร้าง event สำเร็จ; ไม่มี file-picker |
| เวลาในภาพ | วันเวลาอ่านได้จากไฟล์ภาพที่ดาวน์โหลดจริง ตรงกับ server event และ timezone รวมกรณีเที่ยงคืน |
| เข้า/ออก | วันเดียวกดซ้ำ/หลายแท็บได้หนึ่งคู่; ออกก่อนเข้าไม่ได้; retry key เดิมไม่ซ้ำ |
| ข้ามวัน/เปลี่ยน Site | คู่ผูกวันที่เข้า ออกอีก Site ได้เฉพาะมี assignment; ไม่เปิดสิทธิ์ implicit parent/sibling |
| ขอบเขตภาพ | พนักงานอ่านของตน หัวหน้าอ่าน GPS แต่รูป/thumbnail/download โดนปฏิเสธ; HR ข้ามหน่วยไม่ได้; Admin ไม่มี bypass |
| Directory | ไม่มีหัวหน้า, วนวง, หัวหน้ายื่นเอง, HR ยื่นเอง และไม่มีผู้อนุมัติคนที่สอง ไม่ข้ามขั้น |
| คำร้อง | หัวหน้าก่อน HR, ห้าม self/same-person two-step, revision ใหม่ล้างผลอนุมัติเก่า; concurrent actions มีผู้ชนะหนึ่ง |
| 7 วัน | ขอบเขต D+7/R+7 ก่อน/ตรง/หลังเที่ยงคืน; weekend; Draft ไม่ต่ออายุ; ReturnedExpired ส่งต่อไม่ได้ |
| หลักฐานเดิม | อนุมัติแก้แล้วรูป/GPS/เวลาเดิมในภาพไม่เปลี่ยน รายการย้อนหลังไม่มีหลักฐานปลอม |
| Storage | local และ NAS; เปลี่ยน write target รูปเก่ายังอ่าน; ย้ายระหว่างอ่าน; crashทุกช่วง; checksumไม่ตรงไม่cutover |
| Failure atomicity | storage/audit/DB ล่มไม่ให้ผลสำเร็จครึ่งเดียว; reconcile orphan ไม่ลบภาพที่มี business reference |
| Revocation | ถอนสิทธิ์/disable user ระหว่างอ่านภาพหรืออนุมัติไม่ส่งข้อมูลหลัง authorization ที่หมดอายุ |
| Browser | mobile camera/GPS บนอุปกรณ์จริง รวม portrait/landscape, กลับแท็บ, เปลี่ยนบัญชี, keyboard และข้อความ error |
| Regression | Module 1–3, Landing Page, Test/Build/Lint และ backend format ผ่าน พร้อม OpenAPI/permission matrix และ review |

ชุด automated mock ไม่แทน camera/GPS บนมือถือจริง และการ mount โฟลเดอร์จำลองไม่แทน NAS outage/permission/restore บน deployment จริง ต้องแยกหลักฐานทั้งสองชนิด

## 16. ข้อเสนอที่ได้รับการยืนยันใน written-spec review

ข้อกำหนด R01–R15 มาจากข้อตกลงผู้ใช้ ส่วนรายการต่อไปนี้ได้รับอนุมัติพร้อม written Spec แล้ว คำว่าเสนอในเนื้อหาเดิมบอกที่มา ไม่ใช่สถานะรออนุมัติ:

1. เลือกทาง A และแบ่งแผนเป็นบุคลากร/ภาพ/ลงเวลา/คำร้อง ไม่ทำ Module 4–5 เต็มชุด
2. นับ 7 วันเป็นวันปฏิทินถึงสิ้นวันตามเวลาไทย; อายุ pending ไม่หมดเพราะการรอผู้อนุมัติ
3. ใช้การยืนยันงานต่อเนื่องเมื่อออกข้ามวัน แยกจากลืมออกงานโดยไม่มีชั่วโมงตัดอัตโนมัติ และยอมรับว่ารอบค้างบล็อกรอบใหม่จนคำร้องอนุมัติ
4. เริ่มสิทธิ์ลูกทีมที่ direct reports และจำกัดประวัติข้ามต้นสังกัด; ใช้ membership snapshot และ current grants ไม่เปิดสิทธิ์ย้อนหลังโดยปริยาย
5. HR และหัวหน้าต้องเป็นคนต่างกัน; ไม่มีคน/สิทธิ์ครบให้ค้าง ไม่ยกเว้นด้วย Admin
6. ต่าง Site รวมต่าง Workspace ได้เฉพาะมี assignment; สิทธิ์อ่านใช้ต้นสังกัดของวันทำงาน ไม่ขยายตาม Site
7. เวลาประทับเป็นเวลาเซิร์ฟเวอร์รับคำขอ ไม่ใช่การรับรองชัตเตอร์; GPS freshness 60 วินาที, challenge 120 วินาที และภาพ 10 MiB/20 ล้านพิกเซลเป็นค่าเริ่มต้นเสนอ
8. ไม่มีช่องทางแก้ตรงเมื่อคำร้องหมดอายุ และไม่สร้าง email/offline/export เพิ่มในรอบนี้

หลังอนุมัติเอกสารนี้จึงจัดทำ Implementation Plan ภาษาไทย พร้อม migration strategy, interface/DTO, acceptance tests และลำดับแผนย่อย ก่อนขออนุมัติเริ่ม implementation แยกอีกครั้ง

## 17. ผลตรวจทานเอกสาร

ตรวจเทียบข้อตกลง R01–R15 กับกฎเวลา/รูป/คำร้อง/สิทธิ์แล้ว แยกข้อเสนอเพิ่มเติมไว้ในข้อ 16; ไม่ถือโค้ด Department ปัจจุบันว่ามี reporting line แล้ว; ไม่ใช้ technical probe เป็นธุรกิจ; แยกการอนุมัติ spec ออกจากการอนุมัติ Production

เอกสารนี้ไม่มี credentials, MFA secret, รูป หรือพิกัดจริง ไม่มีการแก้ source code/ฐานข้อมูล/Preview และไม่ได้อ้างผล Test/Build/Lint ของ implementation ที่ยังไม่เริ่ม
