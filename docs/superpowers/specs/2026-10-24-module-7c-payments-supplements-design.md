# เอกสารออกแบบ Module 7C การจ่ายเงินทดรองและคำขอส่วนเพิ่ม

วันที่: 24 ตุลาคม 2569 (2026-10-24)

สถานะ: ผู้ใช้อนุมัติเอกสารฉบับรวมและ Implementation Plan แล้วเมื่อ 24 ตุลาคม 2569 อนุญาตเริ่ม Task 1 โดยแยกผู้ลงมือกับผู้ตรวจ ผลดำเนินงานติดตามในแผนและรายงานตรวจสอบ ไม่ถือว่าทั้ง Module เสร็จแล้ว

## สรุปสำหรับผู้ตรวจ

7C รับคำขอที่อนุมัติครบจาก 7B มาจัดการงวดจ่าย ตรวจการเงิน กันวงเงิน และบันทึกผลจ่ายพร้อมหลักฐาน การตรวจผ่านและการกันวงเงินไม่เท่ากับจ่ายเงินจริง ระยะแรกเจ้าหน้าที่โอนเงินหรือจ่ายเงินสดภายนอกระบบ ไม่มีการสั่งโอนผ่านธนาคารอัตโนมัติ

วงเงินคำขอเดิมปรับได้เฉพาะก่อนมีการจ่ายเงินจริง โดยยืนยันและอนุมัติใหม่ หากจ่ายแล้วแม้บางส่วน ต้องสร้างคำขอใหม่เฉพาะส่วนเพิ่ม เชื่อมคำขอเดิม ใช้โครงการและผู้รับผิดชอบเงินคนเดิม ไม่ย้ายยอดจ่ายหรือแก้ประวัติเดิม ใช้ยอดรวมทั้งชุดกำหนดระดับผู้อนุมัติ แต่คำขอใหม่จ่ายได้เฉพาะยอดส่วนเพิ่ม

คง Minor M2-R1/R2-C1 และ HTTPS 504 ไว้ติดตาม พักการทดสอบมือถือจริงและ NAS จริง การเลือกแนวทางหรืออนุมัติเอกสารไม่ถือว่าอนุมัติเริ่มเขียนโค้ด

## 1. เป้าหมายและสิ่งที่ไม่รวม

### สิ่งที่ต้องทำได้

- แบ่งจ่ายหลายงวด โดยแต่ละงวดผ่านผู้ตรวจการเงินก่อนจ่าย
- ไม่จ่ายเกินวงเงิน ไม่จ่ายซ้ำ และไม่ปลดล็อกผลจ่ายที่ไม่ชัดเจนอัตโนมัติ
- ตรวจสิทธิ์ปัจจุบันและแยกหน้าที่ทั้งชุดคำขอเดิมกับส่วนเพิ่ม
- เก็บข้อมูลและหลักฐานทุกฉบับ รวมผลตรวจเก่า เหตุผลแก้ไข และผู้ดำเนินการ
- ปรับคำขอก่อนจ่าย และขอส่วนเพิ่มหลังจ่ายโดยไม่เปลี่ยนประวัติเงินจริง
- รับช่วงเพื่อสะสางงวดค้าง และยุติยอดที่ยังไม่จ่ายผ่านผู้เสนอ–ผู้ยืนยันต่างคน โดยไม่เพิ่มสิทธิ์หรือเปิดให้จ่ายซ้ำ
- แยกวงเงินอนุมัติ ยอดกันไว้ ยอดจ่ายแล้ว และยอดพร้อมจัดงวดให้ผู้มีสิทธิ์เข้าใจตรงกัน

### สิ่งที่ไม่รวม

- การโอนธนาคารอัตโนมัติ การยืนยันจากธนาคารแบบออนไลน์ สกุลเงินอื่น และระบบบัญชีแยกประเภทเต็มรูปแบบ
- การรับรองค่าใช้จ่าย คืนเงิน ปิดคำขออัตโนมัติ และตรวจใบเสร็จค่าใช้จ่ายซ้ำ ซึ่งเป็น 7D
- เบิกคืนภายหลังปิดคำขอ การโอนภาระรับผิดชอบเงินไปบุคคลหรือโครงการอื่น
- การแก้ Minor หรือ HTTPS 504 ไปพร้อมกันโดยปริยาย และการทดสอบมือถือจริง/NAS จริง

ห้ามทำให้การจ่ายครบวงเงินมีความหมายว่าเคลียร์ค่าใช้จ่ายหรือปิดคำขอแล้ว เงินที่จ่ายยังต้องสะสางตาม 7D

## 3. คำขอและยอดเงินสามระดับ

### 3.1 ระดับชุดคำขอ

ชุดหนึ่งประกอบด้วยคำขอหลักและคำขอส่วนเพิ่มที่อ้างอิงกัน มีบริษัท โครงการ และผู้รับผิดชอบเงินเดียวกัน ความเชื่อมโยงต้องตรวจจากเซิร์ฟเวอร์ ไม่เชื่อรหัสชุดที่ client ส่งมาโดยไม่ตรวจ

คำขอส่วนเพิ่มเป็นคำขอใหม่ มีประมาณการเฉพาะเงินเพิ่ม วันที่ต้องการรับเงิน การยืนยัน และผลอนุมัติของตนเอง ยื่นแทนได้ตามสิทธิ์ แต่ผู้รับผิดชอบเงินต้องยืนยันเอง ไม่เพิ่มสิทธิ์ดูคำขออื่นเพราะมีลิงก์เชื่อมกัน

### 3.2 แยกยอดเพื่อไม่ให้จ่ายซ้ำ

- **ยอดคำขอ:** เงินที่ขอในฉบับนั้น เช่น ส่วนเพิ่ม 3,000 บาท
- **ยอดฐานอำนาจอนุมัติ:** วงเงินหลัก + ส่วนเพิ่มที่อนุมัติแล้ว + ส่วนเพิ่มที่กำลังขอ โดยแต่ละคำขอนับครั้งเดียว ไม่บวกยอดรวมสะสมซ้ำ
- **วงเงินจ่ายของคำขอ:** ยอดที่คำขอนั้นได้รับอนุมัติ ไม่ใช่ยอดฐานอำนาจอนุมัติ

ตัวอย่าง: คำขอหลัก 10,000 บาท จ่ายแล้ว 2,000 บาท ขอส่วนเพิ่ม 3,000 บาท ฐานอำนาจอนุมัติคือ 13,000 บาท คำขอหลักยังเหลือวงเงิน 8,000 บาทก่อนหักยอดกันไว้ และคำขอใหม่จ่ายได้ไม่เกิน 3,000 บาทเมื่อผ่านอนุมัติแล้ว ไม่ย้าย 2,000 บาทที่จ่ายแล้วหรือสร้างยอด 10,000 บาทซ้ำ

คำขอที่ปฏิเสธหรือถอนก่อนอนุมัติไม่ให้วงเงินเพิ่ม ไม่บวกยอดร่างเป็นวงเงินจริง หากยุติยอดที่ยังไม่จ่ายของคำขอที่อนุมัติแล้ว ให้ลดเฉพาะวงเงินที่ยังใช้จ่ายได้ แต่ยังนับวงเงินอนุมัติเดิมของคำขอนั้นในฐานอำนาจอนุมัติสะสม เพื่อไม่ให้ยุติแล้วขอส่วนเพิ่มใหม่หลบระดับ ไม่บวกทุกฉบับซ้ำเป็นหลายคำขอ

### 3.3 ความละเอียดและยอดคงเหลือ

ใช้เงินบาทและการคำนวณฐานสิบฝั่งเซิร์ฟเวอร์: จำนวนไม่เกิน 4 ตำแหน่ง อัตรา/ยอดเหมารวมไม่เกิน 2 ตำแหน่ง ปัดแต่ละบรรทัดเป็นสตางค์แบบหลักที่สามตั้งแต่ 5 ปัดขึ้น แล้วรวมตาม 7B ไม่ปัดข้อมูลนำเข้าที่เกินความละเอียดเงียบ ๆ

ยอดงวดและยอดจ่ายเป็นจำนวนบวกไม่เกิน 2 ตำแหน่ง ตรวจ overflow และขอบเขตชนิดข้อมูล ไม่มีการสร้างเพดานธุรกิจใหม่ขึ้นเอง

สำหรับแต่ละคำขอ:

`ยอดจ่ายสำเร็จสะสม + ยอดกันไว้ของงวดที่ยังไม่เสร็จ <= วงเงินอนุมัติที่ใช้จ่ายได้`

`ยอดพร้อมจัดงวด = วงเงินอนุมัติที่ใช้จ่ายได้ - ยอดจ่ายสะสม - ยอดกันไว้`

เมื่อยืนยันจ่ายสำเร็จ ให้ย้ายจำนวนเดียวกันจากกันไว้ไปจ่ายแล้วครั้งเดียว ไม่หักเงินสองรอบ เงินคืนในอนาคตไม่เปิดวงเงินให้จ่ายซ้ำอัตโนมัติ

เมื่อยุติยอดที่เหลือสำเร็จ วงเงินที่ใช้จ่ายได้คงเพียงยอดจ่ายที่บันทึกแล้ว ยอดพร้อมจัดงวดเป็นศูนย์ และสถานะยุติบล็อกการเริ่มจ่าย แยกจากวงเงินอนุมัติเดิมที่ยังใช้เป็นฐานอำนาจอนุมัติสะสม หากยังมีผลจ่ายไม่ชัดเจนต้องสะสางก่อน ไม่ลดวงเงินจนละเมิดยอดที่กันไว้หรือยอดจ่ายจริง

## 4. วงจรงวดจ่าย

| สถานะ | ความหมายและการกันวงเงิน |
|---|---|
| ร่างงวด | ผู้บันทึกจ่ายเตรียมจำนวน ช่องทาง และปลายทาง ยังไม่กันวงเงิน |
| รอตรวจ | ส่งตรวจแล้ว กันวงเงินในธุรกรรมเดียวกับการส่ง |
| ส่งกลับแก้ไข | ระบุเหตุผลและสิ่งที่ต้องแก้ คงยอดกันไว้ |
| ตรวจผ่าน | ตรวจข้อมูลฉบับนั้นแล้ว คงยอดกันไว้ ยังไม่จ่าย |
| กำลังดำเนินการจ่าย | เริ่มก่อนจ่ายภายนอก ล็อกให้ผู้จ่ายคนเดียว คงยอดกันไว้ |
| รอตรวจสอบผล | ผลภายนอกหรือผลการบันทึกไม่ชัดเจน คงล็อกและยอดกันไว้ ห้ามลองจ่ายใหม่ |
| รอยืนยันยกเลิก | หยุดเริ่มจ่าย คงยอดกันไว้จนยืนยันว่าไม่ได้จ่ายจริง |
| ยกเลิกแล้ว | ไม่มีการจ่ายจริง คืนยอดกันไว้ เก็บประวัติ |
| จ่ายแล้ว | บันทึกผลตรงงวดพร้อมวันจ่ายและหลักฐาน ไม่มีการจ่ายรอบสอง |

“เหตุระงับ” แยกจากสถานะงวด อาจมีหลายเหตุพร้อมกัน การแก้เหตุหนึ่งไม่ปลดเหตุอื่น การตรวจสิทธิ์สำเร็จไม่ใช่การปลดเหตุระงับ

ลำดับปกติ: ผู้บันทึกจ่ายเตรียม → ผู้ตรวจการเงินอีกคนตรวจ → ผู้บันทึกจ่ายเริ่มดำเนินการ → จ่ายเงินจริงภายนอก → บันทึกยอดจริง วันจ่าย และหลักฐาน

### 4.1 ตรวจและแก้ไขงวด

- ตรวจทุกงวด ผู้ตรวจและผู้บันทึกจ่ายต้องคนละบุคคล และผ่านกติกาทั้งชุดคำขอ
- เปลี่ยนยอดแม้ลดลง เปลี่ยนช่องทาง หรือเปลี่ยนบัญชีแม้เจ้าของคนเดิม ต้องมีเหตุผลและตรวจใหม่ก่อนจ่าย เก็บผลตรวจเก่าแต่ไม่ใช้กับข้อมูลใหม่
- ส่งกลับยังกันยอดเดิมไว้ เมื่อลดยอดที่บันทึกแล้วคืนเฉพาะส่วนต่าง เพิ่มยอดต้องมีวงเงินว่างพอและตรวจใหม่
- รองรับงวดรอตรวจหลายงวดพร้อมกัน แต่ยอดรวมต้องไม่เกินวงเงิน การส่งพร้อมกันต้องมีผลเหมือนทำตามลำดับ ไม่ให้ทั้งสองรายการใช้ยอดว่างก้อนเดียวกัน
- ผู้ตรวจไม่แก้ข้อมูลแทนผู้บันทึกจ่ายเพื่อผ่านขั้นตรวจ ส่งกลับให้แก้พร้อมเหตุผล

### 4.2 ช่องทางและผู้รับ

โอนเงินต้องมีข้อมูลธนาคาร/บัญชีปลายทาง ผู้ถือบัญชี และหลักฐานโอน เงินสดต้องมีผู้รับและหลักฐานรับเงิน ทั้งสองกรณีจ่ายให้ผู้รับผิดชอบเงินเท่านั้น ไม่ให้ผู้ยื่นแทนหรือบุคคลอื่นรับแทน การตรวจความเป็นเจ้าของบัญชีอาศัยหลักฐานและผู้ตรวจในระยะแรก ไม่กล่าวอ้างว่าระบบตรวจชื่อบัญชีกับธนาคารแล้ว

### 4.3 เริ่มจ่ายและบันทึกผล

ตรวจสิทธิ์ปัจจุบัน ฉบับที่ตรวจผ่าน ผู้รับ ยอด เหตุระงับ และรุ่นข้อมูลอีกครั้งก่อนเริ่ม ล็อกผู้จ่ายตามตัวบุคคลและบันทึกผู้ใช้ที่ลงมือ ป้องกันหลายบัญชีของบุคคลเดียวกันและหลายหน้าจอเริ่มซ้ำ

หลังเริ่ม ไม่อนุญาตแก้ยอด/ช่องทาง/บัญชีหรือยกเลิกแบบปกติ เครือข่ายขาดให้ตรวจสถานะคำสั่งเดิม ไม่ออกคำสั่งโอนภายนอกซ้ำ ไม่มี timeout ที่ปลดล็อกหรือคืนวงเงินเอง

บันทึกผลปกติได้เมื่อยอดและผู้รับตรงงวดที่ตรวจผ่าน วันจ่ายและหลักฐานต้องครบ เวลาเหตุการณ์บันทึกจากเซิร์ฟเวอร์แยกจากวันที่จ่ายที่กรอก ระบบไม่สามารถห้ามคนไปโอนนอกกระบวนการได้ จึงต้องมีคู่มือปฏิบัติงานและการสะสางความคลาดเคลื่อน

### 4.4 ผลไม่ชัดเจน

ผู้บันทึกจ่ายเสนอเหตุผลและหลักฐาน ผู้ตรวจการเงินอีกคนที่มีสิทธิ์ยืนยัน:

| ผลที่ตรวจยืนยัน | การดำเนินการ |
|---|---|
| จ่ายสำเร็จตรงตามงวด | บันทึกจ่ายพร้อมยอด วันจ่าย และหลักฐานครั้งเดียว ห้ามจ่ายซ้ำ |
| ไม่ได้จ่ายเงินจริง | กลับไปตรวจงวดใหม่ คงยอดกันไว้ ไม่กลับเป็นพร้อมจ่ายโดยอัตโนมัติ |
| ยังไม่ชัดเจน หรือยอด/ผู้รับไม่ตรง | คงพักและยอดกันไว้ ไม่คืนวงเงิน ไม่เปิดให้จ่ายซ้ำ |

ไม่ใช้การแก้ metadata กลบการจ่ายผิดยอดหรือผิดคน ใช้กติกาข้อ 4.5 และรับช่วงได้เฉพาะตามข้อ 4.6

### 4.5 พบจ่ายผิดยอดหรือผิดคน

ระงับการเริ่มจ่ายทั้งชุดคำขอหลักและส่วนเพิ่มทันทีที่บันทึกเหตุ พร้อมเหตุผลและหลักฐาน ไม่ใช่พักเฉพาะงวดที่พบปัญหา งวดที่เริ่มไปแล้วต้องสะสางผลต่อ เพราะระบบย้อนหรือหยุดการโอนภายนอกให้เองไม่ได้

หากบันทึกจ่ายแล้ว คงยอดจ่ายและหลักฐานเดิมไว้ เพิ่มเหตุผิดปกติแยกต่างหาก ไม่ย้ายยอดกลับเป็นกันไว้ ไม่คืนวงเงินและไม่ลบผลจ่าย หากยังไม่บันทึกจ่าย คงยอดกันไว้และล็อกของงวดนั้น เก็บยอด/ผู้รับที่พบจริงในหลักฐานเหตุผิดปกติ ไม่บันทึกเป็นการจ่ายตรงงวดทั้งที่ข้อมูลไม่ตรง

ใน 7C ไม่มีคำสั่งปรับยอดเงินจริง คืนเงิน หรือปลดเหตุผิดปกตินี้เพื่อกลับไปจ่าย ระหว่างรอกระบวนการแก้ไขใน 7D ให้คงพักไว้ การแก้ metadata รับช่วงงาน ยุติยอดที่เหลือ หรืออนุมัติส่วนเพิ่ม ไม่ล้างเหตุระงับนี้

### 4.6 ผู้จ่ายเดิมไม่พร้อมหรือหมดสิทธิ์

ผู้บันทึกจ่ายคนใหม่ที่มีสิทธิ์อยู่แล้วในโครงการเสนอรับช่วงงวดค้าง พร้อมเหตุผลและหลักฐาน ผู้ตรวจการเงินอีกคนยืนยัน ทั้งสองคนต้องผ่านการแยกหน้าที่ทั้งชุดคำขอและมีสิทธิ์ปัจจุบัน ขาดคนเข้าเงื่อนไขให้คงพัก ไม่สร้าง grant หรือใช้ admin ข้ามข้อจำกัด

การรับช่วงเปลี่ยนผู้มีสิทธิ์เสนอผลสะสางของงวดนั้นเท่านั้น ให้มีผู้รับผิดชอบปัจจุบันหนึ่งคน ไม่เปลี่ยนผู้ปฏิบัติเดิมในประวัติ ไม่ให้ผู้จ่ายเดิมและคนใหม่ทำงานพร้อมกัน และไม่เปลี่ยนผลตรวจหรือสิทธิ์การอ่านข้อมูลอื่น

ผู้รับช่วงเสนอผลตามสามกรณีในข้อ 4.4 ให้ผู้ตรวจอีกคนยืนยันได้ แต่รับช่วงไม่เท่ากับอนุญาตจ่ายใหม่ ไม่คืนยอดกันไว้หรือปลดล็อกเพราะเปลี่ยนคน การจ่ายครั้งใหม่ทำได้ต่อเมื่อยืนยันว่าไม่จ่ายจริงแล้ว ตรวจงวดใหม่ผ่าน และผ่านการตรวจสิทธิ์/เหตุระงับก่อนเริ่มตามปกติ เก็บผู้เสนอ ผู้ยืนยัน ผู้ปฏิบัติเดิม และผู้รับช่วงครบ

## 5. การยกเลิกและแก้ข้อมูลหลังจ่าย

### 5.1 ยกเลิกงวดที่ยังไม่จ่าย

ผู้บันทึกจ่ายเสนอพร้อมเหตุผล ผู้ตรวจการเงินอีกคนยืนยันว่าไม่ได้จ่ายจริง ระหว่างรอหยุดจ่ายและคงวงเงิน เมื่อยืนยันยกเลิกจึงคืนยอดกันไว้พร้อมเก็บประวัติ ห้ามยกเลิกเพื่อล้างรายการที่จ่ายเงินจริงแล้ว

งวดที่เริ่มจ่ายหรือไม่ทราบผลต้องผ่านการสะสางผลก่อน ไม่ให้คำสั่งยกเลิกชนะผลจ่ายที่กำลังบันทึก การลบร่างที่ยังไม่ส่งและไม่มียอดกันไว้ให้เป็นการเก็บประวัติยุติร่าง ไม่ลบข้อมูลที่ถูกใช้อ้างอิงแล้ว

### 5.2 แก้ข้อมูลที่บันทึกผิดหลังจ่ายถูกต้อง

ใช้รายการแก้ไขเชื่อมกับรายการจ่าย ผู้บันทึกจ่ายเสนอเหตุผลและหลักฐาน ผู้ตรวจอีกคนยืนยัน เก็บข้อมูลก่อน–หลังและหลักฐานเดิม ไม่แก้ยอดเงินหรือผู้รับ ไม่คืนวงเงินและไม่ทำให้รายการกลับมาจ่ายได้

ครอบคลุมวันที่ เลขอ้างอิง และหลักฐาน ไม่ใช้แก้ช่องทางหรือบัญชีของธุรกรรมจริงที่ไม่ตรงงวด หากหลักฐานใหม่บ่งชี้ว่าจ่ายผิด ให้ตั้งเหตุผิดปกติและระงับการเริ่มจ่ายทั้งชุดตามข้อ 4.5 โดยคงยอดจ่ายที่บันทึกแล้วไว้

### 5.3 ยุติยอดที่ยังไม่จ่ายหลังจ่ายบางส่วน

รองรับใน 7C โดยผู้ตรวจการเงินของคำขอเสนอพร้อมเหตุผล แล้วผู้ดำรงบทบาทอนุมัติขั้นสุดท้ายของคำขอนั้นในปัจจุบันยืนยันต่างคน ต้องมีอำนาจครอบคลุมฐานอำนาจอนุมัติที่บันทึกไว้ของคำขอนั้นและผ่านการแยกหน้าที่ทั้งชุด ผู้บันทึกจ่ายไม่เป็นผู้เสนอแทนผู้ตรวจ ไม่มีผู้เข้าเงื่อนไขให้คงพัก

ระหว่างดำเนินการให้หยุดเริ่มจ่ายในคำขอที่ขอยุติ คงยอดกันไว้จนสะสางงวดที่กำลังจ่ายหรือไม่ทราบผล และยืนยันยกเลิกงวดที่ยังไม่จ่ายตามข้อ 5.1 ก่อนทำให้การยุติมีผล การยุติต้องอ้างรุ่นข้อมูลล่าสุด ไม่ยุติจากยอดก่อนทราบผลจริง

เมื่อมีผล ให้ยุติเฉพาะส่วนที่ยังไม่จ่าย เก็บวงเงินอนุมัติเดิมไว้สำหรับประวัติและฐานสะสม ไม่ลบยอดจ่ายหรือเปิดให้ใช้ยอดที่ยุติซ้ำ ยอดจ่ายแล้วยังต้องเคลียร์ค่าใช้จ่ายและคืนเงินเหลือตาม 7D การยุติไม่ใช่การปิดคำขอทางการเงินและไม่ล้างเหตุระงับอื่น

## 6. ปรับวงเงินก่อนมีการจ่าย

ยังไม่มีการจ่ายเงินจริงจึงปรับวงเงินในคำขอเดิมได้ รวมเพิ่มวงเงิน ต้องมีเหตุผล ฉบับใหม่ ผู้รับผิดชอบยืนยัน และอนุมัติใหม่ทุกขั้นจากยอดรวมใหม่กับกติกาที่มีผลล่าสุดสำหรับโครงการ เก็บผลเก่าเป็นประวัติ ไม่ใช้แทนผลใหม่

การเริ่มปรับคำขอที่อนุมัติแล้วต้องระงับการเริ่มจ่ายก่อนเปลี่ยนข้อมูล ไม่ปล่อยให้คำสั่งเริ่มจ่ายกับคำสั่งปรับวงเงินต่างฝ่ายสำเร็จจากสถานะเก่า การเตรียมร่างที่ยังไม่มีผลระงับต้องแสดงชัดว่าร่างไม่รับรองสิทธิ์ปรับ และตรวจใหม่เมื่อจะส่ง

หากมีงวดเริ่มจ่ายแล้วแต่ผลไม่ชัดเจน พักการปรับไว้จนผู้ตรวจยืนยันว่าไม่ได้จ่ายจริง หากจ่ายจริงแล้ว ใช้คำขอส่วนเพิ่ม ไม่เปลี่ยนวงเงินคำขอเดิม แม้ยังไม่ได้บันทึกผลหรือมีเงินคืนภายหลัง ประวัติว่าเคยจ่ายไม่หาย

ก่อนเปิดใช้วงเงินฉบับใหม่ ต้องยืนยันยกเลิกงวดเดิมที่ยังไม่จ่ายและคืนยอดกันไว้ตามกระบวนการผู้บันทึกจ่ายเสนอ–ผู้ตรวจยืนยัน ไม่ยกเลิกหรือคืนเงินกันไว้เองเพียงเพราะเริ่มปรับวงเงิน ต้องครบทั้งการอนุมัติฉบับใหม่และการสะสางงวดเดิมแล้วจึงเปิดใช้วงเงินใหม่ได้ โดยคงเหตุระงับอื่นทั้งหมด

หลังเปิดใช้ฉบับใหม่ จัดงวดใหม่และตรวจใหม่ ไม่ใช้ผลตรวจงวดเดิม และไม่เปิดงวดที่ยกเลิกกลับมา การลดวงเงินต่ำกว่ายอดที่เคยกันไว้จึงต้องรอคืนยอดกันไว้ที่ยืนยันว่าไม่จ่ายครบก่อน ไม่บันทึกวงเงินใหม่ทับแล้วทำให้ยอดพร้อมจัดงวดติดลบ

หากฉบับปรับปรุงถูกปฏิเสธหรือถอน คงระงับการจ่ายไว้ ผู้ตรวจการเงินของคำขอเสนอพร้อมเหตุผลว่าจะกลับใช้เงื่อนไขเดิมหรือยุติยอดที่ยังไม่จ่าย แล้วผู้ดำรงบทบาทอนุมัติขั้นสุดท้ายของคำขอเดิมในปัจจุบันยืนยัน ต้องมีอำนาจครอบคลุมฐานอำนาจอนุมัติเดิมและผ่านการแยกหน้าที่ ผู้เสนอและผู้ยืนยันต่างคน ไม่มีผู้เข้าเงื่อนไขให้คงพัก ไม่มีการปลดอัตโนมัติ

การถอน/ปฏิเสธข้างต้นเป็นผลของฉบับปรับปรุง ไม่ลบคำขอที่เคยอนุมัติ หากกลับใช้เงื่อนไขเดิม งวดที่ยกเลิกแล้วต้องจัดใหม่และตรวจใหม่ งวดที่ยังไม่ยกเลิกต้องตรวจสถานะและผลตรวจปัจจุบันก่อนจ่าย และไม่ปลดเหตุระงับอื่น

## 7. คำขอส่วนเพิ่มหลังมีการจ่าย

### 7.1 กติกาที่ผู้ใช้ยืนยัน

- สร้างคำขอใหม่เฉพาะส่วนเพิ่ม อ้างอิงคำขอเดิม ไม่ยกยอดเดิมมาขอซ้ำ ไม่เปลี่ยนยอดหรือหลักฐานจ่ายเดิม
- โครงการและผู้รับผิดชอบเงินต้องตรงกับคำขอหลัก ผู้ยื่นแทนต้องมีสิทธิ์และผู้รับผิดชอบต้องยืนยัน
- ประเมินขั้นและอำนาจผู้อนุมัติจากยอดรวมทั้งชุด โดยจ่ายคำขอส่วนเพิ่มได้เฉพาะยอดที่อนุมัติของคำขอนั้น
- คำขอใหม่ใช้การยืนยัน กติกาที่มีผลสำหรับโครงการ และลำดับอนุมัติของ 7B ไม่ยกผลเดิมมาใช้
- ภายในชุดเดียวกันมีส่วนเพิ่มที่ส่งแล้วและยังพิจารณาไม่เสร็จได้หนึ่งรายการ รวมส่งกลับแก้ไขและพัก รออนุมัติครบ ปฏิเสธ หรือถอนก่อนส่งรายการถัดไป
- ระหว่างพิจารณาส่วนเพิ่ม คำขอเดิมจ่ายต่อได้ตามกติกาเดิม แต่เหตุระงับอื่นยังอยู่ และห้ามจ่ายส่วนเพิ่มก่อนอนุมัติ
- ไม่เปิดผลอนุมัติคำขอหลักกลับมาเปลี่ยนย้อนหลัง การปฏิเสธส่วนเพิ่มไม่ลบวงเงินเดิม

### 7.2 การคำนวณและข้อมูลตรึงไว้

บันทึกยอดคำขอส่วนเพิ่ม ยอดฐานอำนาจอนุมัติ และรายการคำขอ/ฉบับที่ประกอบฐานนั้นแยกกัน ตรวจจากเซิร์ฟเวอร์และตรึงพร้อมฉบับที่ผู้รับผิดชอบยืนยัน การส่งใหม่หลังถูกส่งกลับประเมินตามกติกาที่มีผลตอนส่งใหม่

คุมการส่งส่วนเพิ่มพร้อมกันด้วยข้อบังคับระดับฐานข้อมูลและธุรกรรม ไม่อาศัยปุ่มหน้าจอ เมื่อมีคำขอส่วนเพิ่มหนึ่งรายการรอตรวจ สถานะส่งกลับหรือพักไม่คืนช่องให้เปิดรายการใหม่หลบงานเดิม การสร้างร่างไม่ได้ให้สิทธิ์จ่ายหรือเปลี่ยนยอดฐานอนุมัติ

คำขอหลักที่ปฏิเสธ ถอน หรือปิดแล้วไม่เปิดเป็นส่วนเพิ่มเพื่อหลบสถานะเดิม การเปลี่ยนโครงการหรือผู้รับผิดชอบไม่ทำผ่านส่วนเพิ่ม ระยะแรกไม่สร้างกระบวนการโอนความรับผิดชอบเงิน

## 8. สิทธิ์และการแยกหน้าที่ทั้งชุด

ใช้การมอบหมายสิทธิ์ 7A ในโครงการและตัวบุคคลจริง ไม่ยกสิทธิ์เพราะเป็น admin ผู้จัดการโครงการ หรือสมาชิกทีม ผู้เสนอสิทธิ์ ผู้อนุมัติสิทธิ์ และผู้รับสิทธิ์ยังต่างคนตามระบบเดิม

| ผู้มีประวัติในชุดคำขอ | ข้อจำกัด |
|---|---|
| ผู้รับผิดชอบเงินหรือผู้ยื่นแทน | ห้ามอนุมัติ ตรวจการเงิน หรือบันทึกจ่ายในชุดเดียวกัน |
| ผู้เคยอนุมัติ | ห้ามเปลี่ยนไปตรวจการเงินหรือบันทึกจ่ายในชุด |
| ผู้เคยตรวจการเงิน | ห้ามอนุมัติหรือบันทึกจ่ายในชุด |
| ผู้เคยบันทึกจ่าย | ห้ามอนุมัติหรือตรวจการเงินในชุด |

คนเดิมทำหน้าที่ที่ไม่ขัดกันซ้ำได้เมื่อมีสิทธิ์ปัจจุบันครบและลงผลใหม่ ผู้อนุมัติยังได้เพียงหนึ่งขั้นต่อฉบับ ห้ามสลับหน้าที่ข้ามงวดหรือข้ามส่วนเพิ่ม ประวัติไม่หายเมื่อถอนสิทธิ์ เปลี่ยนบัญชี หรือเปลี่ยนฉบับ

ต้องบันทึกการมีส่วนร่วมตั้งแต่การลงมือในหน้าที่ เช่น เตรียม/ส่งงวดหรือเริ่มจ่าย ไม่รอจนบันทึกจ่ายสำเร็จแล้วจึงห้ามบุคคลนั้นตรวจงานของตนเอง การตรวจที่ส่งกลับก็เป็นประวัติผู้ตรวจ ไม่ให้สลับหน้าที่เพราะยังไม่ผ่าน

ผู้อนุมัติอ่านเฉพาะงานที่มอบหมาย ผู้ตรวจการเงินและผู้บันทึกจ่ายเข้าถึงตามโครงการ หน้าที่ปัจจุบัน และการแยกหน้าที่ ผู้รับผิดชอบ/ผู้ยื่นแทนอ่านตามสิทธิ์ 7B การรวมประวัติเพื่อตรวจข้อห้ามทำบนเซิร์ฟเวอร์ ไม่คืนรายชื่อหรือหลักฐานอื่นให้ผู้ไม่มีสิทธิ์อ่าน

ผู้อนุมัติที่ได้รับมอบหมายคำขอส่วนเพิ่มเห็นเลขคำขอและยอดอนุมัติของรายการที่ประกอบฐานรวมได้เท่าที่จำเป็นต่อการตัดสินใจ นี่เป็นข้อมูลประกอบในงานที่มอบหมาย ไม่ใช่สิทธิ์อ่านคำขอต้นทางทั้งฉบับ ไม่เปิดเนื้อหา รายการค่าใช้จ่าย บัญชี หรือหลักฐานของคำขออื่นโดยอัตโนมัติ

API คืนเฉพาะข้อมูลประกอบที่อนุญาต และทุกลิงก์ไปคำขอต้นทางยังตรวจสิทธิ์ของปลายทางแยกต่างหาก ไม่ใช้การแสดงเลขคำขอเป็นเหตุให้เพิ่มสิทธิ์ เมื่อพ้นการมอบหมายหรือไม่มีสิทธิ์ปัจจุบัน ให้หยุดเปิดเผยข้อมูลที่อาศัยการมอบหมายนั้น

## 9. หลักฐานและการจัดเก็บ

ข้อเสนอทางเทคนิคของผู้ออกแบบ: หลักฐานการจ่ายรองรับรูปและ PDF เก็บเป็นไฟล์ส่วนตัวแยกจากหลักฐานลงเวลา ไม่บังคับถ่ายสด และไม่ต้องมี GPS การถ่ายหรืออัปโหลดไม่ใช่หลักฐานว่าธนาคารยืนยันธุรกรรมแล้ว

ไฟล์มีตัวระบุคงที่และตัวระบุที่เก็บ ไม่เก็บ absolute path เป็นข้อมูลธุรกิจ ตรวจเนื้อหาไฟล์จริง ขนาด จำนวน และชื่อปลอดภัย ข้อจำกัดปริมาณตั้งค่าได้และระบุในแผน ไม่รับชนิดไฟล์ที่ยังไม่มีตัวตรวจปลอดภัย ไม่เปิดไฟล์ด้วย URL สาธารณะ

การอ่าน/ดาวน์โหลดต้องตรวจสิทธิ์การเงินทุกครั้ง รวมคำสั่งซ้ำและประวัติไฟล์ การแก้หลักฐานเพิ่มฉบับใหม่ ไม่เขียนทับไฟล์เดิม หลักฐานที่ใช้อ้างอิงแล้วไม่ถูกลบโดยหน้าจอแก้ไข

ไฟล์และฐานข้อมูลไม่ใช่ธุรกรรมเดียวกัน ต้องจัดเตรียมไฟล์ให้พร้อมและตรวจ digest ก่อนผูกกับผลจ่าย หากบันทึกฐานข้อมูลล้มเหลวให้ไฟล์ยังไม่ถือเป็นหลักฐานผูกสำเร็จ และมีงานตรวจไฟล์ตกค้างที่ไม่ลบไฟล์ใช้งานจริง หากไฟล์ไม่พร้อมหลังโอนเงินจริง ให้พักบันทึกผลเพื่อสะสาง ไม่ให้ย้อนกลับไปจ่ายซ้ำ

ใช้โฟลเดอร์ที่กำหนดได้และเตรียมตัวเชื่อมที่เก็บสำหรับ NAS โดยไม่อ้างว่าทดสอบ NAS แล้ว ไม่ปรับโครงสร้างการย้ายรูปลงเวลาทั้งระบบในงานนี้ เมื่อย้ายที่เก็บต้องอ้างตัวระบุหลักฐานเดิมและตรวจความครบถ้วนก่อนเปลี่ยนที่อ่าน ไม่ทำให้ประวัติเสีย

## 10. ข้อมูล ธุรกรรม และการป้องกันคำสั่งซ้ำ

ชื่อจริงของตารางและ endpoint ให้ผู้จัดทำแผนกำหนดตามโครงสร้างเดิม แต่ต้องมีหน้าที่ต่อไปนี้:

| ข้อมูล/บริการ | ความรับผิดชอบ |
|---|---|
| ชุดคำขอและชนิดความสัมพันธ์ | แยกส่วนเพิ่มจากการคัดลอก กำกับบริษัท/โครงการ/เจ้าของ ช่องส่วนเพิ่มค้างหนึ่งรายการ และรุ่นชุด |
| ฐานอนุมัติของฉบับ | ยอดขอจริง ยอดใช้ประเมินอำนาจ รายการประกอบ และกติกาที่ตรึงไว้ |
| งวดและฉบับงวด | ยอด ช่องทาง ผู้รับ ปลายทาง ข้อมูลตรวจผ่าน เหตุผล และรุ่นข้อมูล |
| รายการกัน/คืน/ใช้วงเงิน | บันทึกเหตุการณ์ทางการเงินที่ตรวจย้อนกลับได้ แยกจากยอดฐานอนุมัติ |
| ครั้งเริ่มจ่าย | ผู้จ่าย เวลาเริ่ม รหัสคำสั่ง และสถานะผลภายนอก ไม่มีการปลดจากเวลาอย่างเดียว |
| ผลจ่ายและรายการแก้ไข | หนึ่งผลจ่ายต่อครั้งที่ยืนยันสำเร็จ หลักฐาน วันจ่าย และข้อเสนอแก้ metadata ก่อน–หลัง |
| ข้อเสนอและผลตรวจ | ตรวจงวด ยกเลิก สะสางผล และแก้ metadata ต้องตรวจฉบับ/หลักฐานตรงกับที่ผู้ตรวจเห็น |
| เหตุระงับและประวัติ | แยกแต่ละเหตุ ผู้ตั้ง ผู้เสนอปลด ผู้ยืนยัน เหตุผล และการตรวจสิทธิ์ |

ข้อบังคับร่วม:

1. ทุกคำสั่งตรวจสิทธิ์ปัจจุบัน รุ่นคำขอ/งวด/ชุดที่เกี่ยวข้อง และรหัสคำสั่งกันซ้ำ
2. คำสั่งเดิมข้อมูลเดิมมีผลครั้งเดียว รหัสเดิมข้อมูลต่างปฏิเสธ คำสั่งคนละรหัสที่พยายามจ่ายงวดเดิมต้องถูกข้อบังคับสถานะ/ฐานข้อมูลป้องกันด้วย
3. ล็อกตามลำดับที่แน่นอนระหว่างชุด คำขอ และงวด ป้องกันทั้งยอดเกินและประวัติหน้าที่ชนกัน การตรวจสิทธิ์กับบันทึกต้องอยู่ในขอบเขตความสอดคล้องเดียวกัน
4. สถานะ ยอดกันไว้ ยอดจ่าย ประวัติ ผลคำสั่ง และ audit สำเร็จหรือล้มเหลวร่วมกัน ย้อนธุรกรรมรวมกรณี commit ล้มเหลว ไม่ใช้ tracked state ที่ค้างมาแสดงว่าสำเร็จ
5. ห้าม rollback ฐานข้อมูลแล้วอ้างว่าย้อนการโอนภายนอกสำเร็จ การเงินจริงต้องสะสางจากหลักฐาน
6. ตรวจยอดรวมและหน้าที่จากข้อมูลเซิร์ฟเวอร์ ไม่รับจาก client ใช้เวลาจริงของเซิร์ฟเวอร์ตัดสินสิทธิ์หมดอายุ
7. ถ้าตรวจสิทธิ์/กติกา/ไฟล์ไม่ได้ ให้หยุดอย่างปลอดภัย ไม่อนุญาตโดยปริยาย และไม่ล้างเหตุระงับเดิม

## 11. การใช้งานและเกณฑ์รับงาน

### 11.1 ข้อมูลที่ต้องแสดงตามสิทธิ์

ต่อยอดรายละเอียดคำขอและประวัติ 7B ให้แยกวงเงินอนุมัติของคำขอ ยอดจ่าย ยอดกันไว้ ยอดพร้อมจัดงวด ฐานอำนาจอนุมัติ และส่วนเพิ่มอย่างชัดเจน งานผู้ตรวจและผู้บันทึกจ่ายมีรายการที่ต้องลงมือพร้อมเหตุผลพัก ไม่แสดงปุ่มที่ทำไม่ได้แทนการตรวจสิทธิ์บนเซิร์ฟเวอร์

ก่อนเริ่มจ่ายแสดงผู้รับ ยอด ช่องทาง และบัญชีฉบับที่ตรวจผ่านให้ทบทวน หลังเครือข่ายขาดแสดง “กำลังตรวจสอบผล ห้ามจ่ายซ้ำ” และอ่านสถานะล่าสุด ไม่สรุปล้มเหลวเอง หลังคำสั่งสำเร็จโหลดรุ่นล่าสุด ไม่ให้ข้อมูลเก่าล้างหน้าหรือส่งซ้ำ

### 11.2 สิ่งที่ต้องพิสูจน์เมื่อพัฒนา

| รหัส | เกณฑ์ |
|---|---|
| C01 | กันวงเงินเมื่อส่งตรวจ หลายงวดส่งพร้อมกันไม่เกินวงเงิน ส่งซ้ำไม่กันซ้ำ |
| C02 | ส่งกลับคงยอดกันไว้ ลดคืนเฉพาะส่วนต่าง เพิ่มต้องมีวงเงินพอและตรวจใหม่ |
| C03 | เปลี่ยนยอด/ช่องทาง/บัญชีแม้ลดหรือบัญชีเจ้าของเดิม ต้องตรวจใหม่ ผลเก่าไม่รับรองข้อมูลใหม่ |
| C04 | โอน/เงินสดจ่ายได้เฉพาะเจ้าของเงินและต้องมีหลักฐาน ผู้ยื่นแทนรับแทนไม่ได้ |
| C05 | เริ่มจ่ายล็อกผู้จ่ายคนเดียว หลายบัญชี/หน้าจอ/command ID ใหม่ไม่ทำให้จ่ายซ้ำ |
| C06 | ตรวจผ่าน/กันวงเงินไม่ใช่จ่ายแล้ว บันทึกจ่ายย้ายยอดจากกันไว้ครั้งเดียว |
| C07 | เครือข่ายขาด/commit ล้มเหลวอ่านผลได้อย่างปลอดภัย ไม่มี timeout ปลดล็อก |
| C08 | สะสางสามกรณีโดยผู้เสนอและผู้ตรวจต่างคน ไม่มีการ retry จ่ายจากผลที่ยังไม่ชัด |
| C09 | ยกเลิกต้องยืนยันว่าไม่จ่าย คืนยอดครั้งเดียว การชนกับเริ่มจ่ายหรือบันทึกผลมีผลได้ทางเดียว |
| C10 | แก้ metadata หลังจ่ายเก็บก่อน–หลัง ไม่เปลี่ยนยอด/ผู้รับ ไม่คืนวงเงิน ไม่เปิดจ่ายซ้ำ |
| C11 | ก่อนจ่ายปรับวงเงินต้องระงับ ยืนยันใหม่ และอนุมัติใหม่ ผลไม่ชัดบล็อก จ่ายแล้วห้ามปรับเดิม |
| C12 | ส่วนเพิ่มเฉพาะส่วนต่าง โครงการ/เจ้าของเดิม ไม่สร้างยอดหรือผลอนุมัติเดิมซ้ำ |
| C13 | ฐานอนุมัติสะสมถูกต้องทั้งเลือกขั้น เลือกบุคคล และตรวจสิทธิ์ตอนลงผล แต่จ่ายเฉพาะยอดคำขอ |
| C14 | ส่งส่วนเพิ่มพร้อมกันมีค้างได้หนึ่งรายการ รวมส่งกลับ/พัก ไม่จำกัดหลายงวดจ่ายที่ถูกต้อง |
| C15 | วงเงินเดิมจ่ายต่อได้ระหว่างขอส่วนเพิ่ม แต่เหตุระงับอื่นยังอยู่และไม่ใช้วงเงินใหม่ก่อนอนุมัติ |
| C16 | แยกหน้าที่ทั้งชุด ทุกฉบับ ทุกงวด หลายบัญชี ถอน/ให้สิทธิ์ใหม่ไม่ล้างประวัติ |
| C17 | รายการ รายละเอียด หลักฐาน และผลคำสั่งซ้ำไม่รั่วข้ามสิทธิ์ admin/สมาชิกทีมไม่มีสิทธิ์อัตโนมัติ |
| C18 | ไฟล์ปลอม เกินข้อจำกัด ผิดขอบเขต หรือผูกไฟล์ไม่พร้อมถูกปฏิเสธ หลักฐานเดิมไม่ถูกเขียนทับ |
| C19 | กติกา/สิทธิ์เปลี่ยนพร้อมคำสั่ง การคืนยอด/ใช้ยอด/บทบาทชนกัน และ rollback ทดสอบกับฐานข้อมูลจริง |
| C20 | ระบบ 7A/7B เดิมไม่ถดถอย แยก copy reference จาก supplemental family และข้อมูลเดิมไม่มีวงเงินเพิ่มเอง |
| C21 | พบจ่ายผิดก่อนหรือหลังบันทึกผลแล้วระงับเริ่มจ่ายทั้งชุด คงยอดและหลักฐานเดิม ไม่มีทางแก้ metadata หรือรับช่วงเพื่อปลดเหตุนี้ |
| C22 | การปรับวงเงินต้องรอทั้งอนุมัติใหม่และยกเลิกงวดเดิม/คืนยอดกันไว้ครบ ถอนหรือปฏิเสธไม่กลับมาจ่ายเอง |
| C23 | รับช่วงงวดค้างได้เฉพาะผู้มีสิทธิ์กับผู้ตรวจต่างคน มีผู้เสนอผลปัจจุบันหนึ่งคน ไม่เปลี่ยนประวัติ ไม่เพิ่ม grant หรือเปิดจ่ายซ้ำ |
| C24 | ยุติยอดที่เหลือไม่ลดยอดจ่ายแล้ว ไม่ปิดคำขอ และไม่ลดฐานอำนาจอนุมัติสะสม งวดไม่ทราบผลไม่ถูกคืนยอดโดยพลการ |
| C25 | ผู้อนุมัติส่วนเพิ่มเห็นเฉพาะเลขคำขอ/ยอดประกอบที่อนุญาต ไม่มีรายละเอียดหรือหลักฐานต้นทางรั่ว และตรวจสิทธิ์เมื่อเปิดลิงก์/พ้นการมอบหมาย |

เกณฑ์เหล่านี้เป็นงานทดสอบในอนาคต ไม่ใช่ผลที่รันแล้ว แผนพัฒนาต้องใช้ TDD แยกผู้ลงมือกับผู้ตรวจ และรัน Test, Build, Lint ครบก่อนอ้างว่างานพัฒนาเสร็จ พอร์ต dev 4000 และ production preview 4001 ตามโครงการ ไม่ลดการตรวจ TLS/session เพื่อให้เทสต์ผ่าน

## 12. ผลตรวจแบบและขอบเขตการตัดสินใจ

ผู้ตรวจอิสระพบประเด็นธุรกิจ 5 ข้อ และผู้ใช้ยืนยันครบแล้วเมื่อ 24 ตุลาคม 2569 จึงรวมคำตอบไว้ในกติกาหลัก ไม่ต้องตัดสินใจเรื่องเดิมซ้ำตอนเขียนแผน:

| ประเด็นที่ยืนยัน | กติกาในเอกสาร | เกณฑ์รับงาน |
|---|---|---|
| จ่ายผิดให้ระงับทั้งชุด คงประวัติ รอแก้เงินจริงใน 7D | ข้อ 4.5 | C21 |
| ปรับวงเงินก่อนจ่ายต้องสะสางงวดเดิม ถอน/ปฏิเสธยังพัก | ข้อ 6 | C11, C22 |
| ผู้มีสิทธิ์รับช่วงเพื่อสะสางเท่านั้น ผู้ตรวจอีกคนยืนยัน | ข้อ 4.6 | C23 |
| ยุติยอดที่ยังไม่จ่ายได้ แต่คงยอดจ่ายและฐานสะสมเดิม | ข้อ 3.2–3.3 และ 5.3 | C24 |
| ผู้อนุมัติเห็นเลขคำขอ/ยอดประกอบ ไม่ได้สิทธิ์อ่านต้นทาง | ข้อ 8 | C25 |

รายละเอียดทางเทคนิคที่ผู้ออกแบบเสนอไว้ให้ผู้ทำแผนปรับได้: ชื่อสถานะภายใน การแยกตาราง/บริการตามหน้าที่ หลักฐานรูป/PDF และข้อจำกัดไฟล์ที่ตั้งค่าได้ กลไกล็อก/ดัชนีที่พิสูจน์ความถูกต้อง และการแสดงผลโดยไม่เปลี่ยนกติกาธุรกิจ ไม่มีการอนุมัติให้ขยายสิทธิ์หรือเพิ่มช่องทางจ่ายจากการเลือกเทคนิคเหล่านี้

## 13. งานติดตามและขั้นถัดไป

| รายการ | สถานะ |
|---|---|
