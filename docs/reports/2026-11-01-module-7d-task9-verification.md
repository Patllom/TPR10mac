# ผลตรวจรับ Module 7D Task 9 — แก้เงินคืนและรายการปรับปรุงหลังปิด

สถานะ: ผ่านผู้ตรวจอิสระและ Test, Build, Lint/Format ครบตามหลักฐานท้ายรายงาน

- เสนอแก้เงินคืนพร้อมเหตุผลและหลักฐาน ผู้ตรวจการเงินอีกคนยืนยัน จึงลงผลต่างจากยอดสุทธิฉบับล่าสุด ไม่แก้ต้นฉบับและไม่ใช้ผลต่างซ้ำ
- คำขอที่ปิดแล้วคง Closed และ ClosureRecord เดิม ใช้เคสปรับปรุงแยก เช่น แก้ยอดคืน 2,000 เป็น 1,500 เกิดยอดต้องรับเพิ่ม 500 หลังยืนยัน
- ยอดบวกของเคสรับเพิ่มผ่านเจ้าของยืนยันและการเงินตรวจรับ ยอดลบใช้ผู้บันทึกจ่ายเสนอผลจ่ายภายนอกพร้อมหลักฐาน แล้วผู้ตรวจอีกคนยืนยัน ไม่เปิดวงเงินเก่าหรือสั่งโอนธนาคาร
- เก็บยอดเคสบวกและลบตามจริง ปิดเคสใน transaction เมื่อยอดศูนย์และไม่มีรายการรอตรวจหรือส่งกลับค้าง เก็บประวัติการปิดเคสแยก
- ส่งกลับ ปฏิเสธ ยกเลิก หรือเสนอแทนรายการยังไม่รับรองได้ตามสิทธิ์พร้อมประวัติ รักษากติกาแยกหน้าที่และตรวจสิทธิ์ปัจจุบันก่อน replay
- เพิ่มประวัติการจ่ายและปิดเคส พร้อม migration, scoped FK และข้อบังคับห้ามแก้ข้อมูลรับรองแล้ว ตรวจ Down/Up และการปฏิเสธ downgrade เมื่อมีข้อมูลในฐานจำลอง ไม่ได้ migrate ฐานจริง
- อัปโหลดหลักฐานหลังปิดจำกัดตามเป้าหมายและสิทธิ์ ไม่เปิดสิทธิ์ทั่วไปหรือเพิ่ม Payer ให้เจ้าของเงิน

ผู้ลงมือ Tesla และผู้ตรวจ Heisenberg แยกกัน รีวิวแรกพบ T9-R1 หลักฐานจ่ายซ้ำข้ามคำขอ และ T9-R2 การลงทะเบียนบริการในแอปไม่ครบ แก้พร้อม RED/GREEN แล้วผู้ตรวจซ้ำให้ ADDRESSED ทั้งสองข้อ ไม่พบ Critical/Important/Minor ใหม่

Source สุดท้าย fix1-v3 ผ่าน focused31/31, regression51/51 และ full-solution Format ผล freeze ก่อนหน้าเก็บเป็นประวัติ ไม่ใช้แทนผลสุดท้าย การตรวจตัวเองพบ SQL CHECK ยอมรับ NULL ในฐานยอดเคส แก้ด้วย IS NOT NULL และเพิ่มเทสต์ฐานข้อมูลจริงแล้ว

กันไฟล์หลักฐานจ่ายซ้ำทุก hash ใน workspace เดียวกันทั้งเสนอและยืนยัน โดยรับ proof lock ก่อน family/request มีเทสต์ concurrency และการ resolve บริการผ่าน DI จริง ไม่ครอบคลุมสลิปคนละ bytes ที่เป็นเหตุจ่ายเดียวกันหรือต่าง workspace และ global proof lock มีผลแลกเปลี่ยนด้าน throughput เมื่อหลาย workspace ส่งคำสั่งพร้อมกัน
