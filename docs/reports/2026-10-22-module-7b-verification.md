เทสต์ส่งมอบสุดท้ายมี 19 กรณี ครอบคลุมยื่นเอง/แทนต่างขอบเขต หลายฉบับ/หลายกติกา สิทธิ์และข้อห้ามระดับบุคคล Held กลับขั้นเดิม การปฏิเสธ/ถอน/คัดลอก คำสั่งซ้ำ การแข่งขันอนุมัติท้ายสุดกับถอน และ rollback ผ่าน HTTP พร้อม snapshot ของข้อมูลธุรกิจ ประวัติ audit และ receipt กรณีที่ล้มเหลวระหว่างพัฒนาแยกไว้ว่าเป็น product regression หรือ fixture ไม่ใช้ log เหล่านั้นเป็นผลผ่าน

Migration ทดสอบ backup/restore ฐาน 7A สังเคราะห์ลงฐาน disposable แยก เปรียบเทียบทุกคอลัมน์เดิมใน 57 ตาราง จำลอง DDL ล้มเหลวแล้วตรวจ rollback ก่อน upgrade สำเร็จ สิทธิ์เดิมไม่ถูกเติมระดับอนุมัติเอง และทดสอบ idempotent SQL ช่วง 7A→7B ซ้ำสองครั้งโดยข้อมูลเดิมไม่เปลี่ยน ไม่มีการใช้ฐานผู้ใช้จริง ส่วนไฟล์ SQL เต็มจาก CLI สร้างสำเร็จ exit 0 แต่ไม่อ้างว่านำไฟล์เต็มนี้ไป execute สองครั้ง

ตัวอย่างวัด path ใหม่: GET ห้ารายการ (list, screen, history, รายการฉบับ, รายละเอียดฉบับ; page size 1) ใช้ 268 queries ทั้งกรณีมี 4 และ 20 คำขอ เวลา 273.3 และ 263.5 ms ตามลำดับ เป็นตัวอย่างครั้งเดียวในเครื่องทดสอบ รวมการตรวจ session/สิทธิ์/lock ไม่มี concurrent load หรือการแยกวัด lock-wait ไม่ใช่ SLA และไม่ปิด M2

การตรวจ HTTPS รอบแรก: คำขอ 7B ที่ 4000 ผ่าน 9/10 กรณี กรณีใหม่ WB-I2 timeout รอช่องผู้รับผิดชอบขณะหน้าแสดง `main` ว่าง จึงหยุดชุดตรวจ exit 1 และเก็บ `task-10-prefinal-https4000-request-failed.log` ตรวจ fixture แล้ว scope 22 มีสิทธิ์/สายงานครบ รันกรณีเดิมแยกผ่าน 1/1 exit 0 (7.1 วินาที) โดยไม่แก้ source ไม่เพิ่ม timeout ไม่ลด assertion **ยังยืนยันสาเหตุ timeout เดิมไม่ได้ และไม่อ้างว่าแก้แล้ว** จึงรัน final gates เต็มใหม่พร้อม diagnostics ตามผลด้านล่าง; ผลรอบแรกไม่ใช่ผลผ่าน

### เทสต์ PR7-R1

เพิ่มกรณีใน WB-I2 โดยใช้ broadcast เปลี่ยนบัญชีระหว่างเปิดฉบับย้อนหลังและมีคำตอบ HTTP 200 ค้างอยู่ เทสต์กักการโหลดเอกสารใหม่ไว้ก่อน ตรวจว่าเอกสารเดิมซ่อนและนำข้อมูลส่วนตัวออกแล้ว จากนั้นปล่อยคำตอบเก่าที่มาช้าและตรวจว่าไม่พบข้อมูลกลับมาในช่วงสังเกต ทั้งหมดต้องเกิดก่อน `pagehide` จึงไม่ใช้การเปลี่ยนหน้าเป็นหลักฐานแทนการล้างข้อมูล สุดท้ายปล่อย reload จริงและตรวจหน้าปฏิเสธสิทธิ์ของบัญชีใหม่แยกอีกครั้ง

การกักคำตอบทำที่ขอบเขต `fetch` เฉพาะ URL ที่ทดสอบ โดยใช้ body/status/headers จากเซิร์ฟเวอร์จริง จำลองกรณีผลสำเร็จกลับมาหลังการยกเลิก ไม่อ้างว่า native fetch ยังคงส่งคำตอบได้เสมอหลัง abort และไม่เพิ่ม hook ในโค้ดผลิตภัณฑ์

เทสต์แรกติดกลไก Playwright ที่รอ navigation และการ fulfill route ที่ถูกยกเลิก ไม่ใช่ RED ของผลิตภัณฑ์ แก้เฉพาะการสังเกตเอกสารเดิมและจังหวะปล่อยคำตอบแล้ว focused HTTPS 4000 ผ่าน 1/1 บนโค้ดผลิตภัณฑ์เดิม การควบคุมเชิงลบเปลี่ยนเฉพาะข้อความ broadcast เป็นข้อความที่ไม่รู้จัก ทำให้ assertion การซ่อนข้อมูลล้มเหลวด้วย `Expected: false / Received: true`; คืนข้อความจริงแล้วผ่านอีกครั้ง ไม่ถือเป็นหลักฐานว่าผลิตภัณฑ์เดิมมีบั๊ก

### หลักฐานวินิจฉัย HTTPS 504

Log เดิมพบ public JavaScript สองไฟล์ตอบ 504 หลังประมาณ 60 วินาที โดยเวลาเชื่อมต่อและเวลารับ header เป็น `-` ตามคำอธิบายของผู้พัฒนา nginx ค่าเวลาเชื่อมต่อจะถูกบันทึกเมื่อเชื่อมต่อสำเร็จ หลักฐานจึงชี้ไปยังช่วงเชื่อมต่อ nginx → upstream มากกว่าการรอ API แต่ยังไม่บอกว่าเหตุใดการเชื่อมต่อจึงค้าง และยังไม่ใช่หลักฐานว่า Docker, Next หรือระบบปฏิบัติการตัวใดผิด [อ้างอิงการอธิบายตัวแปร upstream ของ nginx](https://mailman.nginx.org/pipermail/nginx-devel/2024-February/XVZPSFY3G43OXSSJO45VRZMG26KNBLA5.html)

ทดลองแยกระบบบัญชี/ฐานข้อมูลออก ใช้ nginx จาก template จริงผ่าน TLS ไปยัง HTTP server สังเคราะห์ที่ `127.0.0.1:4001` ผ่าน `host.docker.internal` รวม 283 คำขอ (277 ผ่าน proxy และ 6 ตรวจตรง) ครอบคลุมครั้งละ 6 คำขอ การใช้ connection ฝั่ง client → proxy ซ้ำ/เปิดใหม่ และพัก 4.9/5.1/6 วินาที ไม่ได้บังคับให้ทุกคำขอเปิด upstream connection ใหม่ ผลผ่าน HTTP 200 ทั้งหมด สูงสุด 14 ms ในรอบนี้ โดยไม่มี asset error ไม่เปลี่ยนค่า timeout/retry หรือความเชื่อถือ CA ระดับเครื่อง ผลนี้ **ไม่พิสูจน์ว่าแก้ 504 แล้ว** และไม่ใช่การทดสอบโหลดเพื่อรับรอง SLA

### ผลตรวจอิสระและขอบเขตการรับรอง

Epicurus ตรวจ diff และ hash ของเทสต์ตรงกับผู้ลงมือแล้ว ผ่านข้อกำหนดและคุณภาพ ไม่มี Critical/Important พบข้อจำกัดระดับ Minor สองเรื่องที่คงไว้เป็นขอบเขตเทสต์ ไม่ใช่บั๊กผลิตภัณฑ์ที่ยืนยันแล้ว:

- R1-L1: flag การปล่อย response และการเดินนาฬิกา 100 ms ไม่ใช่การยืนยันว่า callback ผู้รับทำงานเสร็จทุกกรณี จึงไม่รับรอง callback ที่อาจช้ากว่าช่วงสังเกตหรือ guard แต่ละชั้นแยกจากกัน
- R1-L2: MutationObserver ตรวจ DOM ณ ตอน callback ไม่ได้ตรวจทุก `addedNodes` จึงไม่รับรองการแทรกแล้วลบ node ภายในจังหวะเดียวกัน หรือการเปลี่ยน attribute ทุกแบบ

ผลนี้รับรองสถานการณ์ Firefox และข้อมูลที่เทสต์เลือกตรวจ รวมการนำ subtree ออกก่อน navigation และการปฏิเสธสิทธิ์หลัง reload ไม่ใช่หลักประกันทุก browser/ทุกลำดับเหตุการณ์ ผู้ตรวจเห็นตรงกันว่าไม่มีหลักฐานเพียงพอให้ปิด 504 หรือแก้ค่า transport แบบคาดเดา
