## ประเด็นที่ผู้ตรวจฝากให้ยืนยันจาก dependency

- สิทธิ์และลำดับล็อก: ตรวจ `PaymentAccess` และ `FamilyParticipation` ปัจจุบัน ยังคงตรวจ actor/person/grant และประวัติทั้งชุด ก่อนทำงานในธุรกรรม; advisory lock 7241002 ตามด้วย Family → Request → Installment คงหลักฐาน Task 2–3 และ regression ที่ผ่านรอบนี้
- ขอบเขตเงิน: migration ใช้ PostgreSQL numeric พร้อม CHECK ยอดไม่เกิน 9999999999999999.99 และเท่ากับ trunc(amount,2) ตรงกับบริการ ไม่ได้เพิ่มเพดานธุรกิจใหม่ และไม่อ้างว่าคอลัมน์เป็น numeric(18,2) โดยตรง
- Commit failure: เทสต์ Task 3 `Failure_rolls_back_every_effect_and_clears_reusable_context(failure: "commit")` ใช้ deferred PostgreSQL trigger และผ่านอีกครั้งใน Full G นี้; Task 4 เพิ่มการทดสอบ save failure ของบริการ ไม่อ้างว่าทุก transition มีเทสต์ commit failure แยกใหม่
- ประวัติ: revision มี DB guard ป้องกันแก้เนื้อหา/ลบ ส่วน `InstallmentReview` proposal บริการเพิ่มแถวใหม่เท่านั้น ปัจจุบันไม่มีช่องทางอื่นแก้ผลตรวจชนิดนี้ ไม่อ้างว่า proposal ทุกชนิดถูกบังคับ append-only โดยฐานข้อมูล; Task 7–8 ที่เพิ่มบริการ proposal ต้องรักษาผลตรวจเก่าและแยกชนิดคำสั่งให้ชัด

ข้อข้างต้นเป็นการยืนยันขอบเขตและ dependency ไม่พบช่องว่างที่ต้องแก้โค้ด Task 4 หลัง Full G

## พฤติกรรมที่เพิ่ม

- สร้างงวดร่างโดยไม่กันเงิน ส่งตรวจแล้วจึงกันวงเงิน รองรับหลายงวดโดยไม่เกินยอดที่ใช้จ่ายได้
- ส่งกลับยังคงวงเงิน แก้ลดคืนเฉพาะส่วนต่าง แก้เพิ่มต้องมีวงเงินเพียงพอ เปลี่ยนยอด ช่องทาง หรือบัญชีต้องระบุเหตุผลและตรวจใหม่

- โอนหรือเงินสดต้องรับโดยผู้รับผิดชอบเงินเท่านั้น ตรวจสิทธิ์ปัจจุบันและข้อห้ามแยกหน้าที่ ใช้ธุรกรรมและคำสั่งกันซ้ำจาก Task 3
